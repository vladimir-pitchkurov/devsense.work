# Планы выполнения и типы сканирования

Для оптимизации медленных SQL-запросов необходимо понимать, как именно СУБД извлекает данные с диска или из оперативной памяти. Оптимизатор запросов оценивает множество альтернативных путей и строит наиболее эффективный **план выполнения (Execution Plan)** на основе стоимостных оценок. Анализируя планы выполнения с помощью команды `EXPLAIN`, вы сможете обнаружить узкие места: полные сканирования таблиц, неоптимальный порядок соединения таблиц или проигнорированные индексы. Хотя PostgreSQL и MySQL используют разную терминологию и способы визуализации планов, принципы сканирования в них во многом совпадают.

---

## 1. Генерация и чтение планов выполнения

Обе СУБД предоставляют разработчикам инструменты для детального анализа выполнения запросов.

### PostgreSQL: EXPLAIN и EXPLAIN ANALYZE
В Postgres команда `EXPLAIN` возвращает расчетную стоимость (cost), запланированную оптимизатором. Добавление ключевого слова `ANALYZE` заставляет СУБД выполнить запрос, показывая реальное время работы и количество обработанных строк.
* **Стоимостные метрики (Cost)**: Отображаются в формате `cost=startup..total` (например, `cost=0.00..45.10`). Стоимость — это условная единица (где `1.0` равен стоимости последовательного чтения одной страницы с диска).
* **Фактическое время**: Отображается в миллисекундах.

```sql
-- PostgreSQL: Просмотр фактической статистики выполнения запроса
EXPLAIN (ANALYZE, BUFFERS, COSTS)
SELECT email FROM users WHERE status = 'active';
```
*Опция `BUFFERS` показывает количество прочитанных страниц из кэша (shared buffers) и с диска.*

### MySQL: EXPLAIN и EXPLAIN ANALYZE
Исторически MySQL выводил результат команды `EXPLAIN` в табличном виде. Начиная с версии 8.0, СУБД поддерживает команду `EXPLAIN ANALYZE`, которая строит дерево выполнения с реальным временем работы и затратами на каждом узле.

```sql
-- MySQL: Вывод плана выполнения в виде дерева с замером времени
EXPLAIN ANALYZE
SELECT email FROM users WHERE status = 'active';
```

## 2. Типы сканирования в PostgreSQL

PostgreSQL выбирает метод сканирования в зависимости от наличия индексов, объема таблицы и селективности фильтров.

```
Выбор типа сканирования в PostgreSQL:
Селективность:  Высокая (1-2 строки)     Средняя (5-15%)      Низкая (Вся таблица)
Метод:          [Index Scan]         ->  [Bitmap Scan]   ->  [Seq Scan]
```

### Последовательное сканирование (Seq Scan / Sequential Scan)
* **Суть**: СУБД последовательно читает весь файл таблицы (heap) от начала до конца, проверяя условие `WHERE` для каждой строки.
* **Когда применяется**: Если для колонок в запросе нет подходящего индекса или если оптимизатор считает, что прочитать всю таблицу быстрее, чем использовать индекс (низкая селективность).

### Сканирование индекса (Index Scan)
* **Суть**: База данных просматривает B-Tree индекс для поиска идентификаторов подходящих строк (TID), после чего точечно считывает страницы таблицы (heap) с этими строками.
* **Недостаток**: Если под условие попадает много строк, постоянные переходы между страницами индекса и страницами таблицы приводят к большому количеству случайного I/O.

### Битовое сканирование (Bitmap Index Scan и Bitmap Heap Scan)
* **Суть**: Компромиссный вариант при выборке среднего количества строк.
  1. **Bitmap Index Scan** просматривает индекс и создает в памяти карту битов (bitmap) с адресами страниц таблицы, содержащих нужные строки, сортируя их по физическому расположению на диске.
  2. **Bitmap Heap Scan** последовательно читает страницы по этой карте, исключая повторное чтение одной и той же страницы и уменьшая хаотичный дисковый ввод-вывод.

### Сканирование только индекса (Index Only Scan)
* **Суть**: СУБД получает все необходимые данные прямо из листьев индекса, не обращаясь к самой таблице.
* **Важное условие**: Для выполнения этого сканирования Postgres сверяется с **картой видимости (Visibility Map)**. Если страница помечена как измененная ("грязная"), СУБД все равно придется сходить в таблицу для проверки видимости версии строки.

## 3. Типы доступа в MySQL (InnoDB)

В выводе `EXPLAIN` в MySQL ключевую роль играет колонка `type`, описывающая способ доступа к строкам. Типы перечислены от самого быстрого к самому медленному:

### const / system
* В таблице содержится не более одной подходящей строки (например, поиск по первичному ключу `PRIMARY KEY` или по `UNIQUE` индексу с константным значением). Работает мгновенно.

### eq_ref
* Используется при соединении таблиц (JOIN). Для каждой строки из предыдущей таблицы считывается ровно одна строка из текущей по первичному ключу или уникальному индексу.

### ref
* СУБД считывает строки, используя обычный (неуникальный) индекс. Под условие может подходить несколько строк.

### range
* Поиск строк по индексу в заданном диапазоне значений (запросы с операторами `>`, `<`, `BETWEEN`, `IN`).

### index (Full Index Scan)
* MySQL сканирует дерево индекса целиком. Это аналог `Index Only Scan` в PostgreSQL. Таблица на диске не сканируется, но читается весь файл индекса.

### ALL (Full Table Scan)
* Полное сканирование таблицы. MySQL считывает абсолютно все строки с диска. Это самый медленный тип доступа, которого следует избегать на больших таблицах.

## 4. Сравнительная таблица типов сканирования

| Концепция сканирования | Название в PostgreSQL | Тип в MySQL (InnoDB) | Описание |
| :--- | :--- | :--- | :--- |
| **Полное сканирование таблицы** | `Seq Scan` | `ALL` | Сканирование всех строк таблицы; максимальный I/O. |
| **Поиск по индексу** | `Index Scan` | `ref` или `range` | Поиск по индексу с последующим доступом к таблице. |
| **Поиск только по индексу** | `Index Only Scan` | `index` | Чтение данных исключительно из листьев индекса. |
| **Пакетный поиск по индексу** | `Bitmap Index/Heap Scan`| N/A | Группировка адресов строк по страницам для оптимизации I/O. |
| **Поиск константы** | `Index Scan` (1 строка) | `const` | Мгновенный поиск одной строки по уникальному ключу. |

## 5. Резюме и лучшие практики

1. **Используйте ANALYZE для реальных тестов**: Стандартный `EXPLAIN` показывает лишь гипотетические оценки. Всегда запускайте `EXPLAIN ANALYZE` (на тестовых базах), чтобы увидеть реальное время выполнения и объем памяти.
2. **Следите за деградацией Index Only Scan**: Если в плане PostgreSQL узел `Index Only Scan` показывает большое число обращений к таблице (`Heap Fetches`), выполните `VACUUM` для обновления карты видимости.
3. **Избегайте типа ALL в MySQL**: Если запрос к большой таблице показывает `type: ALL` или `Extra: Using join buffer`, это сигнал о необходимости добавления покрывающего индекса.
4. **Актуализируйте статистику**: Если оптимизатор выбирает неоптимальный план, возможно, статистика распределения данных устарела. Запустите `ANALYZE TABLE имя_таблицы;` в MySQL или `ANALYZE имя_таблицы;` в PostgreSQL.
