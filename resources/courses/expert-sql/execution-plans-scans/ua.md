# Плани виконання та типи сканування

Щоб оптимізувати повільні запити до бази даних, ви повинні розуміти, як саме база даних отримує дані. Оптимізатор запитів оцінює кілька шляхів виконання та будує **план виконання (Execution Plan)** на основі оцінки вартості. Аналізуючи плани виконання за допомогою `EXPLAIN`, ви можете виявити вузькі місця, такі як повне сканування таблиць (full table scans), неправильний порядок об'єднання або проігноровані індекси. PostgreSQL та MySQL використовують різну термінологію та методи візуалізації планів, але їхні базові методи сканування мають спільні концепції.

---

## 1. Генерація та читання планів виконання

Обидва рушії баз даних надають інструменти для аналізу виконання запитів.

### PostgreSQL: EXPLAIN та EXPLAIN ANALYZE
У Postgres `EXPLAIN` повертає розраховану планувальником вартість запиту. Додавання ключового слова `ANALYZE` змушує базу даних виконати запит, надаючи реальний час виконання та фактичну кількість отриманих рядків.
* **Показники вартості (Cost Metrics)**: представлені у форматі `cost=startup..total` (наприклад, `cost=0.00..45.10`). Вартість — це відносна одиниця (де `1.0` відповідає вартості послідовного зчитування однієї сторінки з диска).
* **Фактичний час виконання (Actual Runtimes)**: вказується в мілісекундах.

```sql
-- PostgreSQL: Перевірка реальної статистики виконання
EXPLAIN (ANALYZE, BUFFERS, COSTS)
SELECT email FROM users WHERE status = 'active';
```
*Опція `BUFFERS` показує інформацію про зчитування блоків із розділюваної пам'яті (shared memory hits та reads з диска).*

### MySQL: EXPLAIN та EXPLAIN ANALYZE
Історично MySQL використовував табличний формат для виводу `EXPLAIN`. У MySQL 8.0 було представлено `EXPLAIN ANALYZE`, який виводить плани у вигляді дерева з реальними витратами часу та вартості виконання.

```sql
-- MySQL: Візуалізація у вигляді дерева з реальним часом виконання
EXPLAIN ANALYZE
SELECT email FROM users WHERE status = 'active';
```

## 2. Типи сканування в PostgreSQL

PostgreSQL обирає один із кількох методів сканування на основі наявності індексів, розміру таблиці та селективності даних.

```
Схема вибору сканування у PostgreSQL:
Селективність: Висока (1-2 рядки)      Середня (5-15%)       Низька (Вся таблиця)
Метод:         [Index Scan]     ->  [Bitmap Scan]    ->  [Seq Scan]
```

### Послідовне сканування (Seq Scan)
* **Що робить**: повністю зчитує файл купи (heap) таблиці від початку до кінця, перевіряючи умову `WHERE` для кожного рядка.
* **Коли виникає**: використовується, коли для запиту немає відповідного індексу або коли планувальник вважає, що сканування більшої частини таблиці буде швидшим, ніж використання індексу.

### Сканування індексу (Index Scan)
* **Що робить**: сканує індекс B-Tree для пошуку фізичних адрес (TID) відповідних рядків, а потім отримує ці конкретні блоки з купи таблиці.
* **Недолік**: якщо збігів багато, постійні переходи між сторінками індексу та сторінками купи створюють вузьке місце через велику кількість випадкового введення-виведення (random I/O).

### Bitmap Index Scan та Bitmap Heap Scan
* **Що робить**: використовується, коли Postgres вибирає помірну кількість рядків.
  1. **Bitmap Index Scan** зчитує індекс і будує в пам'яті бітову карту (bitmap) потрібних сторінок купи, сортуючи TID за їхнім фізичним розташуванням на диску.
  2. **Bitmap Heap Scan** послідовно зчитує відсортовані сторінки, запобігаючи випадковому I/O та повторному читанню одних і тих самих сторінок.

### Сканування тільки індексу (Index Only Scan)
* **Що робить**: отримує дані безпосередньо з листових вузлів індексу без звернення до купи таблиці.
* **Застереження щодо карти видимості (Visibility Map)**: Postgres має перевірити **карту видимості**, щоб переконатися, що сторінки не були змінені транзакціями, які ще не пройшли очищення (vacuum). Якщо сторінка позначена як "брудна" (dirty), Postgres все одно доведеться звернутися до купи, що знизить продуктивність.

## 3. Типи сканування в MySQL (InnoDB)

Стовпець `type` у виводі `EXPLAIN` в MySQL описує метод отримання рядків. Типи доступу, впорядковані від найшвидшого до найповільнішого, включають:

### const / system
* Таблиця має не більше одного відповідного рядка (наприклад, запит до `PRIMARY KEY` або `UNIQUE` індексу з константним значенням). Працює миттєво.

### eq_ref
* Використовується при об'єднаннях (joins), коли MySQL зчитує по одному рядку з цієї таблиці для кожної комбінації рядків із попередньої таблиці (відбувається при роботі з первинними або унікальними ключами).

### ref
* Використовується при порівнянні рядків із неунікальним індексом. Може повернути кілька рядків.

### range
* Використовує індекс для вибірки діапазону рядків (наприклад, у запитах із використанням `>`, `<`, `BETWEEN` або `IN`).

### index (Повне сканування індексу)
* MySQL виконує повне сканування дерева індексу. Це еквівалентно скануванню `Index Only Scan` у PostgreSQL. Воно дозволяє уникнути сканування простору таблиці, але все одно зчитує всі записи індексу.

### ALL (Повне сканування таблиці)
* MySQL зчитує кожен рядок таблиці з диска. Це найповільніший тип доступу, якого слід уникати на великих таблицях.

---

## 4. Порівняльна матриця типів сканування

| Концепція сканування | Назва у PostgreSQL | Тип у MySQL (InnoDB) | Опис |
| :--- | :--- | :--- | :--- |
| **Повне сканування таблиці** | `Seq Scan` | `ALL` | Сканує всю таблицю; високе навантаження на I/O. |
| **Пошук за індексом** | `Index Scan` | `ref` або `range` | Обходить індекс, потім зчитує рядок із табличного простору. |
| **Пошук тільки за індексом** | `Index Only Scan` | `index` | Отримує дані виключно з листових вузлів індексу. |
| **Пакетний пошук за індексом** | `Bitmap Index/Heap Scan` | Н/Д | Групує TID за сторінками для оптимізації доступу до диска. |
| **Постійний пошук (Constant)** | `Index Scan` (1 рядок) | `const` | Миттєвий пошук за унікальним індексом. |

---

## 5. Підсумок та найкращі практики

1. **Завжди використовуйте ANALYZE для реальних даних**: звичайний `EXPLAIN` показує лише оцінки. Завжди запускайте `EXPLAIN ANALYZE` (у безпечних середовищах) для перевірки реальної кількості рядків та використання пам'яті.
2. **Слідкуйте за деградацією "Index Only Scan"**: якщо `Index Only Scan` у Postgres показує велику кількість звернень до купи (heap fetches), запустіть `VACUUM` для таблиці, щоб оновити карту видимості (Visibility Map).
3. **Уникайте типу `ALL` у MySQL**: якщо запит до великої таблиці показує `type: ALL` або `Extra: Using join buffer`, додайте індекс, який би покривав стовпці пошуку.
4. **Оновлюйте статистику таблиць**: якщо оптимізатор обирає неефективний тип сканування, статистика таблиці може бути застарілою. Виконайте `ANALYZE TABLE my_table;` у MySQL або `ANALYZE my_table;` у PostgreSQL.
