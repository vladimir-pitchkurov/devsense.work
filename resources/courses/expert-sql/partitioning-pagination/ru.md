# Секционирование и пагинация

Когда таблицы разрастаются до десятков и сотен миллионов строк, стандартные запросы и простые структуры пагинации начинают давать сбои. Обновление данных, резервное копирование и поиск по индексам в огромных массивах вызывают задержки дискового ввода-вывода. Для масштабирования базы данных применяют две основные стратегии: **Секционирование таблиц** (table partitioning — разделение огромной таблицы на физические части под капотом) и **Эффективную пагинацию** (получение страниц данных без сканирования миллионов лишних строк).

---

## 1. Секционирование таблиц: Декларативные правила и отсечение секций (Pruning)

Секционирование разделяет одну логическую таблицу на несколько физических дочерних таблиц (секций / партиций). Родительская таблица выступает в роли маршрутизатора для запросов.

### Типы секционирования
1. **Секционирование по диапазонам (Range Partitioning)**: Распределяет строки по секциям на основе диапазонов значений (например, разделение логов по месяцам).
2. **Секционирование по спискам (List Partitioning)**: Распределяет строки на основе точных значений ключа (например, по коду страны).
3. **Секционирование по хэшу (Hash Partitioning)**: Равномерно распределяет строки по фиксированному числу секций с помощью функции хэширования по модулю. Помогает сбалансировать нагрузку на запись.

### Декларативное секционирование в PostgreSQL
Начиная с версии 10, PostgreSQL поддерживает декларативное секционирование с использованием секции `PARTITION BY` при создании родительской таблицы.

```sql
-- PostgreSQL: Декларативное секционирование по диапазонам
CREATE TABLE app_logs (
    id BIGINT NOT NULL,
    log_date DATE NOT NULL,
    message TEXT
) PARTITION BY RANGE (log_date);

-- Создание отдельных секций
CREATE TABLE app_logs_y2026m01 PARTITION OF app_logs
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE app_logs_y2026m02 PARTITION OF app_logs
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

### Синтаксис секционирования в MySQL
В MySQL секционирование описывается непосредственно внутри определения таблицы, без создания отдельных дочерних таблиц.

```sql
-- MySQL: Секционирование InnoDB по диапазонам
CREATE TABLE app_logs (
    id BIGINT NOT NULL,
    log_date DATE NOT NULL,
    message TEXT,
    PRIMARY KEY (id, log_date)
) ENGINE=InnoDB
PARTITION BY RANGE COLUMNS(log_date) (
    PARTITION p2026m01 VALUES LESS THAN ('2026-02-01'),
    PARTITION p2026m02 VALUES LESS THAN ('2026-03-01')
);
```

### Отсечение секций (Partition Pruning)
Главное преимущество секционирования — **отсечение секций**. Оптимизатор анализирует условия в секции `WHERE` и исключает из плана выполнения те секции, которые заведомо не содержат искомых строк, экономя время на чтение файлов.

```sql
-- Активация отсечения секций
EXPLAIN SELECT * FROM app_logs WHERE log_date = '2026-02-15';
-- План PostgreSQL покажет сканирование только 'app_logs_y2026m02'
-- План MySQL укажет используемую партицию: 'p2026m02'
```

> [!WARNING]
> **Ограничение первичного ключа**
> И в MySQL, и в PostgreSQL любые уникальные ограничения или первичные ключи на секционированной таблице **ОБЯЗАНЫ** содержать все столбцы ключа секционирования. В MySQL нельзя объявить изолированный `PRIMARY KEY (id)`, если вы секционируете по `log_date`; его нужно определить как `PRIMARY KEY (id, log_date)`. Это позволяет СУБД проверять уникальность при вставке без сканирования всех секций подряд.

## 2. Пагинация: Смещение (OFFSET) vs. Пагинация по ключам (Keyset / Cursor)

Вывод списков данных по страницам — базовая задача веб-приложений. Однако стандартный подход может приводить к серьезным задержкам.

### Проблема пагинации через OFFSET
* **Запрос**: `SELECT * FROM orders ORDER BY created_at DESC LIMIT 10 OFFSET 500000;`
* **Что происходит под капотом**: База данных не может мгновенно прыгнуть к 500 000-й строке. Она должна прочитать по индексу все предыдущие 500 000 строк, отбросить их в памяти и вернуть только следующие 10. Это приводит к колоссальным затратам CPU и дискового I/O.

### Пагинация по ключам (Keyset / Cursor-Based Pagination)
* **Запрос**: Вместо смещений используются значения последней полученной записи для фильтрации следующей страницы.
  ```sql
  -- MySQL и PostgreSQL: Пагинация по ключам
  SELECT * FROM orders 
  WHERE created_at < '2026-06-17 10:00:00' 
  ORDER BY created_at DESC 
  LIMIT 10;
  ```
* **Производительность**: При наличии составного индекса на `(created_at, id)` СУБД выполняет точечный переход (index seek) сразу к началу страницы. Время выполнения запроса составляет $O(1)$ и не зависит от глубины просматриваемой страницы.

### Многоколоночная пагинация по ключам (сортировка по неуникальным полям)
Если поле сортировки (например, `created_at` или `price`) содержит дубликаты, к условию необходимо добавить уникальный идентификатор (обычно ID строки), чтобы избежать пропуска записей.
* **Сравнение кортежей (PostgreSQL)**:
  ```sql
  -- PostgreSQL нативно поддерживает сравнение кортежей значений
  SELECT * FROM orders
  WHERE (created_at, id) < ('2026-06-17 10:00:00', 9876)
  ORDER BY created_at DESC, id DESC
  LIMIT 10;
  ```
* **Логическое раскрытие условия (MySQL)**:
  *MySQL 8.0 поддерживает сравнение кортежей, но в старых версиях оптимизатор может обрабатывать его неэффективно. Надежнее расписать условие явно:*
  ```sql
  -- Безопасный синтаксис для MySQL
  SELECT * FROM orders
  WHERE created_at < '2026-06-17 10:00:00'
     OR (created_at = '2026-06-17 10:00:00' AND id < 9876)
  ORDER BY created_at DESC, id DESC
  LIMIT 10;
  ```

> [!TIP]
> **Пагинация нескольких категорий через LATERAL JOIN**
> Если вам нужно выбрать «топ N записей для каждой категории» (например, по 3 самых дорогих товара для каждого из 20 брендов), обычный `GROUP BY` не поможет. Используйте соединение `LATERAL` (поддерживается в PostgreSQL 10+ и MySQL 8.0.14+).
> ```sql
> SELECT c.name, p.title, p.price
> FROM categories c
> INNER JOIN LATERAL (
>     SELECT title, price 
>     FROM products 
>     WHERE category_id = c.id 
>     ORDER BY price DESC LIMIT 3
> ) p ON TRUE;
> ```
> *Этот запрос выполняет оптимизированный поиск по индексу для каждой категории, что в разы быстрее полного сканирования таблицы с использованием оконных функций.*

## 3. Сравнительная матрица функционала

| Возможность | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- |
| **Определение секций** | Отдельные декларативные таблицы | Описание внутри одной таблицы |
| **Маршрутизация строк** | На уровне родительской таблицы | Внутренний механизм InnoDB |
| **Ограничение на PK** | PK должен содержать ключ секционирования | PK должен содержать ключ секционирования |
| **Сравнение кортежей** | Отлично оптимизировано (например, `(a,b) > (x,y)`) | Поддерживается, но возможны проблемы |
| **Латеральные соединения**| Поддерживается (с версии 9.3) | Поддерживается (с версии 8.0.14) |

## 4. Резюме и лучшие практики

1. **Используйте секционирование по датам для архивации**: Диапазонное секционирование идеально для логов. Вместо долгого `DELETE` (генерирующего Undo-логи и раздувающего таблицы), устаревшие данные можно мгновенно удалить с помощью `DROP TABLE имя_секции`.
2. **Откажитесь от больших OFFSET**: Используйте пагинацию по ключам (keyset) для бесконечных лент и списков с глубоким листанием.
3. **Индексируйте ключи пагинации**: Всегда создавайте составные B-Tree индексы под критерии сортировки и фильтрации пагинации (например, индекс на `(created_at, id)`).
