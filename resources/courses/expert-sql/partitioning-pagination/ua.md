# Партиціонування та пагінація

У міру того, як таблиці розростаються до десятків або сотень мільйонів рядків, стандартні запити та прості структури пагінації починають давати збій. Виконання оновлень, резервного копіювання та пошуку за індексами на величезних наборах даних викликає високу затримку диска. Для масштабування бази даних використовують дві основні стратегії: **партиціонування таблиць (Table Partitioning)** (розподіл великої таблиці на менші фізичні частини під капотом) та **ефективна пагінація (Efficient Pagination)** (отримання сторінкових записів без сканування мільйонів рядків зсуву).

---

## 1. Партиціонування таблиць: декларативні правила та відсікання

Партиціонування таблиць ділить одну логічну таблицю на кілька фізичних дочірніх таблиць (партицій). Батьківська таблиця виступає в ролі маршрутизуючого інтерфейсу.

### Типи партиціонування
1. **Партиціонування за діапазоном (Range Partitioning)**: розподіляє рядки по партиціях на основі діапазону значень (наприклад, партиціонування таблиці логів по місяцях).
2. **Партиціонування за списком (List Partitioning)**: розподіляє рядки по партиціях на основі конкретних значень ключів (наприклад, партиціонування за кодом країни).
3. **Партиціонування за хешем (Hash Partitioning)**: розподіляє рядки по фіксованій кількості партицій за допомогою модульної хеш-функції. Ідеально підходить для рівномірного розподілу навантаження на запис.

### Декларативне партиціонування в PostgreSQL
Починаючи з версії 10, PostgreSQL підтримує декларативне партиціонування. Партиції оголошуються за допомогою пропозиції `PARTITION BY`.

```sql
-- PostgreSQL: Декларативне партиціонування за діапазоном
CREATE TABLE app_logs (
    id BIGINT NOT NULL,
    log_date DATE NOT NULL,
    message TEXT
) PARTITION BY RANGE (log_date);

-- Створення окремих партицій
CREATE TABLE app_logs_y2026m01 PARTITION OF app_logs
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE app_logs_y2026m02 PARTITION OF app_logs
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

### Синтаксис партиціонування у MySQL
MySQL реалізує партиціонування безпосередньо всередині визначення таблиці без необхідності створення окремих дочірніх таблиць.

```sql
-- MySQL: InnoDB партиціонування за діапазоном
CREATE TABLE app_logs (
    id BIGINT NOT NULL,
    log_date DATE NOT NULL,
    message TEXT,
    PRIMARY KEY (id, log_date)
) ENGINE=InnoDB
PARTITION BY RANGE COLUMNS(log_date) (
    PARTITION p2026m01 VALUES LESS THAN ('2026-02-01'),
    PARTITION p2026m02 VALUES LESS THAN ('2026-03-01')
);
```

### Відсікання партицій (Partition Pruning)
Основною перевагою партиціонування є **відсікання партицій (Partition Pruning)**. Оптимізатор запитів аналізує умови фільтрації у пропозиції `WHERE` та виключає з обробки партиції, які не можуть містити відповідні рядки, уникаючи повного сканування цих фізичних файлів.

```sql
-- Активація відсікання партицій
EXPLAIN SELECT * FROM app_logs WHERE log_date = '2026-02-15';
-- План PostgreSQL скануватиме лише 'app_logs_y2026m02'
-- План MySQL покаже у списку партицій лише 'p2026m02'
```

> [!WARNING]
> **Обмеження первинних ключів**
> Як у MySQL, так і в PostgreSQL будь-яке обмеження унікальності або первинний ключ на партиційованій таблиці **ОБОВ'ЯЗКОВО** мають містити всі стовпці ключа партиціонування. У MySQL ви не можете мати окремий `PRIMARY KEY (id)`, якщо ви партиціонуєте за `log_date`; він має бути визначений як `PRIMARY KEY (id, log_date)`. Це запобігає необхідності сканування всіх партицій для перевірки унікальності при кожній вставці даних.

## 2. Пагінація: Offset проти Keyset (Cursor)

Отримання списків даних сторінками є базовою вимогою додатків. Проте стандартний підхід SQL може призвести до серйозних проблем із продуктивністю.

### Недолік пагінації через OFFSET
* **Синтаксис**: `SELECT * FROM orders ORDER BY created_at DESC LIMIT 10 OFFSET 500000;`
* **Внутрішній процес**: рушій бази даних не може перестрибнути безпосередньо до 500 000-го рядка. Він повинен пройти по індексу, прочитати всі 500 000 попередніх рядків, відкинути їх і повернути лише наступні 10 рядків. Це викликає велике навантаження на процесор та дискове введення-виведення.

### Пагінація за ключем (Keyset / Cursor-Based Pagination)
* **Синтаксис**: замість зміщень (offsets) використовуйте значення останнього отриманого запису для фільтрації наступних запитів.
  ```sql
  -- MySQL & PostgreSQL: Пагінація за ключем
  SELECT * FROM orders 
  WHERE created_at < '2026-06-17 10:00:00' 
  ORDER BY created_at DESC 
  LIMIT 10;
  ```
* **Продуктивність**: за наявності складеного індексу на `(created_at, id)` запит виконує точковий пошук в індексі (index seek) безпосередньо з потрібного місця, працюючи за час $O(1)$ незалежно від глибини сторінки.

### Багатостовпцева пагінація за ключем (сортування за неунікальними полями)
If the sorting field (like `created_at` or `price`) can contain duplicate values, you must append a unique tie-breaker column (usually the primary key) to avoid skipping rows.
* **Порівняння кортежів (PostgreSQL)**:
  ```sql
  -- PostgreSQL підтримує порівняння значень рядків нативно
  SELECT * FROM orders
  WHERE (created_at, id) < ('2026-06-17 10:00:00', 9876)
  ORDER BY created_at DESC, id DESC
  LIMIT 10;
  ```
* **Явне логічне розгортання (MySQL)**:
  *MySQL 8.0 підтримує порівняння значень рядків, але старіші версії або неефективні оптимізатори можуть обробляти його повільно. Для безпеки розгортайте умову явно:*
  ```sql
  -- Безпечне розгортання пагінації за ключем у MySQL
  SELECT * FROM orders
  WHERE created_at < '2026-06-17 10:00:00'
     OR (created_at = '2026-06-17 10:00:00' AND id < 9876)
  ORDER BY created_at DESC, id DESC
  LIMIT 10;
  ```

> [!TIP]
> **Пагінація за кількома категоріями через LATERAL JOIN**
> Якщо вам потрібно отримати «топ-N елементів для кожної категорії» з пагінацією (наприклад, топ-3 найдорожчі товари для кожної з 20 категорій), стандартний `GROUP BY` не допоможе. Використовуйте об'єднання `LATERAL` (підтримується у PostgreSQL 10+ та MySQL 8.0.14+).
> ```sql
> SELECT c.name, p.title, p.price
> FROM categories c
> INNER JOIN LATERAL (
>     SELECT title, price 
>     FROM products 
>     WHERE category_id = c.id 
>     ORDER BY price DESC LIMIT 3
> ) p ON TRUE;
> ```
> *Цей запит виконує індексований підзапит для кожної категорії, що працює надзвичайно швидко порівняно з повним скануванням віконними функціями.*

## 3. Порівняльна матриця можливостей

| Особливість | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- |
| **Визначення партиціонування** | Декларативні дочірні таблиці | Визначається безпосередньо в батьківській таблиці |
| **Маршрутизація рядків** | Керується батьківською маршрутизацією | Обробляється внутрішньо в InnoDB |
| **Обмеження PK** | PK має містити ключ партиціонування | PK має містити ключ партиціонування |
| **Порівняння значень рядків** | Оптимізовано нативно (наприклад, `(a, b) > (x, y)`) | Підтримується, але можливі пастки оптимізатора |
| **LATERAL об'єднання** | Підтримується (PostgreSQL 9.3+) | Підтримується (MySQL 8.0.14+) |

## 4. Підсумок та найкращі практики

1. **Партиціонуйте за датою для архівування**: партиціонування за діапазоном є ідеальним для логів транзакцій. Коли дані застарівають, ви можете миттєво видалити партицію за допомогою `DROP TABLE partition_name` замість виконання повільного `DELETE`, який генерує гігабайти логів скасування (undo logs).
2. **Ніколи не використовуйте великі зсуви (Offsets)**: впроваджуйте пагінацію за ключем (keyset) для нескінченного скролу або сторінкових списків.
3. **Індексуйте ключі пагінації**: завжди переконуйтеся, що ваші фільтри пагінації за ключем відповідають складеному індексу B-Tree (наприклад, індексу на `(created_at, id)`).
