# Партициониране и странициране

Когато таблиците нараснат до десетки или стотици милиони редове, стандартните заявки и обикновените структури за странициране започват да се провалят. Извършването на актуализации, архивиране и търсене по индекси върху огромни масиви от данни води до висока дискова латентност. За да се мащабират, базите данни използват две основни стратегии: **Партициониране на таблици (Table Partitioning)** (разделяне на масивна таблица на по-малки физически части под капака) и **Ефективно странициране (Efficient Pagination)** (извличане на страницирани записи без сканиране на милиони редове за отместване).

---

## 1. Партициониране на таблици: Декларативни правила и съкращаване (Pruning)

Партиционирането на таблици разделя една логическа таблица на множество физически подчинени таблици (партиции). Родителската таблица действа като маршрутизиращ интерфейс.

### Типове партициониране
1. **Партициониране по диапазон (Range Partitioning)**: Разпределя редовете по партиции въз основа на диапазон от стойности (напр. партициониране на таблица с логове по месеци).
2. **Партициониране по списък (List Partitioning)**: Разпределя редовете по партиции въз основа на изрични стойности на ключове (напр. партициониране по код на държава).
3. **Партициониране по хеш (Hash Partitioning)**: Разпределя редовете в рамките на фиксиран брой партиции с помощта на хеш модулна функция. Идеално за изравняване на натоварването при запис.

### Декларативно партициониране в PostgreSQL
От версия 10 насам PostgreSQL поддържа декларативно партициониране. Партициите се декларират с помощта на клаузата `PARTITION BY`.

```sql
-- PostgreSQL: Declarative Range Partitioning
CREATE TABLE app_logs (
    id BIGINT NOT NULL,
    log_date DATE NOT NULL,
    message TEXT
) PARTITION BY RANGE (log_date);

-- Create individual partitions
CREATE TABLE app_logs_y2026m01 PARTITION OF app_logs
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE app_logs_y2026m02 PARTITION OF app_logs
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

### Синтаксис за партициониране в MySQL
MySQL внедрява партиционирането директно в дефиницията на таблицата, без да изисква отделни оператори за подчинени таблици.

```sql
-- MySQL: InnoDB Range Partitioning
CREATE TABLE app_logs (
    id BIGINT NOT NULL,
    log_date DATE NOT NULL,
    message TEXT,
    PRIMARY KEY (id, log_date)
) ENGINE=InnoDB
PARTITION BY RANGE COLUMNS(log_date) (
    PARTITION p2026m01 VALUES LESS THAN ('2026-02-01'),
    PARTITION p2026m02 VALUES LESS THAN ('2026-03-01')
);
```

### Съкращаване на партиции (Partition Pruning)
Основната полза от партиционирането е **Съкращаване на партиции (Partition Pruning)**. Оптимизаторът на заявки анализира филтъра в клаузата `WHERE` и изключва партициите, които не могат да съдържат съвпадащи редове, избягвайки пълно сканиране на тези физически файлове.

```sql
-- Triggering Partition Pruning
EXPLAIN SELECT * FROM app_logs WHERE log_date = '2026-02-15';
-- PostgreSQL plan will only scan 'app_logs_y2026m02'
-- MySQL plan will list partitions: 'p2026m02'
```

> [!WARNING]
> **Ограничения за първичния ключ**
> Както в MySQL, така и в PostgreSQL, всяко уникално ограничение (unique constraint) или първичен ключ в партиционирана таблица **ТРЯБВА** да включва всички колони от ключа на партиционирането. В MySQL не можете да имате самостоятелен `PRIMARY KEY (id)`, ако партиционирате по `log_date`; той трябва да бъде дефиниран като `PRIMARY KEY (id, log_date)`. Това предотвратява необходимостта базите данни да сканират всички партиции за налагане на уникалност при вмъквания на данни.

## 2. Странициране: Offset срещу Keyset (Cursor)

Извличането на списъци с данни на страници е основно изискване за приложенията. По подразбиране обаче подходът на SQL може да доведе до сериозни затруднения в производителността.

### Недостатъкът на OFFSET страницирането
* **Синтаксис**: `SELECT * FROM orders ORDER BY created_at DESC LIMIT 10 OFFSET 500000;`
* **Под капака**: Сървърът на базата данни не може да скочи директно на ред 500 000. Той трябва да сканира индекса, да прочете всички предходни 500 000 реда, да ги отхвърли и да върне само следващите 10 реда. Това причинява високо натоварване на процесора и интензивен дисков I/O.

### Keyset странициране (базирано на курсор)
* **Синтаксис**: Вместо отмествания (offsets), използвайте последните извлечени стойности за филтриране на следващите заявки.
  ```sql
  -- MySQL & PostgreSQL: Keyset Pagination
  SELECT * FROM orders 
  WHERE created_at < '2026-06-17 10:00:00' 
  ORDER BY created_at DESC 
  LIMIT 10;
  ```
* **Производителност**: При съставен индекс върху `(created_at, id)`, заявката извършва търсене в индекса (index seek) директно до началната точка, изпълнявайки се за време $O(1)$ независимо от номера на страницата.

### Многоколонно Keyset странициране (сортиране по неуникални полета)
Ако сортираното поле (като `created_at` или `price`) може да съдържа дублиращи се стойности, трябва да добавите уникална колона за решаване на равенствата (обикновено първичния ключ), за да избегнете пропускане на редове.
* **Синтаксис за сравнение на кортежи (PostgreSQL)**:
  ```sql
  -- PostgreSQL supports row value comparisons natively
  SELECT * FROM orders
  WHERE (created_at, id) < ('2026-06-17 10:00:00', 9876)
  ORDER BY created_at DESC, id DESC
  LIMIT 10;
  ```
* **Изрично логическо разширение (MySQL)**:
  *MySQL 8.0 поддържа сравнение на кортежи (row-value comparison), но по-старите версии или слабите оптимизатори го изпълняват неефективно. За сигурност го разширете изрично:*
  ```sql
  -- MySQL Safe Keyset Expansion
  SELECT * FROM orders
  WHERE created_at < '2026-06-17 10:00:00'
     OR (created_at = '2026-06-17 10:00:00' AND id < 9876)
  ORDER BY created_at DESC, id DESC
  LIMIT 10;
  ```

> [!TIP]
> **Многокатегорийно странициране с LATERAL JOIN**
> Ако трябва да страницирате и извлечете „най-добрите N артикула за категория“ (напр. топ 3 продукта за всяка от 20 категории), стандартният `GROUP BY` в SQL няма да работи. Използвайте `LATERAL` съединяване (поддържано в PostgreSQL 10+ и MySQL 8.0.14+).
> ```sql
> SELECT c.name, p.title, p.price
> FROM categories c
> INNER JOIN LATERAL (
>     SELECT title, price 
>     FROM products 
>     WHERE category_id = c.id 
>     ORDER BY price DESC LIMIT 3
> ) p ON TRUE;
> ```
> *Това изпълнява базирана на индекс подзаявка за всяка категория, което е изключително бързо в сравнение с пълното сканиране при прозоречни функции.*

## 3. Сравнителна матрица за функционалностите

| Функционалност | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- |
| **Дефиниция на партициониране** | Декларативни подчинени таблици | Дефинирано директно в родителската таблица |
| **Маршрутизация на редове** | Управлява се от родителската таблица | Управлява се вътрешно от InnoDB |
| **Ограничение за PK** | PK трябва да съдържа ключа за партициониране | PK трябва да съдържа ключа за партициониране |
| **Сравнение на кортежи** | Нативно оптимизирано (напр. `(a, b) > (x, y)`) | Поддържа се, но могат да възникнат капани в оптимизатора |
| **Lateral съединявания** | Поддържат се (PostgreSQL 9.3+) | Поддържат се (MySQL 8.0.14+) |

## 4. Резюме и добри практики

1. **Партиционирайте по дата за архивиране**: Партиционирането по диапазон (Range partitioning) е отлично за транзакционни логове. Когато данните остареят, можете да премахнете партицията с `DROP TABLE partition_name` (мигновено), вместо да стартирате масивно `DELETE` (бавно, генериращо undo раздуване).
2. **Никога не използвайте големи отмествания (Offsets)**: Внедрявайте keyset странициране за безкрайно скролиране (infinite scroll) или страницирани списъци.
3. **Индексирайте ключовете си за странициране**: Винаги се уверявайте, че вашите филтри за keyset странициране съвпадат със съставен B-Tree индекс (напр. индекс върху `(created_at, id)`).
