# Параллелизм, MVCC и раздувание таблиц (Bloat)

В высоконагруженных базах данных тысячи транзакций читают и пишут данные одновременно. Если бы каждое чтение блокировало строку, базы данных просто остановились бы. Чтобы решить эту проблему, современные реляционные СУБД используют **многоверсионность (Multi-Version Concurrency Control — MVCC)**. Главный принцип MVCC прост: *читатели не блокируют писателей, а писатели не блокируют читателей*. Тем не менее, MySQL и PostgreSQL реализуют этот принцип совершенно по-разному, что приводит к разным профилям производительности, требованиям к обслуживанию и стратегиям оптимизации.

---

## 1. Как MVCC работает под капотом

Когда транзакция обновляет строку, база данных не перезаписывает старые данные мгновенно. Вместо этого она сохраняет несколько версий этой строки, позволяя активным транзакциям видеть согласованный снимок (snapshot) данных в соответствии с их уровнем изоляции.

### PostgreSQL: Версионирование строк внутри таблицы (In-Heap)
PostgreSQL хранит все версии строк (называемые "кортежами" — tuples) непосредственно в файлах таблиц (heap).
* **xmin**: ID транзакции (TxID), которая вставила (insert) эту строку.
* **xmax**: ID транзакции, которая удалила (delete) или обновила (update) эту строку (изначально равен `0` или null).

При обновлении строки в Postgres физически происходит логическое удаление (`DELETE`) старой версии с последующей вставкой (`INSERT`) новой. СУБД устанавливает `xmax` текущей версии равным TxID текущей транзакции и вставляет новый кортеж с `xmin`, равным этому же TxID.

### MySQL (InnoDB): Журналы отката (Undo Logs) и сегменты отката
Движок InnoDB в MySQL использует иной подход. Он выполняет обновление непосредственно на месте (in-place) внутри страницы таблицы, но записывает старую версию строки в специальную структуру — **журнал отката (Undo Log)**.
* Заголовок каждой строки содержит поля `DB_TRX_ID` (ID транзакции, последней изменившей строку) и `DB_ROLL_PTR` (указатель отката, ссылающийся на запись в Undo Log с предыдущей версией строки).
* Если читателю требуется более старый снимок данных, InnoDB берет актуальную строку и идет назад по цепочке указателей отката, на лету восстанавливая состояние данных на нужный момент времени.

## 2. Раздувание таблиц (Bloat) в PostgreSQL, автоочистка (VACUUM) и HOT-обновления

Поскольку PostgreSQL хранит "мертвые кортежи" (устаревшие версии измененных или удаленных строк) прямо в страницах таблицы, размер файлов таблиц со временем неизбежно растет. Это явление называется **раздуванием таблиц (table bloat)**.

```
Обновление страницы Heap в PostgreSQL:
+-------------------------------------------------------------+
| [Кортеж v1 (xmin: 100, xmax: 101)] -> Мертвый кортеж (Bloat) |
| [Кортеж v2 (xmin: 101, xmax: 0)]   -> Живой кортеж          |
+-------------------------------------------------------------+
```

### Роль процесса VACUUM
Чтобы освободить место, занятое мертвыми кортежами, PostgreSQL запускает фоновый процесс очистки — **Autovacuum**.
* **Обычный VACUUM**: Сканирует страницы и помечает мертвые кортежи как доступные для повторного использования будущими операциями вставки. Он *не* возвращает дисковое пространство операционной системе (за исключением случаев, когда страницы в самом конце таблицы становятся абсолютно пустыми).
* **VACUUM FULL**: Полностью перестраивает таблицу, сжимая ее файлы и возвращая место ОС. **Внимание**: Эта операция блокирует таблицу монопольно (`ACCESS EXCLUSIVE`), закрывая доступ на чтение и запись для всех остальных запросов.

### Оптимизация Heap-Only Tuple (HOT)
Чтобы избежать обновления указателей в индексах при каждом изменении версии строки, PostgreSQL использует оптимизацию **HOT-обновлений**. Если обновление не затрагивает индексируемые столбцы и на текущей странице достаточно свободного места:
1. Postgres размещает новый кортеж на той же странице.
2. Он связывает старый кортеж с новым в цепочку.
3. Индексы продолжают указывать на старый кортеж; читатели прозрачно переходят по цепочке к новому.

> [!WARNING]
> **Настройка Autovacuum обязательна!**
> Стандартные настройки autovacuum в PostgreSQL слишком консервативны. На таблицах с высокой частотой записи это приводит к неконтролируемому росту bloat, замедляя все запросы, так как СУБД приходится сканировать миллионы мертвых строк. Всегда снижайте коэффициент `autovacuum_vacuum_scale_factor` (по умолчанию 0.20 или 20% измененных строк) до `0.05` или ниже для больших таблиц.

## 3. MySQL InnoDB: Очистка журналов отката (Undo Purge) и сжатие

В MySQL раздувание таблиц стоит не так остро, потому что старые версии строк переносятся в Undo Log, а не остаются в табличном пространстве. Однако у InnoDB есть свои узкие места, связанные с параллелизмом.

### Фоновые потоки очистки (Purge Threads)
Как только самая старая из активных транзакций перестает нуждаться в записях журнала отката, фоновый процесс **Purge Thread** удаляет устаревшие записи из Undo Log.
* Если транзакция остается открытой часами (например, из-за долгого аналитического отчета), InnoDB не может очистить журналы отката, созданные с момента старта этой транзакции.
* Это приводит к раздуванию **табличного пространства Undo** (Undo Tablespace). В старых версиях MySQL уменьшить файлы Undo без полного пересоздания базы данных было невозможно.

```sql
-- MySQL: Просмотр активных транзакций InnoDB и их длительности
SELECT 
    trx_id, trx_state, trx_started, 
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_sec
FROM information_schema.innodb_trx
ORDER BY trx_started ASC;
```

> [!TIP]
> **Автоматическое сжатие Undo**
> Начиная с MySQL 8.0, InnoDB по умолчанию поддерживает автоматическое сжатие табличных пространств Undo. Убедитесь, что параметры `innodb_undo_log_truncate = ON` и `innodb_max_undo_log_size` (обычно 1 ГБ) включены для своевременного возврата дискового пространства.

## 4. Сравнительная матрица реализации MVCC

| Характеристика | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- |
| **Где хранятся старые версии** | Внутри таблицы (Heap-файлы) | В журналах отката (Undo Logs) |
| **Механизм обновления** | Delete + Insert (создание кортежа) | Обновление на месте + запись старой версии в Undo |
| **Обновление индексов** | Требует обновления всех индексов (кроме HOT) | Индексы обновляются только при изменении их колонок |
| **Очистка диска** | Vacuum / Autovacuum (освобождает слоты страниц) | Потоки Purge (очищают страницы Undo-логов) |
| **Риск раздувания (Bloat)** | Высокий для таблиц и индексов | Высокий для журналов отката при долгих транзакциях |

---

## 5. Резюме и лучшие практики

1. **Держите транзакции короткими**: Долгие транзакции вредят обеим СУБД. В Postgres они мешают автоочистке удалять мертвые строки, а в MySQL — не дают потокам очистки удалять Undo-логи.
2. **Настраивайте Fillfactor в PostgreSQL**: Для таблиц с частыми обновлениями снижайте параметр `fillfactor` (например, до 80 или 90), чтобы оставлять резервное место на страницах для HOT-обновлений.
3. **Мониторьте Undo-пространство в MySQL**: Настройте алерты на долгие транзакции во избежание переполнения диска журналами отката.
