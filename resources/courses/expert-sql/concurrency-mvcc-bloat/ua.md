# Паралелізм, MVCC та роздування таблиць

У базах даних із високою пропускною здатністю тисячі транзакцій одночасно читають і записують дані. Якби кожне читання блокувало рядок, бази даних зупинилися б. Для вирішення цієї проблеми сучасні реляційні бази даних використовують **багатоверсійне керування паралельним доступом (Multi-Version Concurrency Control, MVCC)**. Основна філософія MVCC проста: *читачі не блокують письменників, а письменники не блокують читачів*. Проте MySQL та PostgreSQL реалізують цю філософію принципово різними способами, що призводить до абсолютно різних профілів продуктивності, вимог до обслуговування та стратегій оптимізації.

---

## 1. Як MVCC працює зсередини

Коли транзакція оновлює рядок, база даних не перезаписує старі дані негайно. Замість цього вона зберігає кілька версій цього рядка, дозволяючи активним транзакціям бачити узгоджений знімок (snapshot) даних на основі їхнього рівня ізоляції.

### PostgreSQL: Версіонування кортежів (In-Heap)
PostgreSQL зберігає всі версії рядків (звані "кортежами") безпосередньо в купі (heap) таблиці.
* **`xmin`**: ідентифікатор транзакції (TxID), яка вставила рядок.
* **`xmax`**: ідентифікатор транзакції, яка видалила або оновила рядок (початково `0` або null).

Коли ви оновлюєте рядок у Postgres, він виконує логічне видалення `DELETE`, після чого йде вставка `INSERT`. Він записує поточний TxID у поле `xmax` існуючого рядка та вставляє новий рядок із `xmin`, що дорівнює поточному TxID.

### MySQL (InnoDB): Логи скасування (Undo Logs) та сегменти відкату (Rollback Segments)
Рушій InnoDB СКБД MySQL використовує інший підхід. Він оновлює дані на місці (in-place) всередині табличного простору, але записує стару версію рядка в спеціальну структуру, яка називається **логом скасування (Undo Log)**.
* Заголовок кожного рядка містить поля `DB_TRX_ID` (ідентифікатор транзакції, яка останньою змінила рядок) та `DB_ROLL_PTR` (покажчик відкату, що вказує на запис у лозі скасування, який містить попередню версію).
* Коли читачеві потрібен старіший знімок даних, InnoDB починає з активного рядка і проходить ланцюжком скасування назад за допомогою покажчика відкату, щоб реконструювати дані "на льоту".

## 2. Роздування таблиць у PostgreSQL, VACUUM та HOT-оновлення

Оскільки PostgreSQL зберігає мертві кортежі (старі версії оновлених/видалених рядків) безпосередньо на сторінках таблиці, таблиці природно збільшуються в розмірі з часом. Це явище називається **роздуванням таблиці (table bloat)**.

```
Оновлення сторінки купи PostgreSQL:
+-------------------------------------------------------------+
| [Кортеж v1 (xmin: 100, xmax: 101)] -> Мертвий кортеж (Роздування) |
| [Кортеж v2 (xmin: 101, xmax: 0)]   -> Живий кортеж          |
+-------------------------------------------------------------+
```

### Роль VACUUM
Для очищення простору, зайнятого мертвими кортежами, PostgreSQL запускає фоновий процес під назвою **Autovacuum**.
* **Стандартний VACUUM**: сканує сторінки, маркує мертві кортежі як доступні для повторного використання при майбутніх вставках. Він *не* повертає простір операційній системі (якщо тільки сторінки в самому кінці таблиці не є повністю порожніми).
* **VACUUM FULL**: повністю перебудовує таблицю, стискаючи її та повертаючи простір ОС. **Увага**: цей процес накладає на таблицю ексклюзивне блокування (`ACCESS EXCLUSIVE`), блокуючи всі операції читання та запису.

### Оптимізація Heap-Only Tuple (HOT-оновлення)
Щоб уникнути оновлення покажчиків індексів щоразу, коли змінюється версія рядка, PostgreSQL використовує **HOT-оновлення**. Якщо оновлення не змінює індексовані стовпці і на сторінці достатньо вільного місця:
1. Postgres розміщує новий кортеж на тій самій сторінці.
2. Він пов'язує старий кортеж із новим у ланцюжок.
3. Індекси продовжують посилатися на старий кортеж; читачі переходять за ланцюжком.

> [!WARNING]
> **Налаштування Autovacuum є обов'язковим!**
> Стандартні налаштування autovacuum в PostgreSQL є дуже консервативними. На таблицях з великою кількістю операцій запису це призводить до неконтрольованого роздування, що погіршує продуктивність запитів, оскільки базі даних доводиться сканувати мертві кортежі. Завжди зменшуйте параметр `autovacuum_vacuum_scale_factor` (за замовчуванням 0.20 або 20% змінених рядків) до `0.05` або нижче для великих таблиць.

## 3. MySQL InnoDB: Очищення логів скасування та урізання

У MySQL роздування таблиць є менш критичною проблемою, оскільки старі версії рядків зберігаються в логах скасування, а не в просторі таблиці. Однак у InnoDB є свої вузькі місця, пов'язані з паралелізмом.

### Потоки очищення InnoDB (Purge Threads)
Коли найстаріша активна транзакція більше не потребує запису в лозі скасування, фоновий процес, званий **потоком очищення (Purge Thread)**, очищає сторінки логу скасування.
* Якщо транзакція залишається відкритою годинами (наприклад, тривалий звітний запит), InnoDB не може очистити жодних логів скасування, створених з моменту запуску цієї транзакції.
* Це призводить до розростання **табличного простору скасування (Undo Tablespace)**. У старіших версіях MySQL табличні простори скасування не могли стискатися, що вимагало повної перебудови бази даних для звільнення дискового простору.

```sql
-- MySQL: Перевірка логу скасування InnoDB та станів транзакцій
SELECT 
    trx_id, trx_state, trx_started, 
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_sec
FROM information_schema.innodb_trx
ORDER BY trx_started ASC;
```

> [!TIP]
> **Автоматичне урізання логів скасування**
> У MySQL 8.0 рушій InnoDB автоматично урізає табличні простори скасування за замовчуванням. Переконайтеся, що параметри `innodb_undo_log_truncate = ON` та `innodb_max_undo_log_size` (зазвичай 1 ГБ) налаштовані для автоматичного звільнення місця на диску табличного простору скасування.

## 4. Порівняльна матриця MVCC

| Особливість | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- |
| **Зберігання старих версій** | In-Heap (безпосередньо у файлах таблиці) | Логи скасування (окремі сегменти відкату) |
| **Механізм оновлення** | Видалення + Вставка (створює новий кортеж) | Оновлення на місці + запис старої версії в Undo |
| **Оновлення індексів** | Вимагає оновлення всіх індексів (якщо не HOT) | Оновлює індекс лише якщо змінено індексований стовпець |
| **Очищення дискового простору** | Vacuum / Autovacuum (звільняє слоти сторінок) | Потоки очищення (очищають сторінки логу скасування) |
| **Ризик роздування** | Високе роздування таблиць та індексів | Високе роздування логів скасування при тривалих транзакціях |

---

## 5. Підсумок та найкращі практики

1. **Тримайте транзакції короткими**: обидва рушії страждають, якщо транзакції залишаються відкритими занадто довго. У Postgres це заважає autovacuum очищати мертві кортежі; у MySQL це заважає потокам очищення звільняти логи скасування.
2. **Налаштовуйте Fillfactor у PostgreSQL**: для таблиць із великим обсягом оновлень зменшуйте параметр `fillfactor` таблиці (наприклад, до 80 або 90), щоб залишати вільне місце на кожній сторінці для HOT-оновлень.
3. **Моніторте простір скасування у MySQL**: налаштуйте сповіщення про тривалі активні транзакції для запобігання вибухоподібному розростанню простору скасування.
