# Індекси: глибоке занурення в B-Tree, GIN, BRIN та кластеризовані індекси

Індекси є основним інструментом підвищення продуктивності запитів. Проте бездумне створення індексів може знизити продуктивність запису та спожити величезну кількість дискового простору. Реляційні бази даних підтримують кілька типів індексів, кожен із яких розроблений для конкретного розподілу даних, патернів запитів та вимог до зберігання. Розуміння внутрішнього устрою B-Tree, кластеризації первинних ключів у MySQL та передових типів індексів у PostgreSQL є важливим для професійного налаштування баз даних.

---

## 1. Внутрішній устрій B-Tree та особливості кластеризації

**B-Tree** (збалансоване дерево) — це тип індексу за замовчуванням майже в усіх реляційних базах даних. Він зберігає дані відсортованими та дозволяє виконувати пошук, послідовний доступ, вставку та видалення за логарифмічний час ($O(\log n)$).

### MySQL InnoDB: Кластеризовані проти вторинних індексів
У рушії InnoDB СКБД MySQL усі таблиці фізично організовані навколо **кластеризованого індексу (Clustered Index)**.
* **Кластеризований індекс**: листові вузли індексу містять безпосередньо самі дані рядків. За замовчуванням це `PRIMARY KEY` таблиці. Якщо первинний ключ не визначено, InnoDB обирає перший індекс `UNIQUE`, у якому всі стовпці є non-null. Якщо таких немає, InnoDB генерує прихований 6-байтний ідентифікатор рядка (row ID).
* **Вторинний індекс (Secondary Index)**: листові вузли будь-какого вторинного індексу *не* містять покажчиків на дані. За замість цього вони зберігають **значення первинного ключа (Primary Key value)** рядка.
* **Пошук за закладкою (Bookmark Lookup)**: коли ви робите запит за допомогою вторинного індексу, MySQL спочатку шукає у вторинному індексі значення первинного ключа, а потім виконує другий пошук у кластеризованому індексі для отримання самого рядка.

```
Пошук за індексом у MySQL InnoDB:
[Пошук у вторинному індексі] ---> Повертає значення PK (наприклад, ID: 42)
                                      |
                                      v
[Пошук у кластеризованому індексі] -> Повертає дані рядка (ім'я, email тощо)
```

### PostgreSQL: Індексація на основі купи (Heap-Based Indexing)
На відміну від MySQL, PostgreSQL не використовує кластеризовані таблиці за замовчуванням. Таблиці організовані у вигляді "купи" (heap) сторінок.
* Усі індекси (включаючи індекс первинного ключа) є **вторинними індексами**.
* Листові вузли індексу у PostgreSQL вказують безпосередньо на фізичну адресу рядка (TID — Tuple ID, що складається з номера сторінки та зміщення) в купі таблиці.
* **Відсутність пошуку за закладкою**: Postgres переходить безпосередньо від листового вузла індексу до сторінки купи. Проте оновлення рядка в Postgres змінює його фізичну адресу, що вимагає оновлення всіх індексів (якщо тільки не відбувається HOT-оновлення).

## 2. Розширені типи індексів у PostgreSQL

PostgreSQL пропонує спеціалізовані типи індексів, які не мають нативних аналогів у MySQL.

### BRIN (Block Range Index — індекс діапазону блоків)
* **Як працює**: замість того, щоб індексувати кожен окремий рядок, індекс BRIN ділить таблицю на фізичні діапазони блоків (за замовчуванням 128 сторінок або 1 МБ даних) і зберігає лише **мінімальне** та **максимальне** значення для кожного діапазону.
* **Коли використовувати**: надзвичайно великі таблиці (сотні гігабайт), де дані природно впорядковані на диску (наприклад, автоінкрементні ID, мітки часу `created_at`).
* **Перевага**: неймовірно малий розмір. Індекс B-Tree розміром 10 ГБ часто можна замінити індексом BRIN розміром всього 10 МБ.

```sql
-- PostgreSQL: Створення індексу BRIN
CREATE INDEX idx_orders_date_brin ON orders USING brin (created_at);
```

### GIN (Generalized Inverted Index — узагальнений зворотний індекс)
* **Як працює**: зіставляє значення (такі як елементи масивів, слова в тексті або ключі JSON) з рядками, в яких вони з'являються.
* **Коли використовувати**: індексування масивів, документів JSONB або стовпців повнотекстового пошуку.

```sql
-- PostgreSQL: Індекс GIN для масивів
CREATE INDEX idx_user_tags ON users USING gin (tags);
```

### GiST (Generalized Search Tree — узагальнене дерево пошуку)
* **Як працює**: шаблон для побудови користувацьких структур B-Tree. Використовується для індексування геометричних координат, діапазонних типів та мережевих адрес.

## 3. Покриваючі, часткові та функціональні індекси

### Покриваючі індекси (Оптимізація сканування тільки індексу)
Покриваючий індекс містить усі стовпці, які вимагаються запитом. Ви можете додати додаткові стовпці корисного навантаження в листовий вузол індексу за допомогою пропозиції `INCLUDE`.
* **Синтаксис у PostgreSQL та MySQL**:
  ```sql
  -- PostgreSQL (з використанням INCLUDE)
  CREATE INDEX idx_users_email_include ON users (email) INCLUDE (username, status);

  -- MySQL (з використанням складеного індексу — порядок стовпців має значення)
  CREATE INDEX idx_users_email_cover ON users (email, username, status);
  ```

### Часткові індекси (Partial Indexes)
Індексують лише підмножину рядків, які відповідають певній умові фільтрації. Це зменшує розмір індексу та накладні витрати на запис.
* **Лише для PostgreSQL**:
  ```sql
  -- Індексація тільки активних акаунтів
  CREATE INDEX idx_users_active_email ON users (email) WHERE status = 'active';
  ```
* *MySQL не підтримує часткові індекси нативно. Для симуляції такої поведінки доводиться створювати функціональні індекси з використанням `CASE WHEN`.*

### Функціональні індекси (індекси за виразами)
Індексують результат функції або виразу, а не вихідні значення стовпця.
* **Синтаксис у MySQL та PostgreSQL**:
  ```sql
  -- PostgreSQL
  CREATE INDEX idx_users_lower_email ON users (LOWER(email));

  -- MySQL 8.0+
  CREATE INDEX idx_users_lower_email ON users ((LOWER(email)));
  ```

> [!WARNING]
> **Синтаксичні пастки функціональних індексів**
> У MySQL 8.0 індекси за виразами ОБОВ'ЯЗКОВО мають бути обгорнуті в подвійні дужки: `((вираз))`. Пропуск зовнішніх дужок призведе до синтаксичної помилки.

> [!TIP]
> **Об'єднання індексів (Index Merge)**
> Коли фільтр запиту містить умови `AND` або `OR` для кількох стовпців, бази даних можуть виконувати **Index Merge**. Вони сканують кілька одностовпцевих індексів та перетинають або об'єднують отримані бітові карти. Проте один складений (багатостовпцевий) індекс майже завжди працює швидше, ніж об'єднання окремих індексів.

## 4. Порівняльна матриця можливостей індексування

| Особливість | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- |
| **Структура кластеризованої таблиці** | Ні (Таблиці побудовані на основі купи) | Так (Таблиця кластеризована за PK B-Tree) |
| **Пошук за первинним ключем** | Індекс -> Сторінка купи | Безпосередньо в листі кластеризованого B-Tree |
| **Часткові індекси** | Так (пропозиція `WHERE`) | Ні (Обхідний шлях через функціональний індекс) |
| **Пропозиція покриваючого індексу** | Так (`INCLUDE`) | Ні (Має бути визначений як складений ключ) |
| **Індекси діапазонів блоків (BRIN)** | Так | Ні |
| **Зворотні індекси (GIN)** | Так | Ні |

---

## 5. Підсумок та найкращі практики

1. **Уникайте накладних витрат на автоінкрементні PK у MySQL**: оскільки InnoDB кластеризує таблиці за первинним ключем, вставка випадкових UUID як PK викликає серйозне розщеплення сторінок та фрагментацію. Використовуйте послідовні ID або впорядковані UUID.
2. **Використовуйте BRIN для великих часових рядів**: якщо у вас є таблиця логів на багато гігабайт, відсортована за міткою часу, використовуйте індекс BRIN. Це заощадить гігабайти пам'яті порівняно зі стандартним B-Tree.
3. **Використовуйте часткові індекси для розріджених стовпців**: якщо ви часто шукаєте в таблиці рідкісні статуси (наприклад, `WHERE status = 'retry'`), створіть частковий індекс для цієї умови, щоб тримати індекс крихітним.
