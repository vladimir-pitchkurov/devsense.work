# Индекси: Дълбоко гмуркане в B-Tree, GIN, BRIN и клъстерирани индекси

Индексите са основният инструмент за ускоряване на производителността на заявките. Сляпото прилагане на индекси обаче може да влоши производителността на запис и да консумира огромни количества дисково пространство. Релационните бази данни поддържат множество типове индекси, всеки от които е проектиран за специфични разпределения на данни, модели на заявки и размер на съхранение. Разбирането на вътрешните механизми на B-Tree, клъстерирането на първични ключове (primary key clustering) в MySQL и напредналите типове индекси в PostgreSQL е от съществено значение за професионалната настройка на бази данни.

---

## 1. Вътрешни механизми на B-Tree и поведение на клъстериране (Clustering)

**B-Tree** (Балансирано дърво) е типът индекс по подразбиране в почти всички релационни бази данни. Той поддържа данните сортирани и позволява търсене, последователен достъп, вмъкване и изтриване в логаритмично време ($O(\log n)$).

### MySQL InnoDB: Клъстерирани срещу вторични индекси (Clustered vs. Secondary Indexes)
В двигателя InnoDB на MySQL всички таблици са физически организирани около **Клъстериран индекс (Clustered Index)**.
* **Клъстериран индекс**: Листните възли (leaf nodes) на индекса съдържат действителните данни на редовете. По подразбиране това е първичният ключ (`PRIMARY KEY`) на таблицата. Ако не е дефиниран първичен ключ, InnoDB избира първия `UNIQUE` индекс, съдържащ само колони без null стойности. Ако такъв не съществува, InnoDB генерира скрит 6-байтов идентификатор на ред (row ID).
* **Вторичен индекс (Secondary Index)**: Листните възли на всеки вторичен индекс *не* съдържат указатели към данни. Вместо това те съхраняват **стойността на първичния ключ** на реда.
* **Bookmark Lookup (Търсене по отметка)**: Когато изпращате заявка, използваща вторичен индекс, MySQL първо претърсва вторичния индекс, за да намери първичния ключ, а след това извършва второ търсене в клъстерирания индекс, за да извлече реда.

```
MySQL InnoDB търсене по индекс:
[Търсене във вторичен индекс] ---> Връща стойността на PK (напр. ID: 42)
                                 |
                                 v
[Търсене в клъстериран индекс] ---> Връща данните на реда (име, имейл и др.)
```

### PostgreSQL: Индексиране, базирано на хийп (Heap-Based Indexing)
За разлика от MySQL, PostgreSQL не използва клъстерирани таблици по подразбиране. Таблиците са организирани като хийп (heap) от страници.
* Всички индекси (включително индексът на първичния ключ) са **Вторични индекси**.
* Листните възли на индекс в PostgreSQL сочат директно към физическия адрес (TID - Tuple ID, състоящ се от номер на страница и отместване) на реда в хийпа на таблицата.
* **Без Bookmark Lookup**: Postgres преминава директно от листния възел на индекса към страницата в хийпа. Актуализирането на ред в Postgres обаче променя физическия му адрес, което налага актуализирането на всички индекси (освен ако не се случи HOT актуализация).

## 2. Разширени типове индекси в PostgreSQL

PostgreSQL предлага специализирани типове индекси, които нямат нативен еквивалент в MySQL.

### BRIN (Block Range Index)
* **Как работи**: Вместо да индексира всеки отделен ред, BRIN индексът разделя таблицата на физически диапазони от блокове (по подразбиране 128 страници или 1MB данни) и съхранява само **минималната** и **максималната** стойност за всеки диапазон.
* **Кога да се използва**: Изключително големи таблици (стотици гигабайти), където данните са естествено сортирани на диска (напр. автоинкрементиращи се IDs, времеви печати `created_at`).
* **Полза**: Изключително малък размер на диска. B-Tree индекс с размер 10GB често може да бъде заменен с 10MB BRIN индекс.

```sql
-- PostgreSQL: Creating a BRIN index
CREATE INDEX idx_orders_date_brin ON orders USING brin (created_at);
```

### GIN (Generalized Inverted Index)
* **Как работи**: Картира стойности (като елементи от масив, думи в текст или JSON ключове) към редовете, в които се появяват те.
* **Кога да се използва**: Индексиране на масиви, JSONB документи или колони за търсене в пълен текст.

```sql
-- PostgreSQL: GIN index for arrays
CREATE INDEX idx_user_tags ON users USING gin (tags);
```

### GiST (Generalized Search Tree)
* **Как работи**: Шаблон за изграждане на потребителски B-Tree структури. Използва се за индексиране на геометрични координати, диапазонни типове (range types) и мрежови адреси.

## 3. Покриващи, частични и функционални индекси

### Покриващи индекси (Оптимизация за Index-Only Scan)
Покриващ индекс (covering index) съдържа всички колони, изисквани от дадена заявка. Можете да добавите допълнителни колони с полезен товар (payload) към листния възел на индекса, като използвате клаузата `INCLUDE`.
* **Синтаксис в PostgreSQL и MySQL**:
  ```sql
  -- PostgreSQL (using INCLUDE)
  CREATE INDEX idx_users_email_include ON users (email) INCLUDE (username, status);

  -- MySQL (using Composite Index - columns must be ordered)
  CREATE INDEX idx_users_email_cover ON users (email, username, status);
  ```

### Частични индекси (Partial Indexes)
Индексират само подмножество от редове, които отговарят на конкретно филтриращо условие. Това намалява размера на индекса и допълнителните разходи при запис.
* **Само за PostgreSQL**:
  ```sql
  -- Index only active accounts
  CREATE INDEX idx_users_active_email ON users (email) WHERE status = 'active';
  ```
* *MySQL не поддържа нативно частични индекси. Трябва да използвате функционални индекси с `CASE WHEN`, за да имитирате това поведение.*

### Функционални индекси (Functional Indexes / Expression Indexes)
Индексират резултата от функция или израз, вместо необработените стойности на колоната.
* **Синтаксис в MySQL и PostgreSQL**:
  ```sql
  -- PostgreSQL
  CREATE INDEX idx_users_lower_email ON users (LOWER(email));

  -- MySQL 8.0+
  CREATE INDEX idx_users_lower_email ON users ((LOWER(email)));
  ```

> [!WARNING]
> **Синтактични капани при функционалните индекси**
> В MySQL 8.0 индексите на базата на изрази ЗАДЪЛЖИТЕЛНО трябва да бъдат оградени в двойни скоби: `((израз))`. Пропускането на външните скоби води до синтактична грешка.

> [!TIP]
> **Сливане на индекси (Index Merging)**
> Когато филтърът на заявката съдържа `AND` или `OR` върху множество колони, базите данни могат да извършат **Index Merge**. Системата сканира няколко едноколонни индекса и пресича или обединява получените битмапи. Въпреки това, единичен съставен (composite) индекс почти винаги е по-бърз от сливането на отделни индекси.

## 4. Сравнителна матрица за функционалностите за индексиране

| Функционалност | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- |
| **Структура на клъстерирана таблица** | Не (Таблиците са базирани на хийп) | Да (Клъстерирана по PK B-Tree) |
| **Търсене по първичен ключ** | Индекс -> Страница от хийпа | Директно в листа на клъстерираното B-Tree |
| **Частични индекси** | Да (клауза `WHERE`) | Не (заобиколно с функционален индекс) |
| **Клауза за покриващ индекс** | Да (`INCLUDE`) | Не (трябва да се дефинира като съставен ключ) |
| **Индекси с блоков диапазон (BRIN)**| Да | Не |
| **Инвертирани индекси (GIN)** | Да | Не |

## 5. Резюме и добри практики

1. **Избягвайте разходите при автоинкрементиращи PK в MySQL**: Тъй като InnoDB клъстерира таблиците по първичен ключ, вмъкването на произволни UUID като PK причинява сериозно разделяне на страници (page splitting) и фрагментация. Използвайте последователни IDs или подредени UUIDs.
2. **Възползвайте се от BRIN за големи хронологични данни**: Ако имате таблица с логове с размер десетки гигабайти, сортирана по времеви печат, използвайте BRIN индекс. Той спестява гигабайти памет в сравнение със стандартен B-Tree.
3. **Използвайте частични индекси за редки колони**: Ако често правите заявки към таблица за рядък статус (напр. `WHERE status = 'retry'`), създайте частичен индекс за това условие, за да поддържате размера на индекса минимален.
