# Индексы: B-Tree, GIN, BRIN и кластеризованные структуры

Индексы — основной инструмент ускорения запросов. Однако бездумное их создание замедляет операции записи и расходует дисковое пространство. СУБД поддерживают разные типы индексов, каждый из которых спроектирован под определенное распределение данных, типы запросов и ограничения памяти. Понимание внутреннего устройства B-Tree, кластеризации в MySQL и продвинутых типов индексов в PostgreSQL необходимо для квалифицированной оптимизации баз данных.

---

## 1. Внутреннее устройство B-Tree и поведение при кластеризации

**B-Tree** (сбалансированное дерево) — тип индекса по умолчанию почти во всех реляционных СУБД. Он хранит данные в отсортированном виде и обеспечивает поиск, последовательный доступ, вставку и удаление за логарифмическое время ($O(\log n)$).

### MySQL InnoDB: Кластеризованные и вторичные индексы
В движке InnoDB (MySQL) все таблицы физически организованы вокруг **кластеризованного индекса (Clustered Index)**.
* **Кластеризованный индекс**: Листья этого дерева содержат непосредственные данные строк таблицы. По умолчанию кластеризованным индексом становится первичный ключ (`PRIMARY KEY`). Если первичного ключа нет, InnoDB берет первый уникальный индекс `UNIQUE`, в котором нет колонок с NULL. Если нет и такого, InnoDB генерирует скрытый 6-байтовый идентификатор строки (row ID).
* **Вторичный индекс (Secondary Index)**: Листья любого вторичного индекса *не* содержат физических адресов строк. Вместо этого они хранят **значение первичного ключа** соответствующей строки.
* **Поиск по закладке (Bookmark Lookup)**: При поиске через вторичный индекс MySQL сначала находит значение первичного ключа в этом индексе, а затем выполняет второй поиск по кластеризованному индексу, чтобы получить саму строку с данными.

```
Поиск строки в MySQL InnoDB:
[Поиск во вторичном индексе] ---> Возвращает PK (например, ID: 42)
                                       |
                                       v
[Поиск в кластеризованном индексе] -> Возвращает данные строки (имя, email и т.д.)
```

### PostgreSQL: Таблицы-кучи (Heap-based)
В отличие от MySQL, PostgreSQL не кластеризует таблицы по умолчанию. Данные хранятся в неупорядоченном файле-куче (heap).
* Все индексы (включая индекс первичного ключа) являются **вторичными**.
* Листья индексов в Postgres указывают напрямую на физический адрес строки (TID — Tuple ID, состоящий из номера страницы и смещения кортежа внутри нее).
* **Отсутствие Bookmark Lookup**: Postgres переходит напрямую от индекса к нужной странице таблицы. Однако изменение физического адреса строки при обновлении (UPDATE) заставляет Postgres обновлять указатели во всех индексах таблицы (если не сработало HOT-обновление).

## 2. Специализированные типы индексов в PostgreSQL

PostgreSQL предлагает продвинутые типы индексов, не имеющие нативных аналогов в MySQL.

### BRIN (Block Range Index — индекс по диапазонам блоков)
* **Принцип работы**: Вместо индексации каждой строки BRIN делит таблицу на физические диапазоны блоков (по умолчанию 128 страниц или 1 МБ данных) и сохраняет только **минимальное** и **максимальное** значение для каждого диапазона.
* **Когда использовать**: Огромные таблицы (сотни гигабайт), данные в которых упорядочены по времени или возрастанию (например, инкрементные ID, даты `created_at`).
* **Плюс**: Крайне малый размер. Индекс B-Tree размером в 10 ГБ часто удается заменить индексом BRIN размером всего в 10 МБ.

```sql
-- PostgreSQL: Создание индекса BRIN
CREATE INDEX idx_orders_date_brin ON orders USING brin (created_at);
```

### GIN (Generalized Inverted Index — обобщенный инвертированный индекс)
* **Принцип работы**: Сопоставляет элементы (элементы массивов, слова текста или ключи JSON) со списками строк, в которых они встречаются.
* **Когда использовать**: Индексирование массивов, документов JSONB или столбцов полнотекстового поиска.

```sql
-- PostgreSQL: GIN-индекс для массивов
CREATE INDEX idx_user_tags ON users USING gin (tags);
```

### GiST (Generalized Search Tree — обобщенное дерево поиска)
* **Принцип работы**: Шаблон для построения произвольных древовидных структур. Применяется для индексирования геометрических координат, диапазонов и сетевых адресов.

## 3. Покрывающие, частичные и функциональные индексы

### Покрывающие индексы (Covering Indexes)
Покрывающий индекс содержит все колонки, запрашиваемые в SELECT, что позволяет избежать обращения к самой таблице. Дополнительные неключевые колонки добавляются в индекс с помощью секции `INCLUDE`.
* **Синтаксис в PostgreSQL и MySQL**:
  ```sql
  -- PostgreSQL (с использованием INCLUDE)
  CREATE INDEX idx_users_email_include ON users (email) INCLUDE (username, status);

  -- MySQL (через составной индекс — важен порядок колонок)
  CREATE INDEX idx_users_email_cover ON users (email, username, status);
  ```

### Частичные индексы (Partial Indexes)
Индексируют только подмножество строк, соответствующих условию фильтрации. Это уменьшает размер индекса и снижает накладные расходы при записи.
* **Только в PostgreSQL**:
  ```sql
  -- Индексирование только активных аккаунтов
  CREATE INDEX idx_users_active_email ON users (email) WHERE status = 'active';
  ```
* *В MySQL нет нативных частичных индексов. Их приходится симулировать через функциональные индексы с условным оператором CASE WHEN.*

### Функциональные индексы (Functional Indexes)
Индексируют результат вычисления функции или выражения над значениями колонок.
* **Синтаксис в MySQL и PostgreSQL**:
  ```sql
  -- PostgreSQL
  CREATE INDEX idx_users_lower_email ON users (LOWER(email));

  -- MySQL 8.0+
  CREATE INDEX idx_users_lower_email ON users ((LOWER(email)));
  ```

> [!WARNING]
> **Синтаксическая ловушка MySQL**
> В MySQL 8.0 выражение функционального индекса ОБЯЗАТЕЛЬНО должно быть заключено в двойные круглые скобки: `((выражение))`. Пропуск внешних скобок приведет к синтаксической ошибке.

> [!TIP]
> **Объединение индексов (Index Merge)**
> Если в фильтре запроса используются условия `AND` или `OR` для разных колонок, СУБД могут сканировать несколько одиночных индексов одновременно и пересекать либо объединять полученные битовые карты. Тем не менее, один составной индекс почти всегда работает быстрее, чем объединение отдельных индексов.

## 4. Сравнительная матрица функционала индексов

| Возможность | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- |
| **Кластеризация таблицы** | Нет (таблицы хранятся в виде Heap) | Да (таблица физически упорядочена по PK) |
| **Поиск по первичному ключу** | Индекс -> Страница Heap | Напрямую в листьях кластеризованного B-Tree |
| **Частичные индексы** | Да (через секцию `WHERE`) | Нет (симуляция через функции) |
| **Покрывающие индексы (INCLUDE)**| Да | Нет (только через составные ключи) |
| **Индексы по диапазонам (BRIN)** | Да | Нет |
| **Инвертированные индексы (GIN)**  | Да | Нет |

---

## 5. Резюме и лучшие практики

1. **Избегайте случайных UUID в первичном ключе MySQL**: Так как InnoDB кластеризует таблицы по PK, вставка случайных UUID вызывает частое расщепление страниц (page split) и фрагментацию диска. Используйте автоинкрементные ID или последовательные UUID.
2. **Используйте BRIN для больших упорядоченных данных**: При наличии лог-таблиц объемом в сотни гигабайт, отсортированных по времени, BRIN сэкономит вам гигабайты оперативной памяти по сравнению с обычным B-Tree.
3. **Применяйте частичные индексы для редких статусов**: Если вы часто ищете строки по какому-то редкому статусу (например, `WHERE status = 'error_retry'`), создайте частичный индекс с этим условием, чтобы держать его размер минимальным.
