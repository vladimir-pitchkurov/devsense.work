# Диалекти, JSON и търсене в JSON

Съвременните приложения често обработват полуструктурирани данни, като отговори от API, динамични потребителски настройки или полиморфни атрибути. Традиционно това изискваше използването на EAV (Entity-Attribute-Value) антимодели или преминаване към NoSQL бази данни. Днес релационните бази данни поддържат нативно JSON с двоични формати за съхранение, индексиране и богати възможности за заявки. PostgreSQL и MySQL обаче подхождат различно към представянето на JSON, синтаксиса на пътищата (path syntax) и механизмите за индексиране.

---

## 1. Вътрешни механизми за съхранение: Текст срещу двоичен JSON

Начинът, по който се съхранява JSON, определя производителността на заявките и приложимостта на индексите.

### PostgreSQL: `json` срещу `jsonb`
PostgreSQL предлага два типа данни за JSON:
* **`json`**: Съхранява данните като точно копие в обикновен текст на входящия JSON. Той запазва шпациите, форматирането и дублиращите се ключове. Въпреки това, той изисква парсиране на текста при всяка операция по четене, което прави заявките за търсене бавни.
* **`jsonb`**: Разлага JSON в парсиран двоичен формат. Той премахва шпациите, изтрива дублиращите се ключове (като запазва само последния) и сортира ключовете на обекта за бързо търсене. Парсирането се случва веднъж при записване на данните, което прави индексирането и търсенето изключително бързи.

### MySQL: Типът данни `JSON`
MySQL предоставя единствен тип данни `JSON`. Под капака MySQL съхранява JSON в двоичен формат, подобен на `jsonb` в PostgreSQL. Той валидира JSON синтаксиса при вмъкване и позволява бърз достъп за четене до елементите на документа без повторно парсиране на необработения текст.

## 2. Заявки към JSON: Синтаксис и изрази за пътища (Path Expressions)

Извличането на данни от JSON обекти изисква специфични оператори за пътища и синтаксис.

### JSON оператори в PostgreSQL
PostgreSQL предоставя оператори за извличане на данни и тестване на структурата на документа:
* `->` връща JSON обект или елемент от масив (запазвайки тип `jsonb`).
* `->>` връща елемента като обикновен текстов низ.
* `#>` и `#>>` извличат вложени обекти с помощта на масив от пътища.
* `@>` тества съдържанието (дали левият JSON съдържа десния JSON).

```sql
-- PostgreSQL: Querying jsonb
SELECT 
    data -> 'user' ->> 'name' AS username,
    data #>> '{user, profile, age}' AS age
FROM app_logs
WHERE data @> '{"status": "error"}';
```

### JSON функции и оператори в MySQL
MySQL използва стандартни функции или вградени оператори с помощта на синтаксиса на пътищата `$`:
* `JSON_EXTRACT(col, 'path')` извлича данни.
* `->` действа като псевдоним за `JSON_EXTRACT`.
* `->>` (вграден оператор за път) извлича данните и премахва кавичките от резултата (еквивалентно на `JSON_UNQUOTE(JSON_EXTRACT(...))`).
* `JSON_CONTAINS(target, candidate, [path])` проверява дали даден документ съдържа друг.

```sql
-- MySQL: Querying JSON
SELECT 
    data->'$.user.name' AS username,
    data->>'$.user.profile.age' AS age
FROM app_logs
WHERE JSON_CONTAINS(data, '"error"', '$.status');
```

## 3. Индексиране на JSON документи

Сканирането на всеки JSON документ в таблица с милиони редове е убиец на производителността. Трябва да индексираме данните.

### PostgreSQL: GIN (Generalized Inverted Indexes)
`jsonb` в PostgreSQL се интегрира напълно с **GIN индекси** (обобщени обърнати индекси), които индексират всеки ключ и стойност в рамките на JSON документа.
* **GIN по подразбиране** (`jsonb_ops`): Индексира ключове, стойности и пътища. Поддържа заявки, съдържащи `@>`, `?`, `?|` и `?&`.
* **Специфичен за път GIN** (`jsonb_path_ops`): Индексира само двойки път-стойност. Създава по-малки индексни файлове и е по-бърз за заявки за съдържание (`@>`), но не поддържа проверки за съществуване на ключове (`?`).

```sql
-- PostgreSQL: Creating GIN Indexes
CREATE INDEX idx_logs_data ON app_logs USING gin (data);
CREATE INDEX idx_logs_data_path ON app_logs USING gin (data jsonb_path_ops);
```

### MySQL: Виртуални колони и индекси с множество стойности (Multi-Valued Indexes)
MySQL не поддържа директно индексиране на целия JSON документ. Вместо това той разчита на две техники:
1. **Генерирани (виртуални) колони + B-Tree**: Извличане на конкретен JSON ключ във виртуална колона и индексиране на тази колона.
2. **Индекси с множество стойности (Multi-Valued Indexes)**: Въведени в MySQL 8.0.17, те ви позволяват да индексирате масиви в JSON документ, поддържайки търсения чрез `MEMBER OF()`, `JSON_CONTAINS()` и `JSON_OVERLAPS()`.

```sql
-- MySQL: Generated Column Indexing
ALTER TABLE app_logs ADD COLUMN log_status VARCHAR(50) 
    GENERATED ALWAYS AS (data->>'$.status') VIRTUAL;
CREATE INDEX idx_logs_status ON app_logs(log_status);

-- MySQL: Multi-Valued Index on JSON Array
-- If data contains: {"tags": ["admin", "system", "web"]}
CREATE INDEX idx_logs_tags ON app_logs( (CAST(data->'$.tags' AS UNSIGNED ARRAY)) );

-- Query using Multi-Valued Index
SELECT * FROM app_logs WHERE 3 MEMBER OF (data->'$.tags');
```

> [!WARNING]
> **Капани с типовете данни при генерираните колони**
> Когато създавате виртуални колони в MySQL, винаги ги съобразявайте с извлечения тип данни. Ако вашето JSON поле съдържа цели числа, кастнете (конвертирайте) виртуалната колона или използвайте правилния тип. Несъответствията пречат на оптимизатора да използва индекса при изпълнението на заявките.

## 4. Сравнителна матрица за функционалностите

| Функционалност | PostgreSQL (`jsonb`) | MySQL (`JSON`) |
| :--- | :--- | :--- |
| **Формат на съхранение** | Сортирано двоично представяне | Нативно двоично представяне |
| **Оператор за път (без кавички)** | `->>` или `#>>` | `->>` |
| **Стандартен език за пътища** | SQL/JSON Path (PostgreSQL 12+) | Синтаксис JSONPath (`$.key`) |
| **Проверка на съдържание** | Оператор `@>` | Функция `JSON_CONTAINS()` |
| **Индексиране на целия документ** | Да (чрез GIN индекси) | Не (изисква генерирани колони / функционален индекс) |
| **Индексиране на масиви** | Да (вграден GIN) | Да (Multi-Valued Indexes, MySQL 8.0.17+) |

---

## 5. Резюме и добри практики

1. **Винаги използвайте двоични типове**: В PostgreSQL винаги избирайте `jsonb` пред `json`, освен ако не съхранявате и извличате данни без да ги заявявате или променяте.
2. **Проектирайте с мисъл за индексите**: В PostgreSQL използвайте GIN индекси за гъвкаво търсене. В MySQL дефинирайте виртуални генерирани колони за често търсени вложени ключове.
3. **Работете правилно с кавичките**: Внимавайте с разликата между `->` и `->>` (или `JSON_EXTRACT` и `JSON_UNQUOTE`). Използването на грешен оператор оставя кавички около низовите стойности, което води до неуспех при проверките за сравнение.
