# Диалекты, JSON и поиск по JSON-документам

Современным приложениям часто приходится работать со слабоструктурированными данными: ответами API, динамическими настройками пользователей или полиморфными атрибутами. Раньше для этого приходилось использовать антипаттерн EAV (Entity-Attribute-Value) или внедрять NoSQL базы данных. Сегодня реляционные СУБД из коробки поддерживают тип данных JSON с бинарным форматом хранения, индексацией и мощными возможностями для поиска. Однако PostgreSQL и MySQL реализуют представление JSON, синтаксис путей и механизмы индексации по-разному.

---

## 1. Внутреннее устройство: Текстовый vs. Бинарный JSON

Способ хранения JSON определяет скорость выполнения запросов и возможность эффективного использования индексов.

### PostgreSQL: `json` vs. `jsonb`
PostgreSQL предлагает два типа для работы с JSON:
* **`json`**: Сохраняет данные в виде точной текстовой копии исходного JSON. Он сохраняет форматирование, пробелы и порядок ключей, включая дубликаты. Однако СУБД приходится парсить текст при каждом чтении, из-за чего поиск работает медленно.
* **`jsonb`**: Разбирает JSON при записи в оптимизированный бинарный формат. Он удаляет лишние пробелы, дублирующиеся ключи (сохраняя последнее значение) и сортирует ключи для быстрого доступа. Парсинг происходит только один раз — при записи, что делает поиск и индексацию крайне быстрыми.

### MySQL: Тип данных `JSON`
MySQL предоставляет единственный тип данных `JSON`. Под капотом MySQL хранит JSON в бинарном формате, аналогичном типу `jsonb` в PostgreSQL. База данных проверяет валидность JSON при вставке и предоставляет быстрый доступ к элементам без повторного парсинга сырого текста.

## 2. Запросы к JSON: Синтаксис и выражения путей

Для извлечения данных из документов JSON используются специальные операторы и функции.

### Операторы JSON в PostgreSQL
PostgreSQL предоставляет удобные операторы для извлечения данных и проверки структуры:
* `->` возвращает элемент JSON или массива в формате JSON (`jsonb`).
* `->>` возвращает элемент в виде обычного текста (`text`).
* `#>` и `#>>` извлекают вложенные объекты по указанному массиву ключей (пути).
* `@>` проверяет вхождение (содержит ли левый JSON-документ правый).

```sql
-- PostgreSQL: Запрос к jsonb
SELECT 
    data -> 'user' ->> 'name' AS username,
    data #>> '{user, profile, age}' AS age
FROM app_logs
WHERE data @> '{"status": "error"}';
```

### Функции и операторы JSON в MySQL
MySQL использует стандартные функции или инлайновые операторы с использованием синтаксиса путей `$`:
* `JSON_EXTRACT(col, 'path')` извлекает данные.
* `->` является сокращенным псевдонимом для `JSON_EXTRACT`.
* `->>` (unquoting operator) извлекает данные и очищает результат от кавычек (эквивалентно `JSON_UNQUOTE(JSON_EXTRACT(...))`).
* `JSON_CONTAINS(target, candidate, [path])` проверяет, содержит ли документ указанный фрагмент.

```sql
-- MySQL: Запрос к JSON
SELECT 
    data->'$.user.name' AS username,
    data->>'$.user.profile.age' AS age
FROM app_logs
WHERE JSON_CONTAINS(data, '"error"', '$.status');
```

## 3. Индексирование JSON-документов

Сканирование каждого JSON-документа при миллионах строк в таблице — это катастрофа для производительности. Данные необходимо индексировать.

### PostgreSQL: GIN (Generalized Inverted Indexes)
Тип `jsonb` в PostgreSQL отлично интегрируется с **GIN-индексами**, которые индексируют каждый ключ и значение внутри JSON.
* **Дефолтный GIN** (`jsonb_ops`): Индексирует ключи, значения и пути. Поддерживает запросы с операторами `@>`, `?`, `?|` и `?&`.
* **Путевой GIN** (`jsonb_path_ops`): Индексирует только пары путь-значение. Создает индекс меньшего размера и работает быстрее для запросов на вхождение (`@>`), но не поддерживает проверку существования ключа (`?`).

```sql
-- PostgreSQL: Создание GIN-индексов
CREATE INDEX idx_logs_data ON app_logs USING gin (data);
CREATE INDEX idx_logs_data_path ON app_logs USING gin (data jsonb_path_ops);
```

### MySQL: Виртуальные колонки и многозначные индексы (Multi-Valued Indexes)
MySQL не поддерживает прямое создание индексов для всего JSON-документа. Вместо этого используются два подхода:
1. **Генерируемые (виртуальные) колонки + B-Tree**: Нужный ключ извлекается в виртуальную колонку, для которой создается стандартный индекс B-Tree.
2. **Многозначные индексы (Multi-Valued Indexes)**: Появились в MySQL 8.0.17. Позволяют индексировать массивы внутри JSON-документов, оптимизируя поиск через `MEMBER OF()`, `JSON_CONTAINS()` и `JSON_OVERLAPS()`.

```sql
-- MySQL: Индексирование генерируемой колонки
ALTER TABLE app_logs ADD COLUMN log_status VARCHAR(50) 
    GENERATED ALWAYS AS (data->>'$.status') VIRTUAL;
CREATE INDEX idx_logs_status ON app_logs(log_status);

-- MySQL: Многозначный индекс на массив в JSON
-- Если данные имеют вид: {"tags": ["admin", "system", "web"]}
CREATE INDEX idx_logs_tags ON app_logs( (CAST(data->'$.tags' AS UNSIGNED ARRAY)) );

-- Запрос с использованием многозначного индекса
SELECT * FROM app_logs WHERE 3 MEMBER OF (data->'$.tags');
```

> [!WARNING]
> **Несовпадение типов в виртуальных колонках**
> При создании виртуальной колонки в MySQL всегда следите за тем, чтобы тип данных колонки совпадал с типом извлекаемых данных. Если в JSON хранится число, приведите виртуальную колонку к числовому типу. Несовпадение типов помешает оптимизатору применить индекс.

## 4. Сравнительная матрица функционала

| Возможность | PostgreSQL (`jsonb`) | MySQL (`JSON`) |
| :--- | :--- | :--- |
| **Формат хранения** | Бинарный упорядоченный | Бинарный нативный |
| **Оператор извлечения без кавычек** | `->>` или `#>>` | `->>` |
| **Язык выражений путей** | SQL/JSON Path (с версии 12) | Синтаксис JSONPath (`$.key`) |
| **Проверка вхождения (containment)**| Оператор `@>` | Функция `JSON_CONTAINS()` |
| **Индекс для всего документа** | Да (GIN-индексы) | Нет (требуются виртуальные колонки) |
| **Индексирование массивов** | Да (из коробки через GIN) | Да (Multi-Valued Indexes с версии 8.0.17+) |

---

## 5. Резюме и лучшие практики

1. **Всегда используйте бинарный тип**: В PostgreSQL всегда выбирайте `jsonb` вместо `json`, кроме случаев, когда вы только записываете и читаете документ целиком без поиска по нему.
2. **Проектируйте структуру под индексы**: В PostgreSQL используйте GIN-индексы для гибкого поиска. В MySQL создавайте виртуальные генерируемые колонки для ключей, по которым часто выполняется поиск.
3. **Правильно очищайте кавычки**: Следите за разницей между `->` и `->>` (или `JSON_EXTRACT` и `JSON_UNQUOTE`). Ошибка в операторе оставит строковое значение в кавычках, из-за чего сравнение с обычной строкой вернет ложь.
