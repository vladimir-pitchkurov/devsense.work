# Діалекти, JSON та пошук у JSON

Сучасні додатки часто обробляють напівструктуровані дані, такі як відповіді API, динамічні налаштування користувачів або поліморфні атрибути. Традиційно це вимагало використання антипатернів EAV (Entity-Attribute-Value) або переходу на бази даних NoSQL. Сьогодні реляційні бази даних нативно підтримують JSON із бінарними форматами зберігання, індексацією та багатими можливостями запитів. Проте PostgreSQL та MySQL підходять до представлення JSON, синтаксису шляхів та механізмів індексації по-різному.

---

## 1. Внутрішній устрій зберігання: Текстовий проти бінарного JSON

Спосіб зберігання JSON безпосередньо впливає на продуктивність запитів та можливість використання індексів.

### PostgreSQL: `json` проти `jsonb`
PostgreSQL пропонує два типи даних для роботи з JSON:
* **`json`**: зберігає дані як точну текстову копію вхідного JSON. Він зберігає пробіли, форматування та дублікати ключів. Однак він вимагає парсингу тексту при кожній операції читання, що сповільнює пошукові запити.
* **`jsonb`**: декомпонує JSON у розібраний бінарний формат. Він видаляє пробіли, дубльовані ключі (залишаючи останній) та сортує ключі об'єктів для швидкого пошуку. Парсинг відбувається один раз під час операцій запису, що робить індексацію та пошук надзвичайно швидкими.

### MySQL: Тип даних `JSON`
MySQL надає один тип даних `JSON`. Зсередини MySQL зберігає JSON у бінарному форматі, схожому на `jsonb` у PostgreSQL. Він валідує синтаксис JSON при вставці та дозволяє швидкий доступ для читання елементів документа без повторного розбору вихідного тексту.

## 2. Запити до JSON: Синтаксис та вирази шляхів (Path Expressions)

Вилучення даних із об'єктів JSON вимагає використання специфічних операторів шляхів та синтаксису.

### Оператори JSON у PostgreSQL
PostgreSQL надає оператори для вилучення даних та перевірки структури документа:
* `->` повертає об'єкт JSON або елемент масиву (зберігаючи тип `jsonb`).
* `->>` повертає елемент як звичайний текстовий рядок.
* `#>` та `#>>` вилучають вкладені об'єкти за допомогою масиву шляхів.
* `@>` перевіряє входження (чи містить лівий JSON правий JSON).

```sql
-- PostgreSQL: Запити до jsonb
SELECT 
    data -> 'user' ->> 'name' AS username,
    data #>> '{user, profile, age}' AS age
FROM app_logs
WHERE data @> '{"status": "error"}';
```

### Функції та оператори JSON у MySQL
MySQL використовує стандартні функції або вбудовані оператори із синтаксисом шляхів `$` (JSONPath):
* `JSON_EXTRACT(col, 'path')` вилучає дані.
* `->` діє як псевдонім для `JSON_EXTRACT`.
* `->>` (вбудований оператор шляху) вилучає дані та видаляє лапки з результату (еквівалентно `JSON_UNQUOTE(JSON_EXTRACT(...))`).
* `JSON_CONTAINS(target, candidate, [path])` перевіряє, чи містить один документ інший.

```sql
-- MySQL: Запити до JSON
SELECT 
    data->'$.user.name' AS username,
    data->>'$.user.profile.age' AS age
FROM app_logs
WHERE JSON_CONTAINS(data, '"error"', '$.status');
```

## 3. Індексація документів JSON

Сканування кожного JSON-документа в таблиці з мільйоном рядків катастрофічно знижує продуктивність. Ми повинні індексувати дані.

### PostgreSQL: GIN (Узагальнені зворотні індекси)
Тип `jsonb` у PostgreSQL повністю інтегрований з **індексами GIN (Generalized Inverted Indexes)**, які індексують кожен ключ і значення всередині JSON-документа.
* **Стандартний GIN** (`jsonb_ops`): індексує ключі, значення та шляхи. Підтримує запити, що містять оператори `@>`, `?`, `?|` та `?&`.
* **GIN для конкретних шляхів** (`jsonb_path_ops`): індексує лише пари шлях-значення. Створює менші файли індексів і працює швидше для запитів на входження (`@>`), але не підтримує перевірку існування ключів (`?`).

```sql
-- PostgreSQL: Створення індексів GIN
CREATE INDEX idx_logs_data ON app_logs USING gin (data);
CREATE INDEX idx_logs_data_path ON app_logs USING gin (data jsonb_path_ops);
```

### MySQL: Віртуальні стовпці та багатозначні індекси
MySQL не підтримує безпосереднє індексування всього документа JSON. Замість цього він покладається на дві техніки:
1. **Генеровані (віртуальні) стовпці + B-Tree**: вилучення конкретного ключа JSON у віртуальний стовпець та індексування цього стовпця.
2. **Багатозначні індекси (Multi-Valued Indexes)**: представлені в MySQL 8.0.17, вони дозволяють індексувати масиви всередині JSON-документа, підтримуючи пошук через `MEMBER OF()`, `JSON_CONTAINS()` та `JSON_OVERLAPS()`.

```sql
-- MySQL: Індексування генерованого стовпця
ALTER TABLE app_logs ADD COLUMN log_status VARCHAR(50) 
    GENERATED ALWAYS AS (data->>'$.status') VIRTUAL;
CREATE INDEX idx_logs_status ON app_logs(log_status);

-- MySQL: Багатозначний індекс для масиву JSON
-- Якщо data містить: {"tags": ["admin", "system", "web"]}
CREATE INDEX idx_logs_tags ON app_logs( (CAST(data->'$.tags' AS UNSIGNED ARRAY)) );

-- Запит з використанням багатозначного індексу
SELECT * FROM app_logs WHERE 3 MEMBER OF (data->'$.tags');
```

> [!WARNING]
> **Пастки типів даних при роботі з генерованими стовпцями**
> При створенні віртуальних стовпців у MySQL завжди узгоджуйте тип вилучених даних. Якщо ваше поле JSON містить цілі числа, виконайте приведення типу (cast) віртуального стовпця або використовуйте правильний тип даних. Невідповідність типів завадить оптимізатору використовувати індекс під час виконання запиту.

## 4. Порівняльна матриця можливостей

| Особливість | PostgreSQL (`jsonb`) | MySQL (`JSON`) |
| :--- | :--- | :--- |
| **Формат зберігання** | Відсортоване бінарне представлення | Нативне бінарне представлення |
| **Оператор шляху (без лапок)** | `->>` або `#>>` | `->>` |
| **Стандартна мова шляхів** | SQL/JSON Path (PostgreSQL 12+) | Синтаксис JSONPath (`$.key`) |
| **Перевірка входження** | Оператор `@>` | Функція `JSON_CONTAINS()` |
| **Індексування всього документа** | Так (через індекси GIN) | Ні (вимагає генерованих стовпців / функціонального індексу) |
| **Індексування масивів** | Так (вбудований GIN) | Так (багатозначні індекси, MySQL 8.0.17+) |

---

## 5. Підсумок та найкращі практики

1. **Завжди використовуйте бінарні типи**: у PostgreSQL завжди обирайте `jsonb` замість `json`, якщо тільки вам не потрібно виключно зберігати та отримувати дані без їхнього аналізу чи зміни.
2. **Проектуйте під індекси**: у PostgreSQL використовуйте індекси GIN для гнучкого пошуку. У MySQL визначайте віртуальні генеровані стовпці для вкладених ключів, за якими часто здійснюється пошук.
3. **Правильно обробляйте лапки**: будьте обережні з вибором між `->` та `->>` (або `JSON_EXTRACT` та `JSON_UNQUOTE`). Використання неправильного оператора залишає лапки навколо рядкових значень, що призведе до помилок при порівнянні.
