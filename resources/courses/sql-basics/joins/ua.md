# Об'єднання таблиць

У нормалізованій реляційній базі даних дані розподіляються по кількох таблицях для усунення надлишковості та збереження цілісності. Наприклад, замість того, щоб повторювати дані про відділ для кожного працівника, ви зберігаєте працівників в одній таблиці, а відділи — в іншій, пов'язуючи їх за допомогою зовнішнього ключа.

Щоб відновити цілісне представлення даних, необхідно використовувати **об'єднання (Joins)**. Об'єднання комбінує стовпці з двох або більше таблиць на основі пов'язаного стовпця між ними. У цьому розділі ми вивчимо різні типи об'єднань, умови їх застосування та розглянемо, як їх виконують PostgreSQL та MySQL.

---

## 1. Візуалізація типів об'єднань

SQL пропонує кілька способів об'єднання таблиць, кожен з яких реалізує різну логіку:

| Тип об'єднання | Опис |
| :--- | :--- |
| **`INNER JOIN`** | Повертає записи, які мають відповідні значення в обох таблицях. |
| **`LEFT JOIN`** | Повертає всі записи з лівої таблиці та відповідні записи з правої. Повертає `NULL` для правої таблиці, якщо збігів немає. |
| **`RIGHT JOIN`** | Повертає всі записи з правої таблиці та відповідні записи з лівої. Повертає `NULL` для лівої таблиці, якщо збігів немає. |
| **`FULL JOIN`** | Повертає всі записи, якщо є збіг у лівій або правій таблиці. |
| **`CROSS JOIN`** | Повертає декартовий добуток обох таблиць (кожен рядок з таблиці А об'єднується з кожним рядком з таблиці Б). |

---

## 2. Синтаксис та приклади

Припустимо, що у нас є дві таблиці: `employees` (зі стовпцем `department_id`) та `departments` (зі стовпцем `id`).

### Inner Join (Внутрішнє об'єднання)
Повертає лише тих працівників, які належать до відділу, і лише ті відділи, до яких належать працівники.
```sql
-- MySQL & PostgreSQL
SELECT e.name AS employee_name, d.name AS department_name
FROM employees e
INNER JOIN departments d ON e.department_id = d.id;
```

### Left Join (Ліве об'єднання — найпоширеніший тип зовнішнього об'єднання)
Повертає всіх працівників, включаючи тих, які не належать до жодного відділу (назва їхнього відділу повернеться як `NULL`).
```sql
-- MySQL & PostgreSQL
SELECT e.name AS employee_name, d.name AS department_name
FROM employees e
LEFT JOIN departments d ON e.department_id = d.id;
```

### Умови об'єднання: `ON` проти `USING`
Коли стовпці, за якими ви об'єднуєте таблиці, мають однакові назви в обох таблицях (наприклад, `department_id` в `employees` та в `departments`), ви можете використовувати коротший запис `USING` замість `ON`.
```sql
-- MySQL & PostgreSQL
SELECT e.name, d.name
FROM employees e
INNER JOIN departments d USING (department_id);
```

## 3. Ключові відмінності: MySQL проти PostgreSQL

### Нативна підтримка `FULL OUTER JOIN`
* **PostgreSQL** нативно підтримує стандартний `FULL OUTER JOIN` (або просто `FULL JOIN`).
* **MySQL** НЕ підтримує `FULL JOIN`. Якщо ви спробуєте його використати, MySQL видасть синтаксичну помилку.

#### Обхідний шлях для FULL JOIN у MySQL
Щоб виконати повне зовнішнє об'єднання (Full Outer Join) у MySQL, необхідно написати `LEFT JOIN` та `RIGHT JOIN` для тих самих таблиць і об'єднати їхні результати за допомогою оператора `UNION` (який автоматично видаляє дублікати рядків).

```sql
-- PostgreSQL (Нативний синтаксис)
SELECT e.name, d.name
FROM employees e
FULL JOIN departments d ON e.department_id = d.id;

-- Обхідний шлях у MySQL (Емуляція)
SELECT e.name, d.name
FROM employees e
LEFT JOIN departments d ON e.department_id = d.id
UNION
SELECT e.name, d.name
FROM employees e
RIGHT JOIN departments d ON e.department_id = d.id;
```

### Алгоритми об'єднання та внутрішня продуктивність
Як рушії баз даних обчислюють об'єднання? Вони використовують різні внутрішні алгоритми:
* **PostgreSQL**: має надзвичайно складний оптимізатор, який десятиліттями підтримує **Nested Loop Joins** (об'єднання вкладеними циклами), **Hash Joins** (хеш-об'єднання) та **Merge Joins** (об'єднання злиттям). Він обирає найкращий алгоритм на основі розміру таблиці та наявності індексів.
* **MySQL**: історично MySQL підтримував лише **Nested Loop Joins** (що є повільним для великих таблиць, оскільки вимагає проходження по другій таблиці для кожного рядка першої). У MySQL 8.0 було впроваджено **Hash Joins** для оптимізації операцій об'єднання на великих неіндексованих стовпцях, що наблизило його до продуктивності об'єднань у PostgreSQL.

> [!WARNING]
> **Пастка декартового добутку!**
> Запуск `CROSS JOIN` (або забута умова об'єднання у старішому синтаксисі SQL, наприклад, `FROM table_a, table_b`) створює декартовий добуток. Якщо таблиця А має 10 000 рядків, а таблиця Б має 10 000 рядків, `CROSS JOIN` згенерує **100 000 000 (100 мільйонів) рядків**, що може миттєво вичерпати пам'ять сервера та заблокувати базу даних.

> [!TIP]
> **Чи знаєте ви?**
> При фільтрації стовпців у `LEFT JOIN` розташування фільтра в пропозиції `ON` порівняно з пропозицією `WHERE` повністю змінює результат.
> - **В `ON`**: фільтрує праву таблицю *до* об'єднання. Ліва таблиця все одно поверне всі свої рядки.
> - **У `WHERE`**: фільтрує результат *після* об'єднання, фактично перетворюючи ваш `LEFT JOIN` на обмежувальний `INNER JOIN`, оскільки він перевіряє значення у стовпці, який міг стати `NULL`.

## 4. Підсумок та найкращі практики

1. **Віддавайте перевагу `LEFT JOIN` перед `RIGHT JOIN`**: ліві об'єднання набагато простіше читати та візуалізувати, оскільки SQL-запити читаються зліва направо (зверху вниз).
2. **Будьте обережні з `WHERE` у зовнішніх об'єднаннях**: не фільтруйте стовпці правої таблиці у пропозиції `WHERE`, якщо тільки ви не перевіряєте на `IS NULL` для пошуку невідповідних рядків.
3. **Пам'ятайте про обмеження `FULL JOIN` у MySQL**: використовуйте обхідний шлях `LEFT JOIN UNION RIGHT JOIN` у MySQL.
4. **Use Explicit Join Syntax**: завжди використовуйте явні ключові слова об'єднання (`INNER JOIN`, `LEFT JOIN`) замість переліку таблиць через кому в пропозиції `FROM` (`FROM table_a, table_b`), щоб запобігти випадковому створенню декартового добутку.
