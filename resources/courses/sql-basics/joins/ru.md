# Соединение таблиц

В нормализованной реляционной базе данных данные распределяются по нескольким таблицам для устранения избыточности и поддержания целостности. Например, вместо того чтобы дублировать информацию об отделе для каждого сотрудника, вы храните сотрудников в одной таблице, а отделы — в другой, связывая их с помощью внешнего ключа.

Чтобы восстановить целостное представление ваших данных, используются **соединения (Joins)**. Соединение объединяет колонки из двух или более таблиц на основе связанных колонок. В этой главе мы изучим различные типы соединений, условия их выполнения, а также разберем, как PostgreSQL и MySQL обрабатывают их под капотом.

---

## 1. Визуализация типов соединений (JOIN)

SQL предлагает несколько типов соединений, каждый из которых работает по своей логике:

| Тип соединения | Описание |
| :--- | :--- |
| **`INNER JOIN`** | Возвращает записи, у которых есть совпадающие значения в обеих таблицах. |
| **`LEFT JOIN`** | Возвращает все записи из левой таблицы и совпадающие записи из правой. Если совпадений нет, для правой таблицы возвращаются значения `NULL`. |
| **`RIGHT JOIN`** | Возвращает все записи из правой таблицы и совпадающие записи из левой. Если совпадений нет, для левой таблицы возвращаются значения `NULL`. |
| **`FULL JOIN`** | Возвращает все записи, если есть совпадение хотя бы в одной из таблиц (левой или правой). |
| **`CROSS JOIN`** | Возвращает декартово произведение обеих таблиц (каждая строка из таблицы А сопоставляется с каждой строкой из таблицы Б). |

---

## 2. Синтаксис и примеры

Предположим, у нас есть две таблицы: `employees` (с колонкой `department_id`) и `departments` (с колонкой `id`).

### Внутреннее соединение (Inner Join)
Извлекает только тех сотрудников, которые привязаны к отделу, и только те отделы, в которых есть сотрудники.
```sql
-- MySQL и PostgreSQL
SELECT e.name AS employee_name, d.name AS department_name
FROM employees e
INNER JOIN departments d ON e.department_id = d.id;
```

### Левое соединение (Left Join — наиболее частый вариант)
Извлекает всех сотрудников, включая тех, кто не привязан ни к одному отделу (их `department_name` вернется как `NULL`).
```sql
-- MySQL и PostgreSQL
SELECT e.name AS employee_name, d.name AS department_name
FROM employees e
LEFT JOIN departments d ON e.department_id = d.id;
```

### Условия соединения: `ON` против `USING`
Если колонки, по которым происходит соединение, имеют абсолютно одинаковые имена в обеих таблицах (например, `department_id` в `employees` и `departments`), вы можете использовать более лаконичное сокращение `USING` вместо `ON`.
```sql
-- MySQL и PostgreSQL
SELECT e.name, d.name
FROM employees e
INNER JOIN departments d USING (department_id);
```

## 3. Ключевые различия: MySQL и PostgreSQL

### Нативная поддержка `FULL OUTER JOIN`
* **PostgreSQL** нативно поддерживает стандартный `FULL OUTER JOIN` (или просто `FULL JOIN`).
* **MySQL** НЕ поддерживает `FULL JOIN`. Попытка использовать его приведет к синтаксической ошибке.

#### Эмуляция FULL JOIN в MySQL
Чтобы реализовать полное внешнее соединение в MySQL, вам придется выполнить `LEFT JOIN` и `RIGHT JOIN` для одних и тех же таблиц, а затем объединить их результаты с помощью оператора `UNION` (который автоматически удалит дубликаты строк).

```sql
-- PostgreSQL (Нативный синтаксис)
SELECT e.name, d.name
FROM employees e
FULL JOIN departments d ON e.department_id = d.id;

-- MySQL (Обходной путь через эмуляцию)
SELECT e.name, d.name
FROM employees e
LEFT JOIN departments d ON e.department_id = d.id
UNION
SELECT e.name, d.name
FROM employees e
RIGHT JOIN departments d ON e.department_id = d.id;
```

### Алгоритмы соединений и их производительность под капотом
Как СУБД физически выполняют операции соединения? Они используют разные внутренние алгоритмы:
* **PostgreSQL**: оснащен очень продвинутым оптимизатором, который десятилетиями поддерживает **Nested Loop Joins** (соединение вложенными циклами), **Hash Joins** (соединение хэшированием) и **Merge Joins** (соединение слиянием). Он автоматически выбирает лучший алгоритм на основе размера таблиц и наличия индексов.
* **MySQL**: исторически MySQL поддерживал только **Nested Loop Joins** (что крайне медленно на больших таблицах, так как требует перебора второй таблицы для каждой строки первой). В версии MySQL 8.0 были внедрены **Hash Joins** для оптимизации соединений по большим неиндексированным колонкам, что существенно приблизило его производительность к PostgreSQL.

> [!WARNING]
> **Ловушка декартова произведения!**
> Запуск `CROSS JOIN` (или пропуск условия соединения в устаревшем синтаксисе SQL вида `FROM table_a, table_b`) создает декартово произведение. Если в таблице А содержится 10 000 строк, а в таблице Б — 10 000 строк, то CROSS JOIN сгенерирует **100 000 000 (100 миллионов) строк**, что может моментально переполнить память сервера и заблокировать базу данных.

> [!TIP]
> **А знаете ли вы?**
> При фильтрации колонок в `LEFT JOIN` указание условия в предложении `ON` или в предложении `WHERE` дает абсолютно разные результаты.
> - **В секции `ON`**: фильтрует правую таблицу *до* выполнения соединения. Левая таблица все равно вернет все свои строки.
> - **В секции `WHERE`**: фильтрует результат *после* соединения, фактически превращая ваш `LEFT JOIN` в строгий `INNER JOIN`, так как проверяются значения в колонке, которые после соединения могли стать `NULL`.

## 4. Резюме и лучшие практики

1. **Предпочитайте `LEFT JOIN` вместо `RIGHT JOIN`**: левые соединения гораздо проще читать и визуализировать, так как SQL-запросы пишутся и читаются слева направо (сверху вниз).
2. **Осторожно используйте `WHERE` при внешних соединениях**: не фильтруйте колонки правой таблицы в предложении `WHERE`, кроме проверок вида `IS NULL` для поиска строк без совпадений.
3. **Помните об ограничениях `FULL JOIN` в MySQL**: используйте конструкцию `LEFT JOIN UNION RIGHT JOIN` для обхода этой проблемы в MySQL.
4. **Пишите явный синтаксис соединений**: всегда используйте ключевые слова `INNER JOIN`, `LEFT JOIN` вместо простого перечисления таблиц через запятую в `FROM` (`FROM table_a, table_b`), чтобы исключить случайное получение декартова произведения.
