# CRUD и транзакции

Извлечение данных — это лишь половина дела. Чтобы создавать динамические приложения, вам необходимо записывать, изменять и удалять записи (операции, известные под аббревиатурой CRUD: Create, Read, Update, Delete). Кроме того, при выполнении нескольких связанных изменений в базе данных (например, при переводе денег с одного счета на другой) необходимо гарантировать, что либо все операции завершатся успешно, либо не выполнится ни одна из них. Для этой цели используются **транзакции**.

В этой финальной главе мы научимся изменять данные, работать с транзакциями, а также рассмотрим важные различия в том, как PostgreSQL и MySQL управляют транзакционными состояниями и конфликтами записи.

---

## 1. Изменение данных: INSERT, UPDATE и DELETE

### Вставка записей (INSERT)
Вы можете вставлять строки по одной или выполнять массовую вставку (bulk insert) одним запросом.
```sql
-- MySQL и PostgreSQL
-- Одиночная вставка
INSERT INTO users (email, name) VALUES ('bob@devsense.work', 'Bob');

-- Массовая вставка (рекомендуется для повышения производительности)
INSERT INTO users (email, name) 
VALUES 
    ('alice@devsense.work', 'Alice'),
    ('charlie@devsense.work', 'Charlie');
```

### Обновление записей (UPDATE)
Модифицирует существующие записи. Всегда следите за тем, чтобы условие обновления ограничивалось предложением `WHERE`.
```sql
-- MySQL и PostgreSQL
UPDATE users SET is_active = true WHERE id = 42;
```

### Удаление записей (DELETE)
Безвозвратно удаляет записи из таблицы. Как и `UPDATE`, операция `DELETE` требует обязательного использования предложения `WHERE` во избежание катастрофической потери данных.
```sql
-- MySQL и PostgreSQL
DELETE FROM users WHERE is_active = false;
```

> [!WARNING]
> **Ловушка отсутствующего WHERE!**
> Если запустить запрос `UPDATE users SET is_active = true;` или `DELETE FROM users;` без предложения `WHERE`, СУБД обновит или удалит **абсолютно все строки** в таблице. Всегда внимательно проверяйте свои запросы перед выполнением!

## 2. Транзакции: защита целостности данных

Транзакция — это последовательность SQL-операторов, выполняемая как единая неделимая группа операций. Транзакции строго следуют стандартам **ACID**:
* **Atomicity (Атомарность)**: все операции транзакции выполняются успешно, либо вся транзакция откатывается назад (все или ничего).
* **Consistency (Согласованность)**: гарантирует, что транзакция переводит базу данных из одного валидного состояния в другое, соблюдая все ограничения схемы.
* **Isolation (Изолированность)**: параллельно выполняющиеся транзакции не должны влиять друг на друга.
* **Durability (Стойкость)**: после фиксации транзакции изменения сохраняются на диске и не пропадут даже в случае сбоя системы.

### Команды управления транзакциями
* **`BEGIN` / `START TRANSACTION`**: открывает блок транзакции.
* **`COMMIT`**: перманентно сохраняет все изменения, сделанные в ходе транзакции.
* **`ROLLBACK`**: отменяет все изменения, сделанные в текущей транзакции, возвращая базу данных в исходное состояние.

```sql
-- MySQL и PostgreSQL
BEGIN; -- Начало транзакции

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- Если все прошло успешно:
COMMIT;

-- Если произошла ошибка или мы передумали:
-- ROLLBACK;
```

## 3. Ключевые различия: MySQL и PostgreSQL

### Синтаксис Upsert (вставка или обновление при конфликте ключей)
Операция «upsert» вставляет запись, если ее нет, или обновляет существующую, если происходит конфликт по уникальному индексу или первичному ключу.
* **MySQL**: использует конструкцию `ON DUPLICATE KEY UPDATE`.
* **PostgreSQL**: использует конструкцию `ON CONFLICT (имя_колонки) DO UPDATE`.

```sql
-- MySQL (ON DUPLICATE KEY UPDATE)
INSERT INTO users (id, email, visits) 
VALUES (1, 'user@devsense.work', 1)
ON DUPLICATE KEY UPDATE visits = visits + 1;

-- PostgreSQL (ON CONFLICT DO UPDATE)
INSERT INTO users (id, email, visits) 
VALUES (1, 'user@devsense.work', 1)
ON CONFLICT (id) DO UPDATE SET visits = users.visits + 1;
```

### Транзакционный DDL (изменение структуры данных)
Это одно из наиболее важных различий в логике работы двух СУБД.
* **PostgreSQL** полностью поддерживает транзакционный DDL. Вы можете создавать, изменять или удалять таблицы (`CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`) внутри транзакции и без проблем откатывать эти изменения с помощью `ROLLBACK`.
* **MySQL** НЕ поддерживает транзакционный DDL. Если вы выполните DDL-запрос внутри транзакции в MySQL, это вызовет **неявный коммит** (implicit commit). MySQL моментально зафиксирует все предыдущие операции и сам DDL на диске, после чего откат (`ROLLBACK`) станет невозможен.

```sql
-- PostgreSQL (Этот код успешно откатит все изменения!)
BEGIN;
DROP TABLE users;
ROLLBACK; -- Таблица 'users' восстановлена на месте!

-- MySQL (Откат не сработает!)
START TRANSACTION;
INSERT INTO logs (message) VALUES ('Deleting users table');
DROP TABLE users; -- Вызывает неявный коммит!
ROLLBACK; -- Ничего не произойдет; вставка и DROP уже зафиксированы!
```

### Синтаксис запуска транзакции
* В **PostgreSQL** общепринятым стандартом является команда `BEGIN` (хотя `START TRANSACTION` тоже поддерживается).
* В **MySQL** предпочтительнее использовать `START TRANSACTION` (поскольку `BEGIN` внутри хранимых процедур MySQL зарезервирован для разграничения блоков кода).

> [!TIP]
> **А знаете ли вы?**
> PostgreSQL поддерживает конструкцию `RETURNING` для операций записи. Она позволяет мгновенно получить сгенерированный ID или вычисляемые колонки без необходимости выполнять отдельный запрос `SELECT`.
> `INSERT INTO users (email) VALUES ('new@devsense.work') RETURNING id, created_at;`
> *В MySQL конструкция `RETURNING` не поддерживается, и для получения сгенерированного ID приходится обращаться к специальным функциям вроде `LAST_INSERT_ID()` на бэкенде.*

## 4. Резюме и лучшие практики

1. **Делайте транзакции короткими**: длинные транзакции удерживают блокировки строк таблицы, мешая другим пользователям и увеличивая риск взаимных блокировок (deadlocks).
2. **Остерегайтесь неявных коммитов в MySQL**: не смешивайте изменение структуры (DDL вроде `ALTER TABLE`) и изменение данных (DML вроде `UPDATE`) в рамках одной транзакции, если рассчитываете на возможность отката.
3. **Правильно пишите upsert-запросы**: используйте `ON CONFLICT` для PostgreSQL и `ON DUPLICATE KEY UPDATE` для MySQL при обработке потенциальных конфликтов по уникальным ключам.
4. **Всегда проверяйте наличие WHERE**: защитите данные от случайного удаления, контролируя наличие условий `WHERE` в операторах `UPDATE` и `DELETE`.
