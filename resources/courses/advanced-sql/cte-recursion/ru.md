# Обобщенные табличные выражения (CTE) и рекурсия

Представьте себе отладку SQL-запроса объемом в 200 строк с глубоко вложенными подзапросами, где один и тот же подзапрос дублируется трижды ради реализации `self-join`. Это кошмар для поддержки, а оптимизаторы СУБД тратят уйму времени на разбор такой структуры. Или представьте задачу обхода иерархических данных: организационной структуры (начальники и подчиненные) или многоуровневого дерева категорий товаров. В императивных языках, таких как PHP или JavaScript, вам пришлось бы загрузить все строки в память и запустить рекурсивные циклы. Однако передача сырых данных по сети — это крайне медленно. В таких сценариях на помощь приходят **Обобщенные табличные выражения (CTE)** и **Рекурсивные CTE**.

CTE (Common Table Expression) представляет собой временный именованный результирующий набор данных, который существует только в рамках выполнения одного конкретного запроса. По сути, это динамическое, удобочитаемое представление (inline view).

---

## 1. Базовые и последовательные CTE

### Синтаксис и структура
* **Тезис**: CTE позволяют объявить временные наборы данных с помощью ключевого слова `WITH` непосредственно перед выполнением основного оператора `SELECT`, `INSERT`, `UPDATE` или `DELETE`.
* **Почему это важно**: Это разбивает сложную логику на понятные, линейные шаги. Вместо вложенных подзапросов вы пишете самодокументируемый код.
* **Пример**:
  ```sql
  -- MySQL и PostgreSQL
  WITH regional_sales AS (
      SELECT region, SUM(amount) AS total_sales
      FROM orders
      GROUP BY region
  ),
  top_regions AS (
      SELECT region
      FROM regional_sales
      WHERE total_sales > 100000
  )
  SELECT o.employee_id, o.amount, o.region
  FROM orders o
  JOIN top_regions t ON o.region = t.region;
  ```
* **Следствие**: Запрос читается сверху вниз. Вы не дублируете подзапросы, а отладка сводится к простому тестированию отдельных блоков CTE.

> [!TIP]
> **А знаете ли вы?**
> CTE можно использовать для изоляции операций записи. В PostgreSQL вы можете модифицировать данные в одном CTE, получить возвращенные ID и вставить их в другую таблицу в рамках того же запроса.
> ```sql
> -- Только в PostgreSQL: Запись внутри CTE
> WITH inserted_user AS (
>     INSERT INTO users (name, email)
>     VALUES ('Alice', 'alice@devsense.work')
>     RETURNING id
> )
> INSERT INTO profiles (user_id, bio)
> SELECT id, 'Software Engineer' FROM inserted_user;
> ```
> *MySQL не поддерживает изменяющие данные операции (INSERT/UPDATE/DELETE) внутри CTE.*

## 2. Рекурсивные CTE (`WITH RECURSIVE`)

Когда требуется обойти иерархические структуры данных, классические соединения (JOIN) пасуют, так как глубина дерева заранее неизвестна. **Рекурсивные CTE** решают эту проблему путем многократного выполнения запроса до тех пор, пока очередная итерация не вернет пустой набор строк.

### Анатомия рекурсии
Рекурсивный CTE всегда состоит из трех ключевых элементов:
1. **Anchor Member (Базовый запрос)**: Инициализирует результирующий набор (выполняется ровно один раз).
2. **Recursive Member (Рекурсивный запрос)**: Запрос, который ссылается на само табличное выражение (CTE) и соединяет его с таблицей-источником.
3. **Условие завершения**: Срабатывает автоматически, когда рекурсивная часть возвращает ноль строк.

```
Схема выполнения:
[Базовый запрос] ---> Стартовые строки
        |
        +---> [Рекурсивный запрос] (Выполняется для стартовых строк) ---> Строки шага 1
                    |
                    +---> [Рекурсивный запрос] (Выполняется для строк шага 1) ---> Строки шага 2
                                |
                                +---> Возврат пустых строк ---> ЗАВЕРШЕНИЕ
```

### Практический пример: Иерархия сотрудников
* **Тезис**: Рекурсивный обход таблицы, содержащей ссылки «родитель-потомок».
* **Пример**:
  ```sql
  -- MySQL и PostgreSQL
  WITH RECURSIVE org_chart AS (
      -- 1. Базовая часть: находим генерального директора (CEO)
      SELECT id, name, manager_id, 1 AS depth
      FROM employees
      WHERE manager_id IS NULL
      
      UNION ALL
      
      -- 2. Рекурсивная часть: соединяем сотрудников с их менеджерами
      SELECT e.id, e.name, e.manager_id, o.depth + 1
      FROM employees e
      INNER JOIN org_chart o ON e.manager_id = o.id
  )
  SELECT * FROM org_chart ORDER BY depth;
  ```
* **Следствие**: Вы получаете дерево подчиненности любой глубины с указанием уровня вложенности за один-единственный запрос, выполненный на стороне СУБД.

> [!WARNING]
> **Опасность зацикливания!**
> Если в данных есть круговая зависимость (например, Сотрудник А подчиняется Б, Б подчиняется В, а В — подчиняется А), рекурсивный запрос будет выполняться бесконечно, что приведет к переполнению памяти сервера.
> - **PostgreSQL** предлагает встроенную защиту с помощью конструкции `CYCLE`:
>   `CYCLE id SET is_cycle USING path`
> - **MySQL** не имеет синтаксиса `CYCLE`, но позволяет ограничить глубину рекурсии на уровне сессии:
>   `SET max_sp_recursion_depth = 255;` или через хинт оптимизатора: `/*+ MAX_EXECUTION_TIME(1000) */`

## 3. Под капотом СУБД: Материализация и оптимизация

Как базы данных обрабатывают CTE? Считают ли они их как временные таблицы или «копипастят» их код напрямую в основной запрос? Здесь поведение СУБД сильно отличается:

### Правила материализации в PostgreSQL
* **PostgreSQL < 12**: Исторически Postgres рассматривал все CTE как «оптимизационные барьеры» (optimization fences). Он всегда сначала вычислял CTE, сохранял результат во временной таблице (материализовал его) и только потом соединял. Это не позволяло переносить внешние условия `WHERE` внутрь CTE, что иногда приводило к просадкам производительности.
* **PostgreSQL 12+**: Поведение по умолчанию изменено на **NOT MATERIALIZED**. Если CTE вызывается один раз, Postgres встраивает его логику в основной запрос (inlining), позволяя использовать индексы.
* **Ручное управление**:
  - `WITH cte AS MATERIALIZED (...)` принудительно материализует результат.
  - `WITH cte AS NOT MATERIALIZED (...)` принудительно встраивает код.

### Оптимизация в MySQL
* **MySQL 8.0**: Использует стоимостной оптимизатор (cost-based optimizer) для принятия решения о материализации. Если выражение простое, MySQL всегда встраивает его код. Если CTE используется в запросе несколько раз, MySQL материализует его во временную таблицу для экономии ресурсов.

## 4. Резюме и лучшие практики

1. **Пишите CTE для читаемости**: Заменяйте сложные вложенные подзапросы последовательными, именованными блоками `WITH`.
2. **Помните об оптимизационном барьере**: В PostgreSQL при многократном обращении к одному CTE используйте `AS NOT MATERIALIZED`, если хотите, чтобы оптимизатор применил внешние индексы.
3. **Защищайтесь от бесконечных циклов**: Всегда валидируйте данные на отсутствие циклических связей перед запуском `WITH RECURSIVE` или устанавливайте лимиты времени выполнения.
