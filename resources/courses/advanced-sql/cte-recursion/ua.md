# Узагальнені табличні вирази (CTE) та рекурсія

Уявіть собі налагодження SQL-запиту на 200 рядків, наповненого глибоко вкладеними підзапитами, де один і той самий підзапит дублюється тричі лише для виконання самооб'єднань (self-joins). Це жах для підтримки, а аналізатори планів запитів баз даних намагаються його оптимізувати. Або подумайте про представлення організаційної структури компанії (керівники та підлеглі) чи багаторівневого дерева категорій товарів. В імперативних мовах програмування, таких як PHP або JavaScript, ви б отримували всі рядки і запускали рекурсивні цикли. Але робити це через мережу — повільно та вкрай неефективно. Саме тут на допомогу приходять **узагальнені табличні вирази (Common Table Expressions, CTE)** та **рекурсивні CTE**.

CTE діє як тимчасовий іменований результуючий набір, який існує лише в межах області виконання одного запиту. Він працює як динамічне, зручне для читання вбудоване представлення (inline view).

---

## 1. Нерекурсивні та послідовні CTE

### Синтаксис та структура
* **Суть**: CTE дозволяють визначати тимчасові результуючі набори за допомогою пропозиції `WITH` перед вашим основним оператором `SELECT`, `INSERT`, `UPDATE` або `DELETE`.
* **Чому це важливо**: це розбиває складні запити на логічні, легкі для читання кроки, замінюючи вкладені підзапити та роблячи код самодокументованим.
* **Приклад**:
  ```sql
  -- MySQL & PostgreSQL
  WITH regional_sales AS (
      SELECT region, SUM(amount) AS total_sales
      FROM orders
      GROUP BY region
  ),
  top_regions AS (
      SELECT region
      FROM regional_sales
      WHERE total_sales > 100000
  )
  SELECT o.employee_id, o.amount, o.region
  FROM orders o
  JOIN top_regions t ON o.region = t.region;
  ```
* **Наслідок**: запит читається лінійно зверху вниз. Ви уникаєте дублювання підзапитів, а налагодження стає таким же простим, як вибірка з одного CTE.

> [!TIP]
> **Чи знаєте ви?**
> CTE можна використовувати для ізоляції операцій запису. У PostgreSQL ви можете записати дані у CTE та вибрати отримані ID для вставки в іншу таблицю в межах того самого запиту.
> ```sql
> -- PostgreSQL Only: Запис у CTE
> WITH inserted_user AS (
>     INSERT INTO users (name, email)
>     VALUES ('Alice', 'alice@devsense.work')
>     RETURNING id
> )
> INSERT INTO profiles (user_id, bio)
> SELECT id, 'Software Engineer' FROM inserted_user;
> ```
> *MySQL не підтримує оператори модифікації даних (INSERT/UPDATE/DELETE) всередині CTE.*

## 2. Рекурсивні CTE (`WITH RECURSIVE`)

Коли вам потрібно обійти ієрархічні структури даних, стандартні об'єднання SQL (joins) не спрацюють, оскільки глибина дерева невідома. **Рекурсивні CTE** вирішують це шляхом багаторазового виконання запиту, доки не припинять повертатися нові рядки.

### Анатомія рекурсії
Рекурсивний CTE складається з трьох частин:
1. **Anchor Member (Якірний запит)**: базовий запит, який ініціалізує результуючий набір (виконується один раз).
2. **Recursive Member (Рекурсивний запит)**: запит, який посилається на сам CTE і об'єднується з результатом попереднього кроку.
3. **Termination Condition (Умова завершення)**: неявно спрацьовує, коли рекурсивний запит повертає нуль рядків.

```
Потік виконання:
[Якірний запит] ---> Початкові рядки
        |
        +---> [Рекурсивний запит] (Виконується для якірних рядків) ---> Рядки кроку 1
                    |
                    +---> [Рекурсивний запит] (Виконується для рядків кроку 1) ---> Рядки кроку 2
                                |
                                +---> Повертає порожній набір ---> ЗАВЕРШЕННЯ
```

### Практичний приклад: ієрархія організації
* **Суть**: рекурсивний обхід таблиці, що містить зв'язки батько-нащадок.
* **Приклад**:
  ```sql
  -- MySQL & PostgreSQL
  WITH RECURSIVE org_chart AS (
      -- 1. Якір: знайти CEO
      SELECT id, name, manager_id, 1 AS depth
      FROM employees
      WHERE manager_id IS NULL
      
      UNION ALL
      
      -- 2. Рекурсивний запит: об'єднати працівників з їхніми керівниками
      SELECT e.id, e.name, e.manager_id, o.depth + 1
      FROM employees e
      INNER JOIN org_chart o ON e.manager_id = o.id
  )
  SELECT * FROM org_chart ORDER BY depth;
  ```
* **Наслідок**: ви отримуєте все дерево підлеглих разом із рівнем їхньої вкладеності за один запит, який повністю виконується всередині бази даних.

> [!WARNING]
> **Захист від нескінченного циклу!**
> Якщо ваші дані містять циклічне посилання (наприклад, працівник А підпорядковується Б, Б підпорядковується В, В підпорядковується А), рекурсивний CTE виконуватиметься нескінченно, що призведе до вичерпання пам'яті сервера.
> - **PostgreSQL** надає пропозицію `CYCLE` для запобігання циклам:
>   `CYCLE id SET is_cycle USING path`
> - **MySQL** не має пропозиції `CYCLE`, але дозволяє обмежувати глибину рекурсії глобально або для конкретного запиту:
>   `SET max_sp_recursion_depth = 255;` або за допомогою підказок оптимізатора: `/*+ MAX_EXECUTION_TIME(1000) */`

## 3. Внутрішній устрій бази даних: матеріалізація та оптимізація

Як рушії баз даних виконують CTE? Чи запускають вони їх як тимчасові таблиці, чи просто копіюють їхній SQL безпосередньо в основний запит? Рушії поводяться по-різному:

### Правила матеріалізації PostgreSQL
* **PostgreSQL < 12**: історично Postgres трактував усі CTE як "бар'єри оптимізації" (optimization fences). Він завжди спочатку виконував CTE, зберігав результати в тимчасовій таблиці (матеріалізував їх), а потім об'єднував. Це заважало оптимізатору опускати зовнішні фільтри `WHERE` всередину CTE, що спричиняло серйозні проблеми з продуктивністю.
* **PostgreSQL 12+**: змінив поведінку за замовчуванням на **NOT MATERIALIZED**. Якщо CTE викликається лише один раз, Postgres об'єднує його логіку з основним запитом (вбудовує її), щоб мати можливість використовувати сканування індексів.
* **Ручне перевизначення**:
  - `WITH cte AS MATERIALIZED (...)` змушує Postgres оцінити його один раз та закешувати результат.
  - `WITH cte AS NOT MATERIALIZED (...)` змушує Postgres вбудувати його в основний запит.

### Вбудовування в MySQL
* **MySQL 8.0**: використовує вартісний оптимізатор (cost-based optimizer), щоб вирішити, чи вбудовувати CTE, чи матеріалізувати його в тимчасову таблицю. Якщо CTE є простим, MySQL завжди вбудовує його. Якщо на нього посилаються кілька разів, MySQL матеріалізує його для уникнення повторних обчислень.

## 4. Підсумок та найкращі практики

1. **Використовуйте CTE для читабельності**: замінюйте складні вкладені підзапити послідовними іменованими CTE.
2. **Слідкуйте за бар'єром оптимізації**: якщо ви використовуєте PostgreSQL, будьте обережні з кількома посиланнями на один і той самий CTE. Використовуйте `AS NOT MATERIALIZED`, якщо хочете, щоб оптимізатор застосовував сканування індексів.
3. **Захищайтеся від розростання циклів**: завжди перевіряйте свої дані на наявність циклічних посилань перед виконанням `WITH RECURSIVE` або встановлюйте обмеження на виконання.
