# Нееквівалентні об'єднання та операції над множинами

Більшість посібників із SQL зосереджуються на об'єднанні таблиць за допомогою оператора рівності (`ON a.id = b.id`). Проте реальні завдання баз даних часто вимагають співставлення записів на основі діапазонів, інтервалів, нерівностей або об'єднання наборів даних за допомогою математичної теорії множин.

Розуміння **нееквівалентних об'єднань (non-equi joins)** та **розширених операцій над множинами** — це те, що відрізняє початківців у SQL від досвідчених інженерів баз даних.

---

## 1. Нееквівалентні об'єднання: вихід за межі рівності

**Нееквівалентне об'єднання (non-equi join)** — це умова об'єднання, яка використовує будь-які оператори, крім знаку рівності (`=`), наприклад, `<`, `>`, `<=`, `>=`, `BETWEEN` або `!=`.

### Сценарій використання: перетин часових інтервалів
Уявіть, що ви керуєте бронюванням готельних номерів. Вам потрібно перевірити, чи перетинається новий запит на бронювання з будь-якими існуючими бронюваннями.
* **Логіка**: перетин (колізія) виникає, якщо дата початку нового запиту передує даті завершення існуючого бронювання, І дата завершення нового запиту є пізнішою за дату початку існуючого бронювання.

```sql
-- MySQL & PostgreSQL
SELECT 
    b1.room_id,
    b1.booking_id AS booking_1,
    b2.booking_id AS booking_2
FROM bookings b1
JOIN bookings b2 ON b1.room_id = b2.room_id
    AND b1.booking_id < b2.booking_id -- Уникнення порівняння з самим собою та дублювання пар
    AND b1.start_date < b2.end_date 
    AND b1.end_date > b2.start_date;
```

### Сценарій використання: групування за діапазонами (наприклад, цінові рівні)
Ви можете призначати товари до цінових категорій без жорсткого кодування цих рівнів у запиті або використання складних вкладених циклів.

```sql
-- MySQL & PostgreSQL
SELECT 
    p.product_name, 
    p.price, 
    t.tier_name
FROM products p
JOIN price_tiers t ON p.price BETWEEN t.min_price AND t.max_price;
```

> [!WARNING]
> **Проблема продуктивності при нееквівалентних об'єднаннях!**
> Хоча сучасні планувальники запитів використовують ефективні **хеш-об'єднання (Hash Joins)** для еквівалентних об'єднань, вони не можуть використовувати їх для нееквівалентних умов. Замість цього вони повертаються до алгоритмів **Nested Loop Joins** (об'єднання вкладеними циклами) або **Block Nested Loops**. Це може призвести до часової складності `O(N * M)`.
> У PostgreSQL ви можете пом'якшити цю проблему за допомогою **діапазонних типів даних (Range Types)** та **індексів GiST**. У MySQL відсутні вбудовані діапазонні типи, тому вам доведеться ретельно проектувати та оптимізувати складені індекси B-Tree.

## 2. Розширені операції над множинами

Операції над множинами об'єднують результати двох або більше запитів в один результуючий набір.

```
Операції над множинами:
[Запит 1] UNION [Запит 2]      --> Повертає всі унікальні рядки з обох запитів.
[Запит 1] INTERSECT [Запит 2]  --> Повертає рядки, які присутні в ОБОХ запитах.
[Запит 1] EXCEPT [Запит 2]     --> Повертає рядки, що є в Запиті 1, але ВІДСУТНІ в Запиті 2.
```

### `UNION` проти `UNION ALL`
* **`UNION`**: об'єднує результуючі набори та видаляє дублікати. Для цього база даних повинна відсортувати дані або побудувати тимчасову хеш-таблицю, що призводить до додаткових витрат продуктивності.
* **`UNION ALL`**: об'єднує результуючі набори, але зберігає всі дублікати. Він не виконує сортування або дедуплікацію, тому працює набагато швидше.

### `INTERSECT` та `EXCEPT` (з `ALL` та без нього)
Стандарт SQL визначає два режими для операцій над множинами:
1. **За замовчуванням (Distinct)**: видаляє повторювані рядки перед поверненням результатів.
2. **`ALL`**: зберігає кардинальність дублікатів. Наприклад, якщо рядок з'являється 3 рази в Запиті 1 і 2 рази в Запиті 2:
   - `INTERSECT ALL` поверне його `MIN(3, 2) = 2` рази.
   - `EXCEPT ALL` поверне його `3 - 2 = 1` раз.

## 3. MySQL проти PostgreSQL: сумісність та синтаксис

Це одна з тих областей, де дві бази даних суттєво відрізняються, особливо якщо говорити про старі версії.

### Таблиця підтримки операцій над множинами

| Оператор | PostgreSQL (Всі версії) | MySQL 8.0.31+ | MySQL < 8.0.31 |
| :--- | :--- | :--- | :--- |
| `UNION` / `UNION ALL` | Підтримується нативно | Підтримується нативно | Підтримується нативно |
| `INTERSECT` (Distinct) | Підтримується нативно | Підтримується нативно | *Не підтримується* |
| `EXCEPT` (Distinct) | Підтримується нативно | Підтримується нативно | *Не підтримується* |
| `INTERSECT ALL` | Підтримується нативно | *Не підтримується* | *Не підтримується* |
| `EXCEPT ALL` | Підтримується нативно | *Не підтримується* | *Не підтримується* |

### Обхідні шляхи для MySQL (емуляція)

Якщо ви працюєте з версіями MySQL старішими за 8.0.31, вам доведеться емулювати `INTERSECT` та `EXCEPT` за допомогою об'єднань або підзапитів.

#### Емуляція `INTERSECT`:
```sql
-- Еквівалент INTERSECT для MySQL < 8.0.31
SELECT DISTINCT a.email 
FROM users_a a
INNER JOIN users_b b ON a.email = b.email;
```

#### Емуляція `EXCEPT`:
```sql
-- Еквівалент EXCEPT для MySQL < 8.0.31
SELECT DISTINCT a.email 
FROM users_a a
LEFT JOIN users_b b ON a.email = b.email
WHERE b.email IS NULL;
```

> [!TIP]
> **Ексклюзив PostgreSQL: обмеження виключення (Exclusion Constraints)**
> У PostgreSQL ви можете на рівні схеми гарантувати, що жодні два рядки в таблиці не будуть перетинатися, використовуючи обмеження `EXCLUSION CONSTRAINT` з індексом GiST.
> ```sql
> -- Лише для PostgreSQL: Запобігання перетину бронювань на рівні схеми бази даних
> ALTER TABLE bookings ADD CONSTRAINT no_overlap 
> EXCLUDE USING gist (room_id WITH =, tsrange(start_date, end_date) WITH &&);
> ```
> *У MySQL для реалізації цього правила знадобиться створення власних тригерів BEFORE INSERT/UPDATE.*

## 4. Підсумок та найкращі практики

1. **Віддавайте перевагу `UNION ALL` замість `UNION`**: якщо вам не потрібно явно видаляти дублікати, завжди використовуйте `UNION ALL` для уникнення накладних витрат на сортування в базі даних.
2. **Слідкуйте за об'єднаннями**: при написанні нееквівалентних об'єднань перевіряйте план виконання запиту (`EXPLAIN`), щоб переконатися, що база даних не виконує повільний вкладений цикл (nested loop) на мільйонах рядків.
3. **Зважайте на сумісність**: якщо ви пишете запити для додатків, які мають працювати з різними СКБД, уникайте нативного використання `INTERSECT`/`EXCEPT` або складного синтаксису емуляції. Замість цього використовуйте структури з `EXISTS` та `LEFT JOIN`.
