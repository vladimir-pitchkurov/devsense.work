# Соединения по неэквивалентности (Non-Equi Joins) и операции над множествами

Большинство учебников по SQL фокусируются на объединении таблиц по условию равенства (`ON a.id = b.id`). Однако в реальных задачах часто требуется сопоставлять записи на основе диапазонов, интервалов, неравенств или объединять наборы данных, используя математическую теорию множеств.

Понимание **соединений по неэквивалентности** и **расширенных операций над множествами** — это то, что отличает опытного разработчика баз данных от новичка.

---

## 1. Соединения по неэквивалентности: выход за рамки равенства

**Соединение по неэквивалентности (non-equi join)** — это условие соединения таблиц, использующее любые операторы сравнения, кроме знака равенства (`=`), такие как `<`, `>`, `<=`, `>=`, `BETWEEN` или `!=`.

### Сценарий использования: пересечение временных интервалов
Представьте, что вы управляете бронированием номеров в отеле. Вам необходимо проверить, не перекрывается ли новый запрос на бронирование с уже существующими.
* **Логика**: Наложение интервалов происходит в том случае, если дата начала нового бронирования наступает раньше даты окончания существующего, И дата окончания нового бронирования наступает позже даты начала существующего.

```sql
-- MySQL и PostgreSQL
SELECT 
    b1.room_id,
    b1.booking_id AS booking_1,
    b2.booking_id AS booking_2
FROM bookings b1
JOIN bookings b2 ON b1.room_id = b2.room_id
    AND b1.booking_id < b2.booking_id -- Исключаем самопересечение и дублирование пар
    AND b1.start_date < b2.end_date 
    AND b1.end_date > b2.start_date;
```

### Сценарий использования: распределение по диапазонам (ценовые категории)
Вы можете распределить продукты по ценовым категориям без жесткого кодирования рамок в коде приложения или использования сложных вложенных циклов.

```sql
-- MySQL и PostgreSQL
SELECT 
    p.product_name, 
    p.price, 
    t.tier_name
FROM products p
JOIN price_tiers t ON p.price BETWEEN t.min_price AND t.max_price;
```

> [!WARNING]
> **Проблемы с производительностью при неэквивалентных соединениях!**
> В то время как для классических соединений по равенству СУБД используют эффективный алгоритм **Hash Join**, для условий неэквивалентности он неприменим. Оптимизаторам приходится откатываться к **Nested Loop Joins** или **Block Nested Loops**, что может привести к временной сложности порядка `O(N * M)`.
> В PostgreSQL для решения этой проблемы можно использовать **диапазонные типы (Range Types)** и **GiST-индексы**. В MySQL диапазонных типов нет, поэтому приходится оптимизировать составные B-Tree индексы вручную.

## 2. Расширенные операции над множествами

Операции над множествами объединяют результаты работы двух или более запросов в один результирующий набор.

```
Операции над множествами:
[Запрос 1] UNION [Запрос 2]      --> Возвращает все уникальные строки из обоих запросов.
[Запрос 1] INTERSECT [Запрос 2]  --> Возвращает строки, присутствующие в ОБОИХ запросах.
[Запрос 1] EXCEPT [Запрос 2]     --> Возвращает строки, которые есть в Запросе 1, но нет в Запросе 2.
```

### `UNION` против `UNION ALL`
* **`UNION`**: Объединяет наборы строк и удаляет дубликаты. Чтобы отфильтровать повторяющиеся записи, СУБД вынуждена сортировать данные или строить временную хэш-таблицу в памяти, что существенно замедляет запрос.
* **`UNION ALL`**: Просто объединяет наборы данных без удаления дубликатов. Никакой сортировки или проверки уникальности не происходит, поэтому операция выполняется значительно быстрее.

### `INTERSECT` и `EXCEPT` (С модификатором `ALL` и без)
Стандарт SQL определяет два режима работы для этих операторов:
1. **По умолчанию (Distinct)**: Удаляет дубликаты строк перед выводом результата.
2. **`ALL`**: Сохраняет кратность совпадений. Например, если строка встречается в первом запросе 3 раза, а во втором — 2 раза:
   - `INTERSECT ALL` вернет строку `MIN(3, 2) = 2` раза.
   - `EXCEPT ALL` вернет строку `3 - 2 = 1` раз.

## 3. Сравнение MySQL и PostgreSQL: поддержка и синтаксис

Это одна из областей, где поведение и поддержка конструкций в двух СУБД значительно расходятся, особенно в старых версиях.

### Таблица поддержки операций над множествами

| Оператор | PostgreSQL (Все версии) | MySQL 8.0.31+ | MySQL < 8.0.31 |
| :--- | :--- | :--- | :--- |
| `UNION` / `UNION ALL` | Поддерживается | Поддерживается | Поддерживается |
| `INTERSECT` (Distinct) | Поддерживается | Поддерживается | *Не поддерживается* |
| `EXCEPT` (Distinct) | Поддерживается | Поддерживается | *Не поддерживается* |
| `INTERSECT ALL` | Поддерживается | *Не поддерживается* | *Не поддерживается* |
| `EXCEPT ALL` | Поддерживается | *Not Supported* | *Не поддерживается* |

### Эмуляция для старых версий MySQL

Если вы работаете с MySQL версий ниже 8.0.31, вам придется эмулировать поведение `INTERSECT` и `EXCEPT` с помощью классических соединений или подзапросов.

#### Эмуляция `INTERSECT`:
```sql
-- Эквивалент INTERSECT для MySQL < 8.0.31
SELECT DISTINCT a.email 
FROM users_a a
INNER JOIN users_b b ON a.email = b.email;
```

#### Эмуляция `EXCEPT`:
```sql
-- Эквивалент EXCEPT для MySQL < 8.0.31
SELECT DISTINCT a.email 
FROM users_a a
LEFT JOIN users_b b ON a.email = b.email
WHERE b.email IS NULL;
```

> [!TIP]
> **Фишка PostgreSQL: Ограничения исключения (Exclusion Constraints)**
> В PostgreSQL можно на уровне схемы данных запретить пересечение интервалов с помощью конструкции `EXCLUDE` и индекса GiST.
> ```sql
> -- Только в PostgreSQL: Запрет на пересечение бронирований на уровне СУБД
> ALTER TABLE bookings ADD CONSTRAINT no_overlap 
> EXCLUDE USING gist (room_id WITH =, tsrange(start_date, end_date) WITH &&);
> ```
> *В MySQL для реализации аналогичного правила потребуется создавать триггеры BEFORE INSERT и BEFORE UPDATE.*

## 4. Резюме и лучшие практики

1. **Предпочитайте `UNION ALL` вместо `UNION`**: Если вам не требуется принудительное удаление дубликатов, всегда пишите `UNION ALL`. Это убережет СУБД от затратной операции сортировки.
2. **Анализируйте планы запросов**: При написании non-equi joins обязательно изучайте план выполнения (`EXPLAIN`). Убедитесь, что СУБД не делает вложенный цикл (nested loop) по таблицам с миллионами строк.
3. **Обеспечивайте совместимость**: Если ваш код должен работать на разных СУБД, избегайте использования нативных `INTERSECT`/`EXCEPT`. Пишите кроссплатформенные запросы с использованием `EXISTS` или `LEFT JOIN`.
