# Збережені процедури, функції та тригери

Перенесення бізнес-логіки ближче до даних може суттєво знизити затримки при передачі даних мережею та забезпечити суворе дотримання цілісності даних. Коли ви пишете програмну логіку, яка виконується безпосередньо всередині бази даних, ви використовуєте три основні конструкції: **функції**, **збережені процедури** та **тригери**.

Розуміння того, як ці елементи керують транзакціями, отримують доступ до пам'яті та чим відрізняються в MySQL та PostgreSQL, є необхідним для проектування надійних баз даних.

---

## 1. Функції користувача (UDF) проти збережених процедур

Хоча обидва інструменти групують оператори SQL разом, вони служать абсолютно різним цілям. Найважливіша відмінність полягає в **керуванні транзакціями**.

| Особливість | Функція користувача (UDF) | Збережена процедура |
| :--- | :--- | :--- |
| **Виклик** | Викликається вбудовано в запитах (наприклад, `SELECT my_func(val)`) | Викликається окремо за допомогою `CALL my_proc(val)` |
| **Значення, що повертається** | Повинна повертати одне значення або таблицю | Не повертає значення (замість цього використовує параметри `OUT`) |
| **Транзакції** | **Не може** виконувати `COMMIT` або `ROLLBACK` | **Може** виконувати `COMMIT` або `ROLLBACK` |
| **Контекст використання** | Читання/перетворення даних у запитах | Узгодження складних пакетних записів та операцій |

### Приклад керування транзакціями (Збережена процедура)
Збережені процедури можуть нативно керувати транзакціями, дозволяючи вам фіксувати або скасовувати зміни під час виконання.

```sql
-- Синтаксис PostgreSQL 11+
CREATE PROCEDURE transfer_funds(sender INT, receiver INT, amount DECIMAL)
LANGUAGE plpgsql AS $$
BEGIN
    UPDATE accounts SET balance = balance - amount WHERE id = sender;
    UPDATE accounts SET balance = balance + amount WHERE id = receiver;
    
    -- Фіксація транзакції всередині процедури
    COMMIT;
EXCEPTION WHEN OTHERS THEN
    -- Відкат змін у разі будь-го збою
    ROLLBACK;
END;
$$;

-- Синтаксис MySQL
CREATE PROCEDURE transfer_funds(IN sender INT, IN receiver INT, IN amount DECIMAL)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
    END;

    START TRANSACTION;
    UPDATE accounts SET balance = balance - amount WHERE id = sender;
    UPDATE accounts SET balance = balance + amount WHERE id = receiver;
    COMMIT;
END;
```

## 2. Тригери: автоматизація бізнес-правил

**Тригер** — це об'єкт бази даних, який автоматично запускає визначений набір SQL-операторів, коли в таблиці відбувається подія (наприклад, `INSERT`, `UPDATE` або `DELETE`).

### Час виконання тригера
* **`BEFORE`**: виконується *до* того, як база даних запише зміни на диск. Використовується для валідації або зміни вхідних значень.
* **`AFTER`**: виконується *після* того, як база даних запише зміни на диск. Використовується для логування, аудиту або оновлення інших таблиць.
* **`INSTEAD OF`**: використовується для представлень для заміни стандартних дій запису на власну логіку.

### Тригери рівня рядка проти тригерів рівня оператора
* **`FOR EACH ROW`**: тригер виконується один раз для кожного окремого рядка, на який впливає запит. Якщо оновлення стосується 10 000 рядків, тригер виконається 10 000 разів.
* **`FOR EACH STATEMENT`**: тригер виконується рівно один раз для всього оператора SQL, незалежно від того, скільки рядків було змінено. Корисний для логування або масових перевірок.

### Псевдозаписи `OLD` та `NEW`
Тригери мають доступ до спеціальних змінних, що відображають стан рядка:
* **`NEW`**: містить нові значення рядка (доступно при `INSERT` та `UPDATE`).
* **`OLD`**: містить початкові значення рядка (доступно при `UPDATE` та `DELETE`).

## 3. MySQL проти PostgreSQL: синтаксичні та структурні відмінності

Архітектура виконання тригерів та процедур суттєво відрізняється між цими двома базами даних.

### 1. Архітектура тригерів: функції проти вбудованого коду
* **PostgreSQL**: вимагає двоетапного процесу. Спочатку ви повинні написати тригерну функцію, яка повертає спеціальний тип `TRIGGER`. Потім ви прив'язуєте цю функцію до таблиці за допомогою `CREATE TRIGGER`.
```sql
-- PostgreSQL: 1. Створення тригерної функції
CREATE FUNCTION log_salary_change() RETURNS TRIGGER AS $$
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit(emp_id, old_val, new_val)
        VALUES (OLD.id, OLD.salary, NEW.salary);
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- PostgreSQL: 2. Прив'язка функції до таблиці
CREATE TRIGGER after_salary_update
AFTER UPDATE ON employees
FOR EACH ROW EXECUTE FUNCTION log_salary_change();
```

* **MySQL**: дозволяє писати логіку тригера безпосередньо вбудованою (inline) всередині визначення тригера.
```sql
-- MySQL: Пряме вбудоване визначення тригера
CREATE TRIGGER after_salary_update
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit(emp_id, old_val, new_val)
        VALUES (OLD.id, OLD.salary, NEW.salary);
    END IF;
END;
```

### 2. Підтримка мов програмування
* **MySQL**: підтримує лише власне розширення синтаксису SQL.
* **PostgreSQL**: підтримує кілька мов. Хоча `PL/pgSQL` є стандартною, ви можете писати функції бази даних та тригери на `PL/Python`, `PL/Perl` або `PL/v8` (JavaScript).

> [!WARNING]
> **Накладні витрати продуктивності тригерів!**
> Тригери рівня рядка (`FOR EACH ROW`) можуть призвести до серйозного зниження продуктивності під час масових оновлень. Якщо ви оновлюєте 1 мільйон рядків, тригер рівня рядка змушує базу даних перемикати контекст між рушієм виконання SQL та інтерпретатором процедурної мови 1 мільйон разів, перетворюючи швидкий запит на основі множин на повільний цикл рядок за рядком.

> [!TIP]
> **Обмеження транзакцій у PostgreSQL:**
> Хоча збережені процедури у PostgreSQL 11+ підтримують команди транзакцій (`COMMIT`/`ROLLBACK`), вони не можуть виконувати їх, якщо процедуру викликано зсередини вже активного блоку транзакції (наприклад, якщо ви запускаєте `BEGIN; CALL my_procedure();`).

## 4. Підсумок та найкращі практики

1. **Функції для обчислень**: використовуйте функції користувача (UDF) для перетворень та обчислень всередині запитів. Не намагайтеся змінювати дані або керувати транзакціями всередині них.
2. **Процедури для робочих процесів**: використовуйте збережені процедури для запуску пакетних оновлень, організації складних записів та керування транзакціями.
3. **Тримайте тригери легковагими**: використовуйте тригери лише для критично важливої перевірки цілісності даних, логування або аудиту. Якщо ви змушені їх використовувати, тримайте логіку мінімальною, щоб запобігти виникненню вузьких місць при записі.
4. **Будьте обережні з масовими операціями**: вимикайте або обходьте тригери під час масового імпорту чи міграції даних для уникнення катастрофічного падіння продуктивності сервера.
