# Хранимые процедуры, функции и триггеры

Перенос бизнес-логики ближе к данным позволяет существенно снизить сетевые задержки и обеспечить строгую целостность базы данных. Для реализации программной логики непосредственно внутри СУБД используются три основных инструмента: **Функции**, **Хранимые процедуры** и **Триггеры**.

Понимание того, как эти инструменты управляют транзакциями, работают с памятью и чем различаются в MySQL и PostgreSQL, критически важно для проектирования надежных систем.

---

## 1. Пользовательские функции (UDF) против хранимых процедур

Хотя оба инструмента группируют SQL-инструкции в именованные блоки, они служат разным целям. Главное различие между ними заключается в **управлении транзакциями**.

| Характеристика | Пользовательская функция (UDF) | Хранимая процедура |
| :--- | :--- | :--- |
| **Вызов** | Вызывается внутри запросов (например, `SELECT my_func(val)`) | Вызывается отдельно с помощью команды `CALL my_proc(val)` |
| **Возвращаемое значение** | Обязательно возвращает значение или таблицу | Не возвращает значение напрямую (использует `OUT`-параметры) |
| **Транзакции** | **Не может** выполнять `COMMIT` или `ROLLBACK` | **Может** управлять транзакциями (`COMMIT` / `ROLLBACK`) |
| **Основное назначение** | Чтение и преобразование данных внутри запросов | Выполнение комплексных сценариев записи и пакетной обработки |

### Пример управления транзакциями (Хранимая процедура)
Хранимые процедуры могут самостоятельно фиксировать или откатывать изменения прямо во время выполнения логики.

```sql
-- Синтаксис PostgreSQL 11+
CREATE PROCEDURE transfer_funds(sender INT, receiver INT, amount DECIMAL)
LANGUAGE plpgsql AS $$
BEGIN
    UPDATE accounts SET balance = balance - amount WHERE id = sender;
    UPDATE accounts SET balance = balance + amount WHERE id = receiver;
    
    -- Фиксируем транзакцию прямо внутри процедуры
    COMMIT;
EXCEPTION WHEN OTHERS THEN
    -- Откатываем изменения в случае любой ошибки
    ROLLBACK;
END;
$$;

-- Синтаксис MySQL
CREATE PROCEDURE transfer_funds(IN sender INT, IN receiver INT, IN amount DECIMAL)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
    END;

    START TRANSACTION;
    UPDATE accounts SET balance = balance - amount WHERE id = sender;
    UPDATE accounts SET balance = balance + amount WHERE id = receiver;
    COMMIT;
END;
```

## 2. Триггеры: Автоматизация бизнес-правил

**Триггер** — это объект базы данных, который автоматически запускает набор SQL-инструкций при возникновении определенного события (`INSERT`, `UPDATE` или `DELETE`) на таблице.

### Время срабатывания триггера
* **`BEFORE`**: Выполняется *до* того, как изменения будут физически записаны на диск. Часто используется для валидации или корректировки входящих данных.
* **`AFTER`**: Выполняется *после* записи изменений на диск. Используется для ведения логов, аудита или обновления связанных таблиц.
* **`INSTEAD OF`**: Используется на представлениях (views) для замены стандартных операций записи пользовательской логикой.

### Уровни выполнения: строчные и операторные триггеры
* **`FOR EACH ROW` (Строчный)**: Выполняется отдельно для каждой строки, измененной запросом. Если UPDATE обновляет 10 000 строк, триггер сработает 10 000 раз.
* **`FOR EACH STATEMENT` (Операторный)**: Выполняется один раз на весь SQL-запрос, независимо от количества измененных строк. Удобен для логирования событий или массовых проверок.

### Псевдозаписи `OLD` и `NEW`
Внутри триггеров доступны специальные переменные, отражающие состояние данных:
* **`NEW`**: Содержит новые значения строки (доступно при `INSERT` и `UPDATE`).
* **`OLD`**: Содержит исходные значения строки (доступно при `UPDATE` и `DELETE`).

## 3. MySQL против PostgreSQL: архитектурные и синтаксические различия

Архитектура выполнения триггеров и процедур в этих СУБД существенно отличается.

### 1. Архитектура триггеров: функции против инлайн-кода
* **PostgreSQL**: Требует двухэтапного описания. Сначала пишется триггерная функция, которая возвращает специальный тип `TRIGGER`. Затем эта функция привязывается к таблице через `CREATE TRIGGER`.
```sql
-- PostgreSQL: 1. Создаем триггерную функцию
CREATE FUNCTION log_salary_change() RETURNS TRIGGER AS $$
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit(emp_id, old_val, new_val)
        VALUES (OLD.id, OLD.salary, NEW.salary);
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- PostgreSQL: 2. Привязываем функцию к таблице
CREATE TRIGGER after_salary_update
AFTER UPDATE ON employees
FOR EACH ROW EXECUTE FUNCTION log_salary_change();
```

* **MySQL**: Позволяет писать логику триггера непосредственно внутри инструкции создания триггера.
```sql
-- MySQL: Определение триггера с инлайн-кодом
CREATE TRIGGER after_salary_update
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit(emp_id, old_val, new_val)
        VALUES (OLD.id, OLD.salary, NEW.salary);
    END IF;
END;
```

### 2. Поддержка языков программирования
* **MySQL**: Поддерживает только свой собственный проприетарный процедурный диалект SQL.
* **PostgreSQL**: Поддерживает несколько языков. Хотя по умолчанию используется `PL/pgSQL`, вы можете писать логику на `PL/Python`, `PL/Perl` или `PL/v8` (JavaScript).

> [!WARNING]
> **Падение производительности из-за триггеров!**
> Строчные триггеры (`FOR EACH ROW`) могут серьезно замедлить массовые операции. Если вы обновляете 1 миллион строк, строчный триггер заставит СУБД переключать контекст между SQL-движком и процедурным интерпретатором 1 миллион раз, превращая быстрый векторный запрос в медленный построчный цикл.

> [!TIP]
> **Ограничение транзакций в PostgreSQL:**
> Несмотря на то, что процедуры в PostgreSQL 11+ поддерживают `COMMIT`/`ROLLBACK`, они не смогут выполнить эти команды, если сама процедура была вызвана из внешнего активного транзакционного блока (например, внутри конструкции `BEGIN; CALL my_procedure();`).

## 4. Резюме и лучшие практики

1. **Функции — для расчетов**: Используйте функции (UDF) для вычислений и преобразований внутри запросов. Не пытайтесь изменять данные или управлять транзакциями внутри функций.
2. **Процедуры — для бизнес-логики**: Используйте хранимые процедуры для пакетных обновлений, оркестрации записей и ручного управления транзакциями.
3. **Делайте триггеры легковесными**: Применяйте триггеры только для критически важного аудита или поддержания целостности. Код триггера должен быть минимальным, чтобы не замедлять запись.
4. **Осторожнее с массовым импортом**: Отключайте или обходите триггеры во время импорта больших объемов данных или миграций, иначе производительность сервера может упасть до критических значений.
