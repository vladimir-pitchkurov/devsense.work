# Съхранени процедури, функции и тригери

Преместването на бизнес логиката по-близо до вашите данни може значително да намали мрежовата латентност и да гарантира строга цялост на данните. Когато пишете програмна логика, която се изпълнява директно в базата данни, използвате три основни конструкции: **Функции (Functions)**, **Съхранени процедури (Stored Procedures)** и **Тригери (Triggers)**.

Разбирането на това как тези елементи управляват транзакциите, достъпват паметта и се различават в MySQL и PostgreSQL, е от съществено значение за проектирането на надеждни бази данни.

---

## 1. Дефинирани от потребителя функции (UDFs) срещу съхранени процедури

Въпреки че и двете обединяват SQL оператори в групи, те служат за много различни цели. Най-важната разлика се състои в **контрола на транзакциите**.

| Характеристика | Потребителска функция (UDF) | Съхранена процедура |
| :--- | :--- | :--- |
| **Извикване** | Извиква се вградено в заявки (напр. `SELECT my_func(val)`) | Извиква се самостоятелно чрез `CALL my_proc(val)` |
| **Връщана стойност** | Трябва да върне единична стойност или таблица | Не връща стойност (използва `OUT` параметри вместо това) |
| **Транзакции** | **Не може** да изпълнява `COMMIT` или `ROLLBACK` | **Може** да изпълнява `COMMIT` или `ROLLBACK` |
| **Контекст на употреба** | Четене/Трансформиране на данни в заявки | Оркестриране на сложни групови записи и операции |

### Пример за контрол на транзакциите (съхранена процедура)
Съхранените процедури могат да управляват транзакциите нативно, позволявайки ви да потвърждавате (commit) или връщате (rollback) промени по средата на изпълнението.

```sql
-- PostgreSQL 11+ Syntax
CREATE PROCEDURE transfer_funds(sender INT, receiver INT, amount DECIMAL)
LANGUAGE plpgsql AS $$
BEGIN
    UPDATE accounts SET balance = balance - amount WHERE id = sender;
    UPDATE accounts SET balance = balance + amount WHERE id = receiver;
    
    -- Commit the transaction inside the procedure
    COMMIT;
EXCEPTION WHEN OTHERS THEN
    -- Rollback changes if anything fails
    ROLLBACK;
END;
$$;

-- MySQL Syntax
CREATE PROCEDURE transfer_funds(IN sender INT, IN receiver INT, IN amount DECIMAL)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
    END;

    START TRANSACTION;
    UPDATE accounts SET balance = balance - amount WHERE id = sender;
    UPDATE accounts SET balance = balance + amount WHERE id = receiver;
    COMMIT;
END;
```

## 2. Тригери: Автоматизиране на бизнес правила

**Тригерът (Trigger)** е обект в базата данни, който автоматично изпълнява определен набор от SQL оператори, когато върху таблица настъпи събитие (като `INSERT`, `UPDATE` или `DELETE`).

### Време за изпълнение на тригери (Trigger Execution Timing)
* **`BEFORE`**: Изпълнява се *преди* базата данни да запише промените на диска. Използва се за валидиране или модифициране на входящите стойности.
* **`AFTER`**: Изпълнява се *след* като базата данни запише промените на диска. Използва се за логване, одит или актуализиране на други таблици.
* **`INSTEAD OF`**: Използва се върху изгледи за пренаписване на стандартните действия за запис с потребителска логика.

### Тригери на ниво ред срещу тригери на ниво оператор
* **`FOR EACH ROW`**: Тригерът се изпълнява веднъж за всеки един ред, засегнат от заявката. Ако актуализацията засяга 10 000 реда, тригерът се изпълнява 10 000 пъти.
* **`FOR EACH STATEMENT`**: Тригерът се изпълнява точно веднъж за SQL оператор, независимо колко реда са модифицирани. Полезно за одит или групови проверки.

### Псевдозаписите `OLD` и `NEW`
Тригерите имат достъп до специални променливи, представящи състоянието на реда:
* **`NEW`**: Съдържа новите стойности на реда (достъпно при `INSERT` и `UPDATE`).
* **`OLD`**: Съдържа оригиналните стойности на реда (достъпно при `UPDATE` и `DELETE`).

## 3. MySQL срещу PostgreSQL: Синтактични и структурни разлики

Архитектурата за изпълнение на тригери и процедури се различава сериозно между тези две бази данни.

### 1. Архитектура на тригера: Функции срещу вграден код (Inline)
* **PostgreSQL**: Изисква процес от две стъпки. Първо, трябва да напишете тригерна функция, която връща специалния тип `TRIGGER`. Второ, свързвате тази функция с таблицата с помощта на `CREATE TRIGGER`.
```sql
-- PostgreSQL: 1. Create Trigger Function
CREATE FUNCTION log_salary_change() RETURNS TRIGGER AS $$
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit(emp_id, old_val, new_val)
        VALUES (OLD.id, OLD.salary, NEW.salary);
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- PostgreSQL: 2. Bind Function to Table
CREATE TRIGGER after_salary_update
AFTER UPDATE ON employees
FOR EACH ROW EXECUTE FUNCTION log_salary_change();
```

* **MySQL**: Позволява ви да напишете логиката на тригера директно (inline) вътре в дефиницията на тригера.
```sql
-- MySQL: Direct inline trigger definition
CREATE TRIGGER after_salary_update
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit(emp_id, old_val, new_val)
        VALUES (OLD.id, OLD.salary, NEW.salary);
    END IF;
END;
```

### 2. Поддръжка на езици
* **MySQL**: Поддържа само собственото си синтактично разширение на SQL.
* **PostgreSQL**: Поддържа множество езици. Докато `PL/pgSQL` е езикът по подразбиране, можете да пишете функции и тригери за бази данни на `PL/Python`, `PL/Perl` или `PL/v8` (JavaScript).

> [!WARNING]
> **Разход на ресурси при използване на тригери!**
> Тригерите на ниво ред (`FOR EACH ROW`) могат да причинят сериозно влошаване на производителността при масови актуализации. Ако актуализирате 1 милион реда, тригерът на ниво ред принуждава базата данни да превключва контекста (context-switch) между машината за изпълнение на SQL и процедурния интерпретатор 1 милион пъти, превръщайки бързата заявка, базирана на набори, в бавен цикъл ред по ред.

> [!TIP]
> **Транзакционно ограничение в PostgreSQL:**
> Въпреки че съхранените процедури в PostgreSQL 11+ поддържат транзакционни команди (`COMMIT`/`ROLLBACK`), те не могат да ги изпълнят, ако процедурата е извикана от вече активен транзакционен блок (напр. ако изпълните `BEGIN; CALL my_procedure();`).

## 4. Резюме и добри практики

1. **Функции за изчисления**: Използвайте потребителски функции (UDFs) за трансформации и изчисления в заявки. Не се опитвайте да променяте данни или да контролирате транзакции вътре в тях.
2. **Процедури за работни процеси**: Използвайте съхранени процедури за изпълнение на групови актуализации, оркестриране на сложни записи и управление на транзакции.
3. **Поддържайте тригерите леки**: Използвайте тригери само за критична целостта на данните, логване или одит. Ако се налага да ги използвате, поддържайте логиката им минимална, за да предотвратите затруднения при писането на данни.
4. **Внимавайте с масовите операции (Bulk Ops)**: Деактивирайте или заобикаляйте тригерите по време на масивен импорт на данни или миграции, за да избегнете срив в производителността на сървъра.
