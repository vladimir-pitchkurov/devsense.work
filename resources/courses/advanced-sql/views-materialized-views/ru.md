# Представления (Views) и материализованные представления (Materialized Views): Абстракция против Кэширования

При проектировании высокопроизводительных баз данных мы часто сталкиваемся с двумя взаимоисключающими проблемами:
1. **Сложность запросов**: Написание и поддержка длинных запросов с десятками соединений (JOIN).
2. **Время выполнения**: Выполнение тяжелых агрегатных расчетов (например, аналитических отчетов) над миллионами строк при каждой загрузке страницы.

В языке SQL для решения этих задач используются **Представления (Views)** и **Материализованные представления (Materialized Views)**. Несмотря на схожие названия, их модели выполнения абсолютно различны: одно является логической оберткой (абстракцией), а другое — физической таблицей-кэшем.

---

## 1. Обычные (виртуальные) представления (Standard Views)

Обычное **представление (View)** — это сохраненный в базе данных SQL-запрос. Это виртуальная таблица, которая физически не хранит данные на диске. Когда вы обращаетесь к представлению, СУБД объединяет код представления с основным запросом и выполняет их вместе «на лету».

### Базовый синтаксис
```sql
-- MySQL и PostgreSQL
CREATE VIEW active_customer_summary AS
SELECT c.id, c.name, COUNT(o.id) AS total_orders
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE c.status = 'active'
GROUP BY c.id, c.name;
```

### Обновляемые представления (Updatable Views)
Можно ли выполнять операции `INSERT`, `UPDATE` или `DELETE` над представлениями? Да, но при соблюдении строгих условий. Представление является обновляемым только в том случае, если СУБД может однозначно сопоставить операцию записи с конкретными строками одной физической таблицы.
* **Правила**: Представление не должно содержать:
  - Агрегатные функции (`SUM`, `COUNT`, `AVG`).
  - Группировки `GROUP BY`, `HAVING` или ключевое слово `DISTINCT`.
  - Операторы множеств (`UNION`, `INTERSECT`, `EXCEPT`).
  - Оконные функции.

> [!WARNING]
> **Опция `WITH CHECK OPTION`**
> При изменении данных через представление вы можете случайно обновить строку так, что она перестанет соответствовать фильтрам самого представления и «исчезнет» из него!
> ```sql
> CREATE VIEW premium_customers AS 
> SELECT * FROM customers WHERE balance > 1000;
> ```
> Если вы выполните `UPDATE premium_customers SET balance = 500 WHERE id = 1`, запрос выполнится успешно, но клиент пропадет из представления. Чтобы избежать этого, добавьте `WITH CHECK OPTION` в конец определения представления. Это заставит СУБД отклонять любые `INSERT` и `UPDATE`, которые нарушают условие `WHERE` представления.

## 2. Материализованные представления (PostgreSQL)

В отличие от обычных представлений, **материализованное представление (Materialized View)** физически сохраняет результаты запроса на диск, работая как обычная таблица. Чтение данных из него происходит мгновенно, поскольку СУБД не нужно выполнять повторные соединения и агрегацию. Однако данные в нем со временем устаревают.

### Синтаксис и обновление данных
```sql
-- Только в PostgreSQL
CREATE MATERIALIZED VIEW monthly_revenue_report AS
SELECT extract(year from order_date) as year, extract(month from order_date) as month, SUM(total_amount) as revenue
FROM orders
GROUP BY 1, 2;
```

Для актуализации данных необходимо вручную запускать обновление:
```sql
REFRESH MATERIALIZED VIEW monthly_revenue_report;
```

### Неблокирующее обновление: `CONCURRENTLY`
По умолчанию выполнение `REFRESH MATERIALIZED VIEW` накладывает эксклюзивную блокировку на представление, закрывая операции чтения (`SELECT`) для других пользователей до завершения процесса. Чтобы обновить данные без блокировки пользователей, используйте опцию `CONCURRENTLY`.

```sql
-- Только в PostgreSQL: Обновление без блокировки чтения
CREATE UNIQUE INDEX idx_monthly_rev ON monthly_revenue_report (year, month);
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue_report;
```
* **Требование**: Перед использованием опции `CONCURRENTLY` необходимо создать хотя бы один уникальный индекс по полям материализованного представления.

## 3. Эмуляция материализованных представлений в MySQL

MySQL **не поддерживает** материализованные представления нативно. Если вам нужен аналогичный функционал в MySQL, придется эмулировать его самостоятельно.

### Вариант 1: Обычная таблица + Планировщик событий (Event Scheduler)
Вы можете создать обычную таблицу, которая будет играть роль кэша, и настроить периодическое событие для ее обновления.

```sql
-- Только в MySQL
-- 1. Создаем физическую таблицу-кэш
CREATE TABLE monthly_revenue_report_cache AS
SELECT YEAR(order_date) as year, MONTH(order_date) as month, SUM(total_amount) as revenue
FROM orders GROUP BY 1, 2;

-- 2. Настраиваем ежечасное обновление таблицы
CREATE EVENT refresh_revenue_report
ON SCHEDULE EVERY 1 HOUR
DO
  BEGIN
    TRUNCATE TABLE monthly_revenue_report_cache;
    INSERT INTO monthly_revenue_report_cache
    SELECT YEAR(order_date) as year, MONTH(order_date) as month, SUM(total_amount) as revenue
    FROM orders GROUP BY 1, 2;
  END;
```

### Вариант 2: Использование триггеров
Если вам нужно обновлять материализованное представление в реальном времени, можно написать триггеры `AFTER INSERT/UPDATE/DELETE` на базовых таблицах, которые будут инкрементально вносить изменения в таблицу-кэш.

## 4. Сравнение возможностей: MySQL против PostgreSQL

| Функция | MySQL 8.0 | PostgreSQL |
| :--- | :--- | :--- |
| Обычные виртуальные представления | Поддерживается | Поддерживается |
| Обновляемые представления | Поддерживается (с ограничениями) | Поддерживается (с ограничениями) |
| Нативные материализованные представления | *Не поддерживается* | Поддерживается |
| Неблокирующее обновление (Concurrently) | *Не поддерживается* | Поддерживается (через `CONCURRENTLY`) |
| Безопасность (DEFINER / INVOKER) | Поддерживается | Поддерживается |

> [!TIP]
> **Совет по безопасности: INVOKER против DEFINER**
> По умолчанию представления выполняются с правами пользователя, который их создал (`DEFINER`). Это позволяет безопасно предоставлять пользователям доступ к определенной части данных (например, исключая колонки с паролями или зарплатой) без выдачи им прав на чтение всей исходной таблицы.

---

## 5. Резюме и лучшие практики

1. **Используйте обычные представления для абстракции**: Они идеальны для упрощения логики запросов и разграничения прав доступа.
2. **Используйте материализованные представления для кэширования**: Физически кэшируйте тяжелые отчеты в высоконагруженных системах.
3. **Обновляйте конкурентно**: В продакшене на PostgreSQL всегда создавайте уникальный индекс для материализованного представления, чтобы обновлять его с опцией `CONCURRENTLY`.
4. **В MySQL используйте триггеры или планировщик**: Создавайте кэш-таблицы и наполняйте их по расписанию для симуляции материализованных представлений.
