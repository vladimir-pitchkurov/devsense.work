# Изгледи и материализирани изгледи: Абстракция срещу кеширане

При проектирането на високопроизводителни бази данни често се сблъскваме с два конкурентни проблема:
1. **Сложност на заявките**: Писане и поддръжка на дълги, вложени заявки, които обхващат десетки съединения.
2. **Латентност на изпълнението**: Стартиране на тежки агрегиращи заявки (като отчети за продажби) върху милиони редове при всяко зареждане на страница.

SQL адресира тези предизвикателства с **Изгледи (Views)** и **Материализирани изгледи (Materialized Views)**. Въпреки че звучат сходно, техните модели на изпълнение са напълно различни: единият е логическа връзка (абстракция), а другият е физически кеш на таблица.

---

## 1. Стандартни (виртуални) изгледи

Стандартният **Изглед (View)** е записана дефиниция на заявка. Той е виртуална таблица — не съхранява никакви физически данни на диска. Когато изпращате заявка към изглед, сървърът на базата данни обединява неговата дефиниция с основната заявка и ги изпълнява заедно.

### Основен синтаксис
```sql
-- MySQL & PostgreSQL
CREATE VIEW active_customer_summary AS
SELECT c.id, c.name, COUNT(o.id) AS total_orders
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE c.status = 'active'
GROUP BY c.id, c.name;
```

### Обновяеми изгледи (Updatable Views)
Можете ли да изпълнявате оператори `INSERT`, `UPDATE` или `DELETE` върху изглед? Да, при строги условия. Един изглед е обновяем само ако сървърът на базата данни може да съпостави операциите по запис директно обратно към единична лежаща отдолу физическа таблица.
* **Правила**: Изгледът не трябва да съдържа:
  - Агрегатни функции (`SUM`, `COUNT`, `AVG`).
  - Клаузи `GROUP BY`, `HAVING` или `DISTINCT`.
  - Оператори за множества (`UNION`, `INTERSECT`, `EXCEPT`).
  - Прозоречни функции.

> [!WARNING]
> **Клаузата `WITH CHECK OPTION`**
> Когато актуализирате данни чрез изглед, можете случайно да запишете данни, които карат реда да изчезне от самия изглед!
> ```sql
> CREATE VIEW premium_customers AS 
> SELECT * FROM customers WHERE balance > 1000;
> ```
> Ако изпълните `UPDATE premium_customers SET balance = 500 WHERE id = 1`, актуализацията ще успее, но клиентът ще изчезне от изгледа. За да предотвратите това, добавете `WITH CHECK OPTION` към дефиницията на изгледа. Това принуждава базата данни да отхвърля всякакви вмъквания или актуализации, които нарушават клаузата `WHERE` на изгледа.

## 2. Материализирани изгледи (PostgreSQL)

За разлика от стандартните изгледи, **Материализираният изглед (Materialized View)** физически съхранява резултатите от заявката на диска, държейки се като обикновена таблица. Заявките към материализиран изглед са изключително бързи, тъй като той заобикаля съединенията и изчисленията за агрегиране. Данните обаче могат да остареят.

### Синтаксис и обновяване
```sql
-- PostgreSQL Only
CREATE MATERIALIZED VIEW monthly_revenue_report AS
SELECT extract(year from order_date) as year, extract(month from order_date) as month, SUM(total_amount) as revenue
FROM orders
GROUP BY 1, 2;
```

За да актуализирате данните, трябва ръчно да задействате обновяване:
```sql
REFRESH MATERIALIZED VIEW monthly_revenue_report;
```

### Неблокиращи актуализации: `CONCURRENTLY`
По подразбиране `REFRESH MATERIALIZED VIEW` поставя изключително заключване (exclusive lock) върху изгледа, блокирайки всички операции за четене (`SELECT`), докато обновяването приключи. За да актуализирате изгледа, без да блокирате потребителите си, използвайте опцията `CONCURRENTLY`.

```sql
-- PostgreSQL Only: Non-blocking refresh
CREATE UNIQUE INDEX idx_monthly_rev ON monthly_revenue_report (year, month);
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue_report;
```
* **Изискване**: Трябва да създадете уникален индекс върху една или повече колони на материализирания изглед, преди да можете да използвате клаузата `CONCURRENTLY`.

## 3. Заобиколни начини в MySQL за материализирани изгледи

MySQL **не** поддържа нативно материализирани изгледи. Ако се нуждаете от тази функционалност в MySQL, трябва да я симулирате с помощта на един от двата обичайни заобиколни начина.

### Заобиколен начин 1: Обикновена таблица + Планировчик на събития (Event Scheduler)
Можете да създадете нормална таблица, която да действа като ваш кеш, и да напишете планирано събитие (event) в базата данни за периодичното ѝ обновяване.

```sql
-- MySQL Only
-- 1. Create the physical table
CREATE TABLE monthly_revenue_report_cache AS
SELECT YEAR(order_date) as year, MONTH(order_date) as month, SUM(total_amount) as revenue
FROM orders GROUP BY 1, 2;

-- 2. Create an event to refresh the table every hour
CREATE EVENT refresh_revenue_report
ON SCHEDULE EVERY 1 HOUR
DO
  BEGIN
    TRUNCATE TABLE monthly_revenue_report_cache;
    INSERT INTO monthly_revenue_report_cache
    SELECT YEAR(order_date) as year, MONTH(order_date) as month, SUM(total_amount) as revenue
    FROM orders GROUP BY 1, 2;
  END;
```

### Заобиколен начин 2: Тригери в базата данни (Database Triggers)
Ако се нуждаете от материализирани изгледи в реално време в MySQL, можете да напишете тригери `AFTER INSERT/UPDATE/DELETE` върху изходната таблица, които инкрементално да актуализират таблицата с кешираните резюмета.

## 4. Сравнение на функционалностите: MySQL срещу PostgreSQL

| Функционалност | MySQL 8.0 | PostgreSQL |
| :--- | :--- | :--- |
| Стандартни виртуални изгледи | Нативно поддържани | Нативно поддържани |
| Обновяеми изгледи | Поддържани (с ограничения) | Поддържани (с ограничения) |
| Нативни материализирани изгледи | *Не се поддържат* | Нативно поддържани |
| Едновременно/неблокиращо обновяване | *Не се поддържа* | Нативно поддържано (чрез `CONCURRENTLY`) |
| Сигурност на изгледа (DEFINER/INVOKER) | Нативно поддържана | Нативно поддържана |

> [!TIP]
> **Съвет за сигурност: INVOKER срещу DEFINER**
> По подразбиране стандартните изгледи в MySQL и PostgreSQL се изпълняват с привилегиите на потребителя, който е *създал* изгледа (`DEFINER`). Това е мощна функционалност, която ви позволява да предоставите на потребителите достъп до конкретни подмножества от данни в таблица (като например изключване на колона за парола), без да им давате разрешения за четене на цялата лежаща отдолу таблица.

---

## 5. Резюме и добри практики

1. **Използвайте стандартни изгледи за абстракция**: Стандартните изгледи са отлични за опростяване на сложни заявки и внедряване на роли за сигурност в базата данни.
2. **Използвайте материализирани изгледи за кеширане**: За тежки агрегации в среди с високо натоварване на четене, кеширайте данните физически.
3. **Винаги обновявайте едновременно (concurrently)**: В производствени среди на PostgreSQL винаги създавайте уникален индекс върху вашите материализирани изгледи, за да можете да ги обновявате без блокиране (concurrently).
4. **Използвайте планировчик или тригери в MySQL**: Ако използвате MySQL, проектирайте кеш таблица с помощта на събития (events) или кеширане на ниво приложение, за да симулирате материализирани изгледи.
