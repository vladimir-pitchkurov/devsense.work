# Представлення та матеріалізовані представлення: абстракція проти кешування

При проектуванні високопродуктивних баз даних ми часто стикаємося з двома взаємовиключними проблемами:
1. **Складність запитів**: написання та підтримка довгих, вкладених запитів, що охоплюють десятки об'єднань (joins).
2. **Затримка виконання**: виконання важких агрегатних запитів (наприклад, звітів з продажів) на мільйонах рядків при кожному завантаженні сторінки.

SQL вирішує ці проблеми за допомогою **представлень (Views)** та **матеріалізованих представлень (Materialized Views)**. Хоча їхні назви схожі, моделі їхнього виконання абсолютно різні: перше є логічним ярликом (абстракцією), а друге — фізичним кешем таблиці.

---

## 1. Стандартні (віртуальні) представлення

Стандартне **представлення (View)** — це збережене визначення запиту. Воно є віртуальною таблицею і не зберігає жодних фізичних даних на диску. Коли ви робите запит до представлення, рушій бази даних об'єднує визначення запиту представлення з основним запитом та виконує їх разом.

### Базовий синтаксис
```sql
-- MySQL & PostgreSQL
CREATE VIEW active_customer_summary AS
SELECT c.id, c.name, COUNT(o.id) AS total_orders
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE c.status = 'active'
GROUP BY c.id, c.name;
```

### Оновлювані представлення
Чи можна виконувати оператори `INSERT`, `UPDATE` або `DELETE` над представленням? Так, за певних суворих умов. Представлення є оновлюваним лише тоді, коли рушій бази даних може безпосередньо відобразити операції запису на одну базову фізичну таблицю.
* **Правила**: представлення не повинно містити:
  - агрегатних функцій (`SUM`, `COUNT`, `AVG`).
  - пропозицій `GROUP BY`, `HAVING` або `DISTINCT`.
  - операторів множин (`UNION`, `INTERSECT`, `EXCEPT`).
  - віконних функцій.

> [!WARNING]
> **Пропозиція `WITH CHECK OPTION`**
> При оновленні даних через представлення ви можете випадково записати такі дані, через які рядок зникне з самого представлення!
> ```sql
> CREATE VIEW premium_customers AS 
> SELECT * FROM customers WHERE balance > 1000;
> ```
> Якщо ви виконаєте `UPDATE premium_customers SET balance = 500 WHERE id = 1`, оновлення пройде успішно, але клієнт зникне з представлення. Щоб запобігти цьому, додайте `WITH CHECK OPTION` до визначення представлення. Це змусить базу даних відхиляти будь-які операції вставки або оновлення, які порушують умову `WHERE` представлення.

## 2. Матеріалізовані представлення (PostgreSQL)

На відміну від стандартних представлень, **матеріалізоване представлення (Materialized View)** фізично зберігає результати запиту на диску, поводячись як звичайна таблиця. Запити до матеріалізованого представлення виконуються надзвичайно швидко, оскільки вони не потребують обчислення об'єднань та агрегацій. Проте дані в ньому можуть застарівати.

### Синтаксис та оновлення
```sql
-- Лише для PostgreSQL
CREATE MATERIALIZED VIEW monthly_revenue_report AS
SELECT extract(year from order_date) as year, extract(month from order_date) as month, SUM(total_amount) as revenue
FROM orders
GROUP BY 1, 2;
```

Щоб оновити дані, необхідно вручну запустити процес оновлення:
```sql
REFRESH MATERIALIZED VIEW monthly_revenue_report;
```

### Неблокуючі оновлення: `CONCURRENTLY`
За замовчуванням `REFRESH MATERIALIZED VIEW` накладає ексклюзивне блокування на представлення, блокуючи всі операції читання (`SELECT`), доки оновлення не завершиться. Щоб оновити представлення без блокування користувачів, використовуйте опцію `CONCURRENTLY`.

```sql
-- Лише для PostgreSQL: Неблокуюче оновлення
CREATE UNIQUE INDEX idx_monthly_rev ON monthly_revenue_report (year, month);
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue_report;
```
* **Вимога**: перед використанням пропозиції `CONCURRENTLY` ви повинні створити унікальний індекс для одного або кількох стовпців матеріалізованого представлення.

## 3. Обхідні шляхи для матеріалізованих представлень у MySQL

MySQL **не** підтримує матеріалізовані представлення нативно. Якщо вам потрібна така функціональність у MySQL, вам доведеться симулювати її за допомогою одного з двох поширених методів.

### Спосіб 1: Звичайна таблиця + Планувальник подій (Event Scheduler)
Ви можете створити звичайну таблицю, яка буде виконувати роль кешу, і написати заплановану подію бази даних для її періодичного оновлення.

```sql
-- Лише для MySQL
-- 1. Створення фізичної таблиці
CREATE TABLE monthly_revenue_report_cache AS
SELECT YEAR(order_date) as year, MONTH(order_date) as month, SUM(total_amount) as revenue
FROM orders GROUP BY 1, 2;

-- 2. Створення події для оновлення таблиці кожну годину
CREATE EVENT refresh_revenue_report
ON SCHEDULE EVERY 1 HOUR
DO
  BEGIN
    TRUNCATE TABLE monthly_revenue_report_cache;
    INSERT INTO monthly_revenue_report_cache
    SELECT YEAR(order_date) as year, MONTH(order_date) as month, SUM(total_amount) as revenue
    FROM orders GROUP BY 1, 2;
  END;
```

### Спосіб 2: Тригери бази даних
Якщо вам потрібні матеріалізовані представлення в режимі реального часу в MySQL, ви можете створити тригери `AFTER INSERT/UPDATE/DELETE` на вихідній таблиці, які будуть інкрементно оновлювати таблицю кешу підсумків.

## 4. Порівняння можливостей: MySQL проти PostgreSQL

| Можливість | MySQL 8.0 | PostgreSQL |
| :--- | :--- | :--- |
| Стандартні віртуальні представлення | Підтримується нативно | Підтримується нативно |
| Оновлювані представлення | Підтримується (з обмеженнями) | Підтримується (з обмеженнями) |
| Нативні матеріалізовані представлення | *Не підтримується* | Підтримується нативно |
| Паралельне/неблокуюче оновлення | *Не підтримується* | Підтримується нативно (через `CONCURRENTLY`) |
| Безпека представлення (DEFINER/INVOKER) | Підтримується нативно | Підтримується нативно |

> [!TIP]
> **Порада щодо безпеки: INVOKER проти DEFINER**
> За замовчуванням стандартні представлення в MySQL та PostgreSQL виконуються з привілеями користувача, який *створив* це представлення (`DEFINER`). Це потужна функція, яка дозволяє надавати користувачам доступ до конкретних підмножин даних у таблиці (наприклад, виключаючи стовпець із паролем) без надання їм прав на читання всієї вихідної таблиці.

---

## 5. Підсумок та найкращі практики

1. **Використовуйте стандартні представлення для абстракції**: стандартні представлення чудово підходять для спрощення складних запитів та реалізації ролей безпеки бази даних.
2. **Використовуйте матеріалізовані представлення для кешування**: для важких агрегацій у системах із переважанням операцій читання кешуйте дані фізично.
3. **Завжди оновлюйте паралельно**: у продакшен-середовищах PostgreSQL завжди створюйте унікальний індекс на ваших матеріалізованих представленнях, щоб мати можливість оновлювати їх паралельно.
4. **Використовуйте планувальник або тригери в MySQL**: при використанні MySQL проектуйте таблицю кешу за допомогою подій або кешування на рівні додатка для симуляції матеріалізованих представлень.
