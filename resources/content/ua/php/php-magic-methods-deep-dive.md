# Магічні методи в PHP: під капотом динамічного ООП

Рівень: Middle  
Версія PHP: PHP 7.0+ (Функції виділені маркерами версій)

Кожен PHP-розробник використовував `__construct()`, але мало хто усвідомлює, що виклик динамічних магічних методів, таких як `__get()` або `__call()`, може сповільнити доступ до властивостей до 300%, вимкнути автодоповнення в IDE та спричинити приховані баги, які обходять статичні аналізатори, такі як PHPStan. Магічні методи — це вбудовані в PHP точки розширення для динамічної поведінки, але при неправильному використанні вони перетворюють чистий код на кошмар для відлагодження.

---

## 1. Життєвий цикл об'єкта: `__construct` та `__destruct`

### __construct()
* **Суть**: Метод `__construct` автоматично викликається при створенні нового екземпляра класу, виступаючи точкою входу для ініціалізації об'єкта. Починаючи з **PHP 8.0+**, цей метод підтримує спрощене оголошення властивостей у конструкторі (Constructor Property Promotion) для суттєвого зменшення кількості шаблонного коду.
* **Чому це важливо**: Без конструктора об'єкти ініціалізуються в порожньому стані, змушуючи розробників використовувати сеттери або змінювати публічні властивості, що створює ризик неповної ініціалізації. Спрощене оголошення властивостей у конструкторі спрощує код, об'єднуючи оголошення властивості, визначення типу параметра та присвоєння в один сигнатурний рядок.
* **Приклад**:
  ```php
  // app/DTO/UserSession.php
  namespace App\DTO;

  class UserSession 
  {
      private string $sessionId;

      // PHP 8.0+ Constructor Property Promotion
      public function __construct(
          public string $username,
          protected string $role = 'guest',
          private bool $isActive = true
      ) {
          $this->sessionId = bin2hex(random_bytes(16));
      }

      public function getSessionId(): string 
      {
          return $this->sessionId;
      }
  }
  ```
* **Наслідок**: Спрощене оголошення властивостей у конструкторі усуває шаблонний код і гарантує, що класи завжди перебувають у валідному типізованому стані з моменту створення екземпляра. Однак це може призвести до роздутих сигнатур конструктора, якщо впроваджується занадто багато залежностей, що маскує порушення принципу єдиної відповідальності (Single Responsibility Principle).

### __destruct()
* **Суть**: Метод `__destruct` викликається автоматично, коли на об'єкт більше немає посилань, або під час завершення роботи скрипту.
* **Чому це важливо**: Він забезпечує надійну точку підключення для вивільнення ресурсів, таких як закриття відкритих з'єднань із базою даних, запис буферів логів або зняття блокувань на системному рівні.
* **Приклад**:
  ```php
  // app/Services/FileLogger.php
  namespace App\Services;

  class FileLogger 
  {
      private mixed $handle;

      public function __construct(string $filePath) 
      {
          $this->handle = fopen($filePath, 'a');
      }

      public function log(string $message): void 
      {
          fwrite($this->handle, $message . PHP_EOL);
      }

      public function __destruct() 
      {
          if (is_resource($this->handle)) {
              fclose($this->handle);
          }
      }
  }
  ```
* **Наслідок**: Деструктори автоматизують очищення ресурсів. Однак, оскільки PHP використовує підрахунок посилань та циклічний збирач сміття, точний час знищення об'єкта є недетермінованим. Якщо ваш додаток покладається на деструктори для звільнення критичних, чутливих до часу системних блокувань, він може зіткнутися зі станом гонитви (race conditions).

## 2. Динамічні аксесоари (перевантаження властивостей): `__get`, `__set`, `__isset` та `__unset`

* **Суть**: Ці чотири магічні методи перехоплюють операції читання, запису, перевірки існування (`isset()`) та видалення (`unset()`) для властивостей, які є невизначеними або недоступними (наприклад, private/protected) з поточної області видимості.
* **Чому це важливо**: Вони дозволяють класам виступати в ролі гнучких, динамічних контейнерів даних. ORM фреймворків (такі як Eloquent у Laravel) покладаються на перевантаження властивостей для динамічного відображення стовпців бази даних на властивості об'єкта без необхідності жорстко прописувати кожен стовпець як властивість класу.
* **Приклад**:
  ```php
  // app/Models/SettingsBag.php
  namespace App\Models;

  class SettingsBag 
  {
      private array $settings = [];

      public function __construct(array $defaultSettings = []) 
      {
          $this->settings = $defaultSettings;
      }

      // Triggered when reading an inaccessible or non-existent property
      public function __get(string $name): mixed 
      {
          return $this->settings[$name] ?? null;
      }

      // Triggered when writing to an inaccessible or non-existent property
      public function __set(string $name, mixed $value): void 
      {
          $this->settings[$name] = $value;
      }

      // Triggered when calling isset() or empty() on inaccessible properties
      public function __isset(string $name): bool 
      {
          return isset($this->settings[$name]);
      }

      // Triggered when calling unset() on inaccessible properties
      public function __unset(string $name): void 
      {
          unset($this->settings[$name]);
      }
  }
  ```
* **Наслідок**: Перевантаження властивостей забезпечує надзвичайну гнучкість, що дозволяє швидко створювати прототипи. Однак це руйнує статичний аналіз. IDE не можуть автодоповнювати такі властивості, а інструменти на кшталт PHPStan повідомлятимуть про них як про помилки, якщо ви вручну не задокументуєте їх за допомогою анотацій PHPDoc `@property` на рівні класу.

> [!WARNING]
> **Сувора валідація сигнатур (PHP 8.0+)**
> До версії PHP 8.0 сигнатури магічних методів перевірялися не суворо. Починаючи з **PHP 8.0+**, PHP вимагає суворої перевірки типів для магічних методів, якщо ви вказуєте типи. Наприклад, оголошення `__isset(string $name): bool` проходить перевірку, і повернення значення, що не є bool, або невідповідність типу параметра викличе фатальну помилку (Fatal Error) на етапі компіляції.

## 3. Динамічний виклик методів (перевантаження методів): `__call` та `__callStatic`

* **Суть**: `__call` перехоплює виклики невизначених або недоступних методів об'єкта, тоді як `__callStatic` перехоплює виклики невизначених або недоступних статичних методів.
* **Чому це важливо**: Ці методи спрощують реалізацію патернів проектування «проксі» (замісник), «декоратор» та архітектури фасадів. Перехоплюючи імена методів та аргументи під час виконання, ви можете перенаправляти виклики до внутрішніх сервісів, динамічно логувати виконання або створювати зручні інтерфейси на кшталт fluent API.
* **Приклад**:
  ```php
  // app/Services/MetricsCollector.php
  namespace App\Services;

  class MetricsCollector 
  {
      public function __construct(
          private object $service
      ) {}

      // Intercepts instance method calls
      public function __call(string $name, array $arguments): mixed 
      {
          if (!method_exists($this->service, $name)) {
              throw new \BadMethodCallException("Method {$name} does not exist.");
          }

          $start = microtime(true);
          $result = call_user_func_array([$this->service, $name], $arguments);
          $duration = microtime(true) - $start;

          // Log performance metrics
          error_log("Service method {$name} took " . round($duration, 4) . "s to execute.");

          return $result;
      }

      // Intercepts static method calls
      public static function __callStatic(string $name, array $arguments): mixed 
      {
          return "Static method '{$name}' called with arguments: " . json_encode($arguments);
      }
  }
  ```
* **Наслідок**: Перевантаження методів дозволяє створювати елегантні та чисті архітектурні абстракції (наприклад, фасади в Laravel). Однак відлагодження стеків викликів ускладнюється, оскільки трасування стеку перенаправляється через магічний обробник. Крім того, інструменти статичного аналізу вимагають явних тегів PHPDoc `@method` для запобігання помилкам.

## 4. Перетворення та поведінка об'єктів: `__toString`, `__invoke` та `__clone`

* **Суть**: Ці методи керують тим, як об'єкти взаємодіють із базовими конструкціями мови PHP: приведенням до рядка, синтаксисом виклику функції та клонуванням.
* **Чому це важливо**:
  - `__toString()` дозволяє об'єктам представляти себе у вигляді рядків (наприклад, для відображення Value Object, такого як адреса Email або представлення валюти).
  - `__invoke()` дозволяє викликати об'єкт так, ніби він є функцією, полегшуючи реалізацію патерну single-action (поодинока дія).
  - `__clone()` перехоплює клонування об'єкта, дозволяючи виконувати глибоке копіювання вкладених ресурсів замість створення поверхневих посилань.
* **Приклад**:
  ```php
  // app/ValueObjects/EmailAddress.php
  namespace App\ValueObjects;

  class EmailAddress 
  {
      public function __construct(
          public string $email
      ) {
          if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
              throw new \InvalidArgumentException("Invalid email format.");
          }
      }

      // String representation - makes this class Stringable
      public function __toString(): string 
      {
          return $this->email;
      }
  }

  // app/Services/JobRunner.php
  namespace App\Services;

  class JobRunner 
  {
      public \DateTimeImmutable $lastRun;

      public function __construct() 
      {
          $this->lastRun = new \DateTimeImmutable();
      }

      // Makes the class callable as a function
      public function __invoke(string $taskName): string 
      {
          return "Executing task '{$taskName}' at {$this->lastRun->format('Y-m-d')}";
      }

      // Defines custom cloning behavior for deep copy
      public function __clone() 
      {
          // Clone internal object references to prevent shared state
          $this->lastRun = new \DateTimeImmutable();
      }
  }
  ```
* **Наслідок**:
  - **Неявна реалізація інтерфейсу**: Починаючи з **PHP 8.0+**, будь-який клас, який реалізує `__toString()`, автоматично реалізує вбудований інтерфейс `Stringable`, що дозволяє використовувати підказку типу `string|\Stringable`.
  - **Функціональні патерни**: Реалізація `__invoke` дозволяє передавати об'єкти безпосередньо туди, де потрібні аргументи типу `callable`.
  - **Баги з посиланнями**: Стандартні операції `clone` виконують поверхневе копіювання. Якщо об'єкт містить вкладені об'єкти і ви не напишете власний обробник `__clone`, зміна властивостей клонованого об'єкта призведе до випадкової зміни вкладених об'єктів оригінального об'єкта.

## 5. Серіалізація об'єктів: Еволюція збереження стану

* **Суть**: Магічні методи серіалізації керують тим, як об'єкт перетворюється на лінійний рядок за допомогою `serialize()` і як відновлюється його стан через `unserialize()`.
* **Чому це важливо**: Певні властивості, такі як необроблені з'єднання з базою даних, дескриптори ресурсів HTTP-клієнтів або конфіденційні облікові дані, не можуть або не повинні серіалізуватися. Налаштовуючи серіалізацію, ви повністю контролюєте, які саме змінні зберігаються і як відновлюються зв'язки після десеріалізації.
* **Приклад**:
  ```php
  // app/Services/SearchClient.php
  namespace App\Services;

  class SearchClient 
  {
      private mixed $connection; // Resource handle that cannot be serialized

      public function __construct(
          private string $host,
          private int $port,
          public array $options = []
      ) {
          $this->connect();
      }

      private function connect(): void 
      {
          // Simulate a network connection initialization
          $this->connection = "Socket connected to {$this->host}:{$this->port}";
      }

      // MODERN APPROACH: Available since PHP 7.4+
      public function __serialize(): array 
      {
          // Return an array representing the object state
          return [
              'host' => $this->host,
              'port' => $this->port,
              'options' => $this->options,
          ];
      }

      public function __unserialize(array $data): void 
      {
          $this->host = $data['host'];
          $this->port = $data['port'];
          $this->options = $data['options'];

          // Re-establish connection automatically
          $this->connect();
      }

      /* 
       * Legacy Sleep & Wakeup (Pre-PHP 7.4)
       * Note: If __serialize() and __unserialize() exist, 
       * PHP 7.4+ will ignore __sleep() and __wakeup() entirely.
       */
      public function __sleep(): array 
      {
          // Must return an array of property names
          return ['host', 'port', 'options'];
      }

      public function __wakeup(): void 
      {
          $this->connect();
      }
  }
  ```
* **Наслідок**:
  - **Чому виграють __serialize/__unserialize (PHP 7.4+)**: Застарілий метод `__sleep` повертає масив імен властивостей, що обмежує можливості, оскільки ви не можете змінювати чи фільтрувати структури даних «на льоту». Сучасний `__serialize` повертає довільний асоціативний масив. Це дозволяє форматувати дані, виключати глибоко вкладені масиви або серіалізувати власні динамічні значення без оголошення їх як властивостей класу.
  - **Пріоритет**: Якщо в класі присутні як застарілі, так і сучасні методи серіалізації, PHP 7.4+ виконає сучасні методи `__serialize` та `__unserialize`, повністю ігноруючи `__sleep` та `__wakeup`.

## 6. Архітектурні компроміси та обмеження

Хоча магічні методи дозволяють створювати елегантний і чистий синтаксис, вони несуть із собою значні витрати в реальних проектах. Розробники повинні зважити ці компроміси перед їх використанням.

### 1. Зниження продуктивності
Магічні методи розпізнаються під час виконання і не можуть бути ефективно оптимізовані рушієм OPcache в PHP. Прямий доступ до публічної властивості відбувається набагато швидше, ніж маршрутизація через `__get` та `__set`. Виклик `__call` створює додаткові накладні витрати через пакування аргументів у масив та динамічну маршрутизацію виконання.

| Операція | Відносна швидкість | Вплив на великі цикли |
| :--- | :--- | :--- |
| Прямий доступ до властивості | **1.0x (Найшвидше)** | Незначний |
| Магічні `__get` / `__set` | **У 3.5 - 4.0 рази повільніше** | Відчутне навантаження на CPU |
| Прямий виклик методу | **1.0x (Найшвидше)** | Незначний |
| Магічний `__call` | **У 2.5 - 3.0 рази повільніше** | Високі накладні витрати CPU |

### 2. Статичний аналіз та автодоповнення в IDE
Сучасна розробка на PHP значною мірою спирається на статичний аналіз (PHPStan, Psalm) для виявлення багів ще до того, як код потрапить у продакшн. Оскільки магічні методи приховують оголошення властивостей та сигнатури методів, ці інструменти не можуть перевірити правильність коду. Без детальних тегів PHPDoc `@property` та `@method` ви втрачаєте автодоповнення, інструменти рефакторингу та типізацію.

### 3. Ризики безпеки (впровадження об'єктів)
Десеріалізація ненадійних даних користувача за допомогою `unserialize()` є небезпечною вразливістю в PHP. Коли PHP створює екземпляр об'єкта через `unserialize`, він викликає `__wakeup` або `__unserialize`. Зловмисники можуть створювати спеціальні серіалізовані дані (так звані POP-ланцюжки), які використовують код всередині цих магічних методів для виконання довільних системних команд (Remote Code Execution — віддалене виконання коду).

## Тест для самоперевірки

Перевірте своє розуміння магічних методів PHP. Виберіть відповідь та розгорніть випадний список для перевірки.

### Запитання 1: Як PHP 8.0+ обробляє конфліктні методи серіалізації?
Якщо клас одночасно реалізує `__sleep()`, `__wakeup()`, `__serialize()` та `__unserialize()`, що станеться в PHP 7.4+?
- A) PHP видасть фатальну помилку (Fatal Error) через дублювання оголошень серіалізації.
- B) PHP виконає `__serialize()` та `__unserialize()`, ігноруючи застарілі методи.
- C) PHP об'єднає результати обох методів серіалізації.

<details>
<summary>Натисніть, щоб переглянути відповідь</summary>

**Відповідь: B**  
Починаючи з PHP 7.4+, рушій віддає пріоритет методам `__serialize()` та `__unserialize()`. Якщо ці сучасні методи присутні, застарілі методи `__sleep()` та `__wakeup()` ігноруються.
</details>

### Запитання 2: Що відбувається при спробі присвоїти значення неіснуючій властивості, якщо `__set` не визначено?
- A) PHP викидає виняток `RuntimeException`.
- B) PHP викидає помилку типу `TypeError`.
- C) PHP динамічно створює публічну властивість в екземплярі об'єкта.

<details>
<summary>Натисніть, щоб переглянути відповідь</summary>

**Відповідь: C**  
У PHP, якщо властивість не визначена в класі та магічний метод `__set` не реалізований, присвоєння значення на кшталт `$object->foo = 'bar'` змусить PHP динамічно створити публічну властивість в екземплярі об'єкта. *(Примітка: Динамічні властивості застаріли в PHP 8.2+ і викликатимуть попередження Deprecated, якщо клас не позначений атрибутом `#[AllowDynamicProperties]`)*.
</details>

- A) `Serializable`

</details>

## Практичні висновки

Магічні методи є потужним інструментом для побудови надзвичайно гнучких API, бібліотек та фреймворків, але в загальній розробці додатків їх слід використовувати помірно.

**Чек-лист найкращих практик**:
1. **Завжди документуйте динамічні структури**: Якщо ви використовуєте `__get`, `__set` або `__call`, додавайте відповідні теги PHPDoc `@property` та `@method` на рівні класу.
2. **Віддавайте перевагу сучасній серіалізації**: Завжди використовуйте `__serialize` та `__unserialize` замість застарілих sleep/wakeup у новому коді для PHP 7.4+.
3. **Уникайте магії на гарячих шляхах виконання**: Не використовуйте магічні методи в циклах з великою кількістю ітерацій, щоб уникнути вузьких місць у продуктивності.
4. **Контролюйте типи**: Починаючи з PHP 8.0+, вказуйте типи параметрів та повертаних значень для магічних методів, щоб запобігти невідповідності типів під час виконання.
