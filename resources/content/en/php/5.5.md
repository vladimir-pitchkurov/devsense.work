# PHP 5.5: Memory Efficiency & Native Security

Reading a 5GB log file line-by-line using `file()` can exhaust your server's memory in seconds, throwing a dreaded "Allowed memory size exhausted" error. PHP 5.5 resolved this forever by introducing generators (`yield`), enabling memory-friendly stream processing on the fly.

Before PHP 5.5, developers had to parse large files or datasets by building giant arrays in memory, or write complex, verbose Iterator objects. Additionally, secure password hashing was a mess of hand-rolled MD5/SHA256 salts, and resource cleanup after errors was messy because PHP lacked a `finally` block.

> [!IMPORTANT]
> PHP 5.5 introduced game-changing memory optimizations via generators and standardized cryptography with the built-in Password Hashing API.

<a id="generators"></a>
## Generators (`yield`)

Generators compute values on-the-fly rather than building and returning a giant array.

```php
// app/Services/LogReader.php
function readLines(string $filePath): Generator
{
    $handle = fopen($filePath, 'r');
    if (!$handle) {
        return;
    }
    try {
        while (($line = fgets($handle)) !== false) {
            yield trim($line);
        }
    } finally {
        fclose($handle);
    }
}
```

* **Why it matters**: Iterating over large files, database results, or infinite sequences takes a constant, tiny amount of memory (often under a few kilobytes) regardless of the dataset size.
* **Consequence**: Batch processing and data pipelines become highly performant and stable under heavy workloads.

<a id="finally"></a>
## The `finally` Block

PHP 5.5 adds the `finally` keyword to the `try-catch` structure. Code inside `finally` runs regardless of whether an exception was thrown or not, even if `return` is called inside `try` or `catch`.

```php
// app/Services/DatabaseClient.php
public function processTransaction()
{
    $this->db->connect();
    try {
        $this->db->execute();
    } catch (\Exception $e) {
        $this->logError($e);
    } finally {
        // This is ALWAYS executed, avoiding resource leaks
        $this->db->disconnect();
    }
}
```

* **Why it matters**: Simplifies cleanup operations like closing file handles, database connections, or unlocking files.

<a id="password-api"></a>
## Native Password Hashing API

Stop hand-rolling salt generation. The new password functions make securing passwords foolproof.

```php
// app/Services/AuthService.php
// Hash a password using bcrypt (PASSWORD_DEFAULT)
$hash = password_hash($password, PASSWORD_DEFAULT);

// Verify the password on login
if (password_verify($password, $hash)) {
    // If the cost parameter or algorithm changes, update the hash
    if (password_needs_rehash($hash, PASSWORD_DEFAULT)) {
        $newHash = password_hash($password, PASSWORD_DEFAULT);
        // Save $newHash to DB
    }
}
```

> [!NOTE]
> `password_hash` generates a secure cryptographic salt automatically and stores it inside the returned hash string, meaning you do not need a separate database column for salts.

## `array_column()` & `::class`

PHP 5.5 introduces two highly practical tools:

### 1. `array_column()`
Extracts a single column from a multi-dimensional array or objects.

```php
// app/Services/Report.php
$users = [
    ['id' => 1, 'name' => 'Alice'],
    ['id' => 2, 'name' => 'Bob']
];
$ids = array_column($users, 'id'); // [1, 2]
```

### 2. `ClassName::class`
Returns the fully qualified namespace name of a class as a string.

```php
// app/Services/Container.php
use App\Models\User;
echo User::class; // "App\Models\User"
```

<a id="opcache"></a>
## Zend OPcache Bundling

Zend OPcache is now built into the PHP core. It stores compiled PHP bytecode in memory, so files do not need to be parsed and compiled on every request.

* **Why it matters**: Increases production performance by 2-3x depending on framework size.
* **Consequence**: Developers must implement cache clearing strategies (like calling `opcache_reset()` or restarting the process manager) during deployment.

<a id="common-mistakes"></a>
## ⚠️ Common Mistakes

### 1. Using the Dangerous `/e` Modifier in `preg_replace`
The `/e` modifier evaluates the replacement string as PHP code, leading to remote code execution (RCE) vulnerabilities. It is deprecated in PHP 5.5.

```php
// app/Helpers/StringHelper.php
// ❌ Deprecated & Highly Insecure!
$output = preg_replace('/(\w+)/e', 'strtoupper("$1")', $text);

// ✅ Correct Approach
$output = preg_replace_callback('/(\w+)/', function($m) {
    return strtoupper($m[1]);
}, $text);
```

### 2. Failing to clean up generator resources when loop terminates early
If you break out of a generator loop, resources like open files might remain open unless wrapped in `try/finally` blocks inside the generator.

```php
// app/Services/FileReader.php
// ❌ Dangerous: if loop breaks, fclose() never runs
function readData($file) {
    $fh = fopen($file, 'r');
    while($line = fgets($fh)) yield $line;
    fclose($fh);
}

// ✅ Correct Approach
function readDataSafe($file) {
    $fh = fopen($file, 'r');
    try {
        while($line = fgets($fh)) yield $line;
    } finally {
        fclose($fh); // Guaranteed to run when generator is destroyed
    }
}
```

### 3. Relying on the old `mysql` extension
The `mysql_connect()` functions are deprecated in PHP 5.5.

```php
// app/Database/LegacyDb.php
// ❌ Deprecated in PHP 5.5, throws E_DEPRECATED
$conn = mysql_connect('localhost', 'user', 'pass');

// ✅ Correct Approach
$conn = new PDO('mysql:host=localhost;dbname=test', 'user', 'pass');
```

<a id="practical-recipes"></a>
## Practical Recipes

### Expectation vs Reality: `finally` and Returns

What happens when both the `try` block and the `finally` block return values?

```php
// app/Demo/FinallyDemo.php
function testFinally(): string
{
    try {
        return "Return from try";
    } finally {
        return "Return from finally";
    }
}

// Expectation: Returns "Return from try"
// Reality:
echo testFinally(); // Output: Return from try (but in some cases finally can override, let's look at standard execution: finally runs and if it returns, it overrides the try return value!)
```

> [!WARNING]
> If you return a value inside the `finally` block, it will override any value returned in the `try` or `catch` blocks. Avoid putting `return` statements inside `finally`.

<a id="backward-incompatible"></a>
## Backward Incompatible Changes

1. **`preg_replace` `/e` modifier deprecation**: Throws warnings; must use `preg_replace_callback()`.
2. **`mysql` extension deprecation**: Throws `E_DEPRECATED` warnings on connections.
3. **`empty()` on expressions**: Prior to 5.5, `empty()` only accepted variables (e.g. `empty($x)`). Now it accepts expressions like `empty(trim($x))`. While not directly breaking, it makes old workarounds obsolete.
4. **`pack()` and `unpack()` format changes**: Some 64-bit alignment changes might affect binary serialization.

## 🧠 Self-Check Questions

1. **True or False?** A generator function returns a `Generator` object that implements the `Iterator` interface.
2. If an exception is thrown in a `try` block and is NOT caught by any `catch` block, does the code inside the `finally` block still run?
3. What happens if you try to pass an array of cost parameters directly to `password_verify()`?
4. **True or False?** `ClassName::class` works at runtime even if the class is not loaded or does not exist.

<details>
<summary><b>Reveal Answers</b></summary>

1. **True.** Generators return an instance of the `Generator` class, which allows them to be used directly inside `foreach` loops.
2. **Yes.** The `finally` block is guaranteed to execute before the exception bubbles up and halts script execution.
3. Nothing, because `password_verify` only accepts two arguments: the plain password and the hash. It reads the algorithm and cost parameters directly from the hash string itself.
4. **True.** `::class` is a compile-time resolution. It does not attempt to autoload or verify the existence of the class; it simply returns the namespace string.
</details>
