# PHP 8.4: Major Features & Interactive Guide

PHP 8.4 is a major "power tools" release. It completely changes how we express invariants at property boundaries (Property Hooks, asymmetric visibility), introduces framework-level internals (Lazy Objects), and resolves long-standing DOM extension issues with WHATWG-compliant DOM classes.

In this guide, we'll dive deep into these features using lively, human-friendly examples, explore common gotchas, and test your knowledge at the end!

<a id="property-hooks"></a>
## Property Hooks (get/set logic on properties)

For years, PHP developers had to write verbose boilerplate getters and setters just to validate or format values before saving them. PHP 8.4 introduces **Property Hooks** directly in the property declaration.

There are two kinds of hooks:
- `set`: triggered when writing to a property.
- `get`: triggered when reading a property.

Let's see this in action:

```php
// app/DTO/Person.php
final class Person
{
    // A hook can write to a backing property using $this->propName
    public string $firstName {
        set => ucfirst(strtolower($value));
    }

    public string $lastName {
        set {
            if (strlen($value) < 2) {
                throw new InvalidArgumentException('Last name is too short!');
            }
            $this->lastName = $value;
        }
    }

    // Computed (virtual) property with no backing storage!
    public string $fullName {
        get => $this->firstName . ' ' . $this->lastName;
    }
}
```

> [!NOTE]
> **Did you know?**
> Properties that define only a `get` hook are virtual by default and don't occupy any memory or database-backing footprint in objects.

### ⚠️ Common Mistakes

**1. Attempting to pass a hooked property by reference**
Because accessing a property with hooks calls a function under the hood, you cannot pass it by reference:
```php
// app/Services/ContactService.php
function cleanString(string &$str) {
    $str = trim($str);
}

$person = new Person();
cleanString($person->firstName); // ❌ Fatal Error: Cannot pass property Person::$firstName by reference
```

**2. Accidentally creating infinite recursion in `set` hooks**
If you assign to `$this->propertyName` inside its own hook using `$this->propertyName = $value`, it compiles but if you do not use the backing variable logic correctly, you might trigger infinite recursion. Fortunately, shorthand expressions (`=>`) assign to the backing value automatically.

<a id="asymmetric-visibility"></a>
## Asymmetric Property Visibility (`public private(set)`)

In PHP 8.4, you can now define different visibility permissions for reading and writing properties. This is a massive improvement for read-only DTOs and aggregate roots in Domain-Driven Design (DDD).

```php
// app/Models/User.php
final class User
{
    // Readable anywhere, but only modifiable from within this class
    public private(set) string $email;

    public protected(set) int $loginAttempts = 0;

    public function __construct(string $email)
    {
        $this->email = $email;
    }

    public function incrementAttempts(): void
    {
        $this->loginAttempts++;
    }
}
```

> [!NOTE]
> **Did you know?**
> Asymmetric visibility requires the write operation (`set`) to be **stricter** than the read operation. For example, `private public(set)` is invalid and will throw a syntax error.

<a id="lazy-objects"></a>
## Lazy Objects (Ghosts & Proxies via Reflection)

PHP 8.4 introduces native support for **Lazy Objects**. This is primarily targetted at framework and ORM authors (like Doctrine or Laravel's Eloquent relations) who need to defer expensive database hydration or API calls until a property is accessed.

Previously, libraries had to generate complex proxy classes on the fly. Now, Reflection supports this natively:

```php
// app/Services/Container.php
$initializer = static function (LargeService $service) {
    $service->loadHeavyConfiguration();
};

$r = new ReflectionClass(LargeService::class);
// Creates a lazy ghost instance of LargeService
$lazyService = $r->newLazyGhost($initializer);
```

The object's initializer function is only executed once you attempt to access any property on `$lazyService`.

<a id="deprecated-attribute"></a>
## Userland Deprecations with `#[Deprecated]`

Previously, to deprecate custom functions or methods, developers had to trigger `E_USER_DEPRECATED` manually. Now you can use the native `#[\Deprecated]` attribute:

```php
// app/Helpers/LegacyMath.php
class LegacyMath
{
    #[\Deprecated(message: "Use BCMath or native division instead", since: "1.4.0")]
    public static function divide(int $a, int $b): float
    {
        return $a / $b;
    }
}
```

When someone calls this method, PHP will automatically trigger a deprecation warning showing your message and version.

<a id="dom-modern"></a>
## WHATWG-Compliant DOM Namespace (`Dom\*`)

For a long time, PHP's `DOMDocument` suffered from poor HTML5 compliance. PHP 8.4 introduces a modern, WHATWG-compliant DOM API under the `Dom` namespace.

```php
// app/Services/HtmlParser.php
// Parse modern HTML5 structures without hacky workarounds
$dom = Dom\HTMLDocument::createFromString('<main><article>Modern HTML5!</article></main>');
$node = $dom->querySelector('article');

echo $node->textContent; // Output: Modern HTML5!
```

Existing classes like `DOMDocument` remain for backward compatibility, but developers are encouraged to migrate to `Dom\HTMLDocument` and `Dom\XMLDocument`.

<a id="request-parse-body"></a>
## Non-POST Multipart Parsing: `request_parse_body()`

If you've ever built a REST API in PHP where users upload files via `PUT` or `PATCH` requests, you know the pain: `$_FILES` and `$_POST` are only populated for `POST` requests. Developers had to parse raw stream chunks manually.

PHP 8.4 gives us `request_parse_body()`, which parses multipart/form-data RFC1867 requests for any HTTP verb:

```php
// public/index.php
if ($_SERVER['REQUEST_METHOD'] === 'PUT') {
    [$postData, $files] = request_parse_body();
    
    // $postData contains form fields
    // $files contains uploaded files mapped identically to $_FILES
}
```

<a id="new-functions"></a>
## New Array & Math Helpers

PHP 8.4 packs several utility functions to make daily development easier:

### 1. `array_find()`, `array_find_key()`, `array_any()`, `array_all()`

```php
// app/Services/Validator.php
$users = [
    ['name' => 'Alice', 'role' => 'user'],
    ['name' => 'Bob', 'role' => 'admin'],
];

// Find the first admin user
$admin = array_find($users, fn($u) => $u['role'] === 'admin');

// Check if any users exist
$hasUsers = array_any($users, fn($u) => $u['role'] === 'user');
```

### 2. Multibyte String Trimming (`mb_trim`)
Native `trim()` is not multibyte-safe, leaving trailing wide space characters in UTF-8. PHP 8.4 fixes this with `mb_trim()`, `mb_ltrim()`, and `mb_rtrim()`.

<a id="backward-incompatible"></a>
## Backward Incompatible Changes & Deprecations

Before updating production servers to PHP 8.4, audit your codebase for these changes:

1. **Implicitly Nullable Parameters are Deprecated**
   ```php
   // ❌ Deprecated in PHP 8.4
   function save(string $name = null) {}

   // ✅ Correct approach
   function save(?string $name = null) {}
   ```
2. **`exit()` and `die()` Behavior**
   They are now functions instead of statements. This means they are subject to standard type coercions and strict types. If you pass an invalid object or array, it will throw a `TypeError`.
3. **Resource to Object Migrations**
   Extensions like DBA, ODBC, and SOAP now return objects instead of resources. If you use `is_resource()` checks on these connections, they will now return `false`.
