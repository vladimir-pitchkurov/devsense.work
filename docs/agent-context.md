# Контекст проекта DevSense для AI-агентов

Этот документ предназначен для того, чтобы новые AI-агенты могли быстро войти в курс дела, понять архитектуру, текущее состояние проекта, а также правила написания/модификации контента и код-гайдлайны.

---

## 1. Стек технологий и инфраструктура (Laravel Sail)

Проект работает в локальной среде через **Laravel Sail** (Docker-окружение в WSL2):
* **Core**: PHP 8.5.4 (Laravel 11 / 12)
* **БД**: PostgreSQL 16 (контейнер `pgsql`) — основная база данных проекта.
* **Кэширование и очереди**: Redis (Alpine) — используется для кэширования метаданных и отпарсенного HTML, а также сессий/очередей.
* **Поиск**: Meilisearch
* **Тестирование почты**: Mailpit
* **Тестирование браузера**: Selenium (headless Chromium)

### Команды для локальной разработки и обслуживания:
* Запуск Sail: `wsl ./vendor/bin/sail up -d`
* Остановка Sail: `wsl ./vendor/bin/sail down`
* Сборка Sail: `wsl ./vendor/bin/sail up -d --build`
* Запуск тестов: `wsl ./vendor/bin/sail test`
* Запуск миграций и базовых сидеров: `wsl ./vendor/bin/sail artisan migrate:fresh --seed`
* Импорт основных статей (локали `en`, `ru`, `ua`, `bg`) без перезаписи существующих: `wsl ./vendor/bin/sail artisan app:migrate-articles-to-database`
* Импорт основных статей с перезаписью изменившихся (smart diff): `wsl ./vendor/bin/sail artisan app:migrate-articles-to-database --update`
* Импорт переводов статей (локали `de`, `fr`, `es`, `it` под `content-translations`) без перезаписи: `wsl ./vendor/bin/sail artisan app:seed-translations`
* Импорт переводов статей с перезаписью изменившихся (smart diff): `wsl ./vendor/bin/sail artisan app:seed-translations --update`
* Полное сидирование квизов и ачивок (очистка и повторный импорт): `wsl ./vendor/bin/sail artisan db:seed --class=QuizSeeder`
* Генерация статического файла sitemap.xml: `wsl ./vendor/bin/sail artisan sitemap:write`
* Пинг IndexNow (только новые/изменившиеся после последнего пинга): `wsl ./vendor/bin/sail artisan seo:ping-indexnow`
* Принудительный пинг IndexNow для всех страниц: `wsl ./vendor/bin/sail artisan seo:ping-indexnow --force`

> [!WARNING]
> **Кэширование переменных окружения (.env)**:
> При изменении или добавлении переменных окружения в `.env` на сервере, новые значения **не применятся** автоматически из-за кэширования конфигурации Laravel и кэша OPcache в PHP-FPM.
> В таких случаях необходимо сбросить кэш и перезапустить/перезагрузить PHP-FPM:
> ```bash
> php artisan optimize:clear
> sudo systemctl reload php8.5-fpm # подставьте вашу версию php-fpm
> ```

## 2. Архитектура работы с контентом

Изначально статьи были статическими markdown-файлами. Сейчас реализована **гибридная модель**:

1. **База данных как единственный источник истины**:
   * Статьи хранятся в таблицах `articles` и `article_translations` (поддержка 8 локалей: `en`, `ru`, `ua`, `bg`, `de`, `fr`, `es`, `it`).
   * Связанные сущности: категории (`categories`), теги (`tags`), авторы (`users`).
2. **Консольный импорт**:
   * Команда `app:migrate-articles-to-database` сканирует файлы в `resources/content/{locale}/{category}/{slug}.md` (для локалей `en`, `ru`, `ua`, `bg`) и импортирует их в PostgreSQL.
   * Команда `app:seed-translations` сканирует файлы в `resources/content-translations/{locale}/{category}/{slug}.md` (для локалей `de`, `fr`, `es`, `it`) и импортирует их.
   * По умолчанию они пропускают уже импортированные статьи. Флаг `--update` включает сравнение контента/метаданных и обновление измененных статей.
   * Во время деплоя на продакшн эти команды запускаются автоматически для синхронизации контента.
3. **MarkdownContentService**:
   * Класс `App\Services\MarkdownContentService` сначала пытается найти статью в БД по `slug`, `category` и `locale`.
   * Если статья найдена, её контент парсится из Markdown в HTML.
   * Если статья отсутствует в БД, сервис делает fallback-запрос к файловой системе (`resources/content/...`).
   * Результаты кэшируются через `Cache::rememberForever` с использованием кэш-ключа, зависящего от времени последнего изменения статьи.
4. **Локализация ссылок**:
   * Внутри статей все относительные ссылки на другие статьи автоматически локализуются методом `localizeLinks` в `MarkdownContentService`. Например, если текущая локаль `ru`, ссылка вида `/php/8.4` преобразуется в `/ru/php/8.4`.

## 3. Ролевая модель и Кабинет автора

В проекте есть три роли пользователей (`role` в таблице `users`):
* `reader` (Читатель) — обычный пользователь.
* `author` (Автор) — может писать и редактировать свои статьи.
* `super-admin` (Супер-администратор) — полный доступ ко всему.

### Разграничение прав в Админке (Кабинете автора):
* При регистрации через `/register` пользователю автоматически присваивается роль `author`.
* Доступ к админ-панели (маршруты с префиксом `admin`) регулируется Gate `access-admin`. Доступ открыт для `author` и `super-admin`.
* **Ограничение контента**: В `ArticlesController` (CRUD статей) не-администраторы видят, редактируют и удаляют **только те статьи, авторами которых они являются**. Супер-администратор видит и управляет всеми статьями в системе.
* **Настройки профиля**: В `/admin/profile` авторы могут редактировать свои метаданные (job title, bio, социальные ссылки) и флаг `is_public` (публичность профиля).

## 4. Архитектура квизов и ачивок

Для повышения вовлеченности пользователей реализована система интерактивных тестов (квизов) и достижений (бейджей/ачивок).

1. **Квизы**:
   * Данные хранятся в таблицах `quizzes`, `quiz_translations`, `quiz_questions`, `quiz_question_translations`.
   * Основной квиз: "Собеседование по основам PHP" (`php-basics-interview`), состоящий из 100 вопросов. Вопросы структурированы по темам: базовый синтаксис, области видимости, суперглобальные переменные, ООП, магические методы, функциональный PHP, ошибки и исключения.
   * Вопросы и ответы загружаются из локализованных JSON-файлов: `resources/quizzes/php-basics-interview/{locale}.json` (всего 8 поддерживаемых локалей).
   * Если фича языка специфична для PHP 7.0+, в тексте вопроса в конце указывается версия в круглых скобках, например: `(PHP 8.0+)`.
2. **Ачивки (Бейджи)**:
   * Бейджи хранятся в таблицах `badges` и `badge_translations`.
   * Для квиза по основам PHP реализовано 4 уровня наград на основе процента правильных ответов:
     * **Bronze** (Бронза): >= 50%
     * **Silver** (Серебро): >= 70%
     * **Gold** (Золото): >= 85%
     * **Expert** (Эксперт): 100%
   * Векторные изображения бейджей расположены в `public/images/badges/`.

## 5. Индексация, Sitemap и IndexNow

Для оптимизации SEO и мгновенной индексации поисковыми роботами и AI-краулерами используются следующие механизмы:

1. **XML Sitemap**:
   * Генерируется статически в `public/sitemap.xml` с помощью команды `php artisan sitemap:write` (вызывается билдером `App\Services\SiteSitemapBuilder`).
   * Включает главную страницу, подразделы, все опубликованные статьи, публичные профили авторов (где `is_public = true`) и квизы.
   * Автоматически добавляет альтернативные ссылки `hreflang` для всех 8 языковых версий.
2. **IndexNow**:
   * Команда `seo:ping-indexnow` отправляет список новых или измененных страниц в поисковые системы (Bing, Yandex и др.) через API IndexNow.
   * Чтобы избежать повторного пинга сотен страниц на каждом деплое (поскольку команда `optimize:clear` сбрасывает Redis-кэш), метка времени последнего пинга сохраняется в постоянный файл на диске: `storage/app/.indexnow_last_run`.
   * Сканируются только статьи и квизы, время обновления (`updated_at` или `filemtime`) которых новее времени модификации этого файла-флага.
   * Флаг `--force` сбрасывает проверку времени и отправляет все доступные URL.

## 6. Правила написания и форматирования статей

Все статьи в проекте пишутся на Markdown и должны строго соответствовать следующим правилам для сохранения единообразия UI/UX и SEO-показателей:

### 1. Front Matter (YAML-блок в начале файла)
Каждая статья должна начинаться с YAML-блока метаданных:
```yaml
---
title: "Название статьи: Подзаголовок | DevSense"
description: "SEO-оптимизированное описание статьи (150-160 символов) с ключевыми словами."
faq:
  - question: "Вопрос 1 по теме?"
    answer: "Краткий емкий ответ для разметки FAQ Schema."
  - question: "Вопрос 2?"
    answer: "Ответ на второй вопрос."
---
```
* **Title**: Должен содержать ключевое название темы и суффикс ` | DevSense`.
* **Description**: Должен кратко описывать пользу статьи для разработчика.
* **FAQ**: Массив вопросов и ответов. Он парсится системой для автоматической генерации JSON-LD разметки (`FAQPage` schema) на странице статьи, что критически важно для SEO.

### 2. Заголовок H1
В тексте статьи должен быть ровно один заголовок первого уровня `#`:
```markdown
# Название статьи: Основная тема
```

### 3. Оглавление (Table of Contents)
После H1 и краткого введения обязательно должно идти оглавление со ссылками на подразделы:
```markdown
## Содержание
* [Первый подраздел](#first-section)
* [Второй подраздел](#second-section)
```
Каждому подразделу в тексте должен соответствовать HTML-якорь непосредственно перед заголовком:
```markdown
<a id="first-section"></a>
## Первый подраздел
```

### 4. Оформление кода и указание файлов
В примерах кода обязательно указывать путь к файлу в первой строчке в виде комментария:
```php
// app/Services/MyService.php
class MyService {
    // ...
}
```
Всегда используйте строгую типизацию в примерах кода PHP (`declare(strict_types=1);` приветствуется при необходимости, типы аргументов и возвращаемых значений обязательны).

### 5. Информационные блоки (GitHub-style callouts)
Для важных замечаний или интересных фактов используйте разметку алертов:
```markdown
> [!NOTE]
> **А вы знали?**
> Текст полезного замечания.
```
Также поддерживаются `[!WARNING]`, `[!IMPORTANT]`, `[!TIP]`.

### 6. Раздел работы над ошибками (Common Mistakes)
В технической статье обязательно должен быть блок с разбором типичных ошибок:
```markdown
### ⚠️ Типичные ошибки
 
**1. Название ошибки**
Описание того, как делать не надо, и правильный вариант решения.
```

### 7. Блок самопроверки (Self-Check)
В самом конце статьи располагается блок интерактивных вопросов для читателя:
```markdown
## 🧠 Вопросы для самопроверки
 
1. Какой-то технический вопрос?
2. Второй вопрос?
 
<details>
<summary><b>Показать ответы</b></summary>
 
1. Правильный ответ на первый вопрос с объяснением.
2. Правильный ответ на второй вопрос.
</details>
```

## 7. Правила работы для AI-агентов (AI Agent Guidelines)

Для поддержания качества кодовой базы, документации и эффективного взаимодействия с пользователем, AI-агенты обязаны следовать правилам:

1. **Язык общения и саммари**: Все ответы, пояснения и резюме о проделанной работе пользователю должны быть написаны исключительно на **русском языке**.
2. **Комментарии в коде**: В самом коде комментарии следует оставлять только при крайней необходимости (код должен быть самодокументируемым). Все комментарии в кодовой базе (файлы `.php`, `.vue`, `.js` и т.д.) должны быть написаны строго на **английском языке**.
3. **Рекомендуемый коммит**: В самом конце ответа после выполнения задачи агент должен предложить готовый и информативный **Git commit message** (желательно в формате Conventional Commits).
4. **Обязательные переводы (All locales)**: Любой создаваемый или модифицируемый контент (статьи, квизы, метаданные, бейджи) должен сразу переводиться на все поддерживаемые языки: `en`, `ru`, `ua`, `bg`, `de`, `fr`, `es`, `it`. Недопустимо оставлять контент частично непереведенным.
5. **Обновление документации**: Любые архитектурные изменения, новые команды, настройки окружения или логика работы должны быть своевременно описаны как в `README.md`, так и в этом файле `docs/agent-context.md`.
6. **Сброс кэша при изменении `.env`**: При изменении или добавлении переменных окружения на продакшн-сервере, агент обязан напомнить о необходимости сброса кэша конфигурации (`php artisan optimize:clear`) и перезапуска/перезагрузки PHP-FPM.
